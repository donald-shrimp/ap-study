# 解答解説の共通記述ルール — すべての資格・科目

> **対象：** 応用情報・AB-730・FP2級などの全資格、選択式と記述／実技の解説、既存教材の改稿と今後の新規作問。
> **状態：** 共通の表示対応は実装・公開済み。表示の要件は [解答解説の全資格共通仕様](explanation-presentation-spec.md)、作業全体の順序は [問題の追加手順](content-authoring.md)を参照。教材ごとの作成・改稿と独立レビューはその手順に従う。

## 1. 解説の役割を分ける

| フィールド | 読者の疑問 | 記述ルール |
| --- | --- | --- |
| `summary` | **「この問題は何を問うているのか？」** | 任意。問われる概念・判断基準・区別すべき制度を簡潔に示す。解答番号や解説全文は書かない |
| `explanation` | **「なぜこの答えになるのか？」** | 問題固有の判断の決め手と根拠を示す。理解に必要な用語の定義・途中計算・例外を補う |
| `takeaway` | **「次の問題でも使える知識は何か？」** | 任意。ルール・数値・見分け方を再利用できる形にまとめる。summaryやexplanationの単なる言い換えは追加しない |

これらは**説明の役割を区別するフィールド**で、三つの欄を埋めるためのものではない。`summary`・`takeaway` は新規作問でも任意とし、短い問題は `explanation` と各肢の理由だけで十分な場合もある。同じ文章を複製したり、専用の見出しを本文に書き足したりしない。既存の教材契約で個別に必須とされる項目は、その契約に従う。

定義・手順・根拠・例外は、説明の不足を確かめる観点であり、毎問書く項目や固定の記述順ではない。問題の判断の決め手から説明し、必要な情報だけを加える。文数や文章量を品質の基準にしない。

### `choiceReasons[]`（選択式）

選択肢の**順番と1対1**で、各肢の正誤理由を記す。正答肢だけでなくすべての肢について、正誤の分岐点を示す。比較対象・要件・例外は、その判断に必要なものを説明する。

- 問題が「最も適切」か「最も不適切」かを最初に確認する。単純に「正解」だけで理由を代用しない。
- 「この選択肢は公式正答ではない」「独立レビューで検証する」といった定型文で埋めない。
- 1肢につき根拠が分かる独立した文章にする。選択肢本文の長い引用を繰り返すのではなく、正誤の分岐点を示す。
- `choiceReasons` の位置と `choices[].id`・公式正答を一致させる。複数選択でも各肢の理由を記載する。

### `hints[].text`（段階ヒント）

解答前に見せる情報。第一段階は**どの観点で考えるか**、第二段階は**どの条件を比較するか**とし、正答番号・正答の全文・正答だけを識別できる直接的な手掛かりを出さない。`revealsAnswer:false` は見かけだけでなく実際の内容で保証する。ヒントに重要語の強調を付ける場合も、強調自体が答えの漏えいにならないことを確認する。

### 記述式・ケース／実技

既存の解答欄の `explanation` には、**問われる内容・判断／計算の順序・答えに到達する根拠**をその欄に固有の形で記述する。三つの新フィールドを全解答欄へ機械的に新設せず、必要な説明を一つの `explanation` にまとめる。既存の数式・表・コード等の限定書式は維持し、強調には共通の太字記法を使う。

`rubric[]` は解答に必要な採点観点を従来どおり記載する。`referenceAnswers`・正答ID・数値の採点用文字列を装飾しない。`rubric[]`・ラベル・出典等も今回の太字対応の対象には追加しない。

## 2. 強調方法：Markdownの太字だけ

**重要なのは文章自体で、太字は判断の決め手を見つける補助。**

### 書いてよい記法

- `**判断基準**`、`**5年以下**`、`**例外：条件を満たす場合**` のように、同じ行で閉じる `**…**`。
- 判断の決め手だけを強調する。フィールドごとの必須数・最低数を設けず、強調なしでもよい。太字を増やすために文章を追加しない。
- 強調するのは **概念名・数値・判定時点・要件・例外・比較の決定的な違い**。文章全体を囲わず、短い意味単位に限定する。
- 数値だけでは誤解を招く場合は、適用条件・単位・基準時点と合わせて示す。太字だけを拾っても、条件のない一般則として誤学習しないようにする。
- 装飾のない過去の説明は**そのままで正しく表示**されるべきであり、無理に太字を追加する必要はない。

### 書かない記法

- 生HTML：`<b>`、`<strong>`、`<br>`、`<span>`、任意のHTMLタグや属性。
- 自動リンク、画像、見出し、脚注、フルMarkdownを強調のために追加しない。問題文・科目B／実技の解説で既存の限定書式が扱う数式・表・コード・段落は引き続き使える。コード内の `**` は強調ではなく文字として扱う。
- `****` のような空の強調、閉じていない `**`、過度なネスト、大半の単語を太字にする記述。
- 色の指定や「正解は3」といった装飾目的のネタバレ。太字のみを根拠の代わりにしない。

## 3. JSONの作問例

### 選択問題の例（例示用の架空設問）

~~~json
{
  "summary": "この問題は、デビットカードとクレジットカードの**支払い時点の違い**を問う。",
  "explanation": "クレジットカードは商品を購入したあとで代金を支払う**後払い**。これに対し、デビットカードは原則として利用時に銀行口座から引き落とす**即時払い**。支払手段の名称ではなく、資金がいつ移動するかを確認して判断する。",
  "choiceReasons": [
    "適切。カード会社がいったん立て替える**後払い**の仕組みを説明している。",
    "不適切。デビットカードを後払いとしているが、原則として**利用時の即時引落し**である。"
  ],
  "takeaway": "クレジット＝**後払い**、デビット＝**即時払い**、チャージ型プリペイド＝**前払い**。",
  "hints": [
    {
      "title": "比較の軸",
      "text": "買い物の前・その場・後のうち、いつ利用者のお金が動くかを考えよう。",
      "revealsAnswer": false
    },
    {
      "title": "仕組みを分ける",
      "text": "カード会社による立替と、銀行口座からの直接引落しの違いを整理しよう。",
      "revealsAnswer": false
    }
  ]
}
~~~

※ `choiceReasons` は仕組みを示す**抜粋例（2肢）**。実際の登録では問題の全選択肢に1件ずつ理由を付け、公式正答ID・説明を照合する。

### 短い問題の解説（抜粋例）

~~~json
{
  "explanation": "二分探索では、中央の値との大小比較で探索範囲を半分に絞る。そのため、データが**探索キーの順に整列済み**である必要がある。"
}
~~~

解説部分だけの例。登録には問題形式が要求する本文・正答・全肢の理由等も用意する。`summary`・`takeaway` に同じ内容を言い換えて追加する必要はない。

### 数式・手順がある問題の例

~~~text
summary:
  この問題は、割合を算出する際の**分母に何を使うか**を判断する。
explanation:
  **全体の合計値を分母、対象の値を分子**に置く。
  例えば対象40件／全体200件なら、40÷200×100＝20％。
  **「全体」と「対象」を逆にしない**ことが重要。
takeaway:
  割合（％）＝**対象÷全体×100**。計算後に単位を確認する。
~~~

数学・IT・会計・法律・医療や語学など、試験ごとに別の強調方法を採用しない。数式そのものの表記・実装は既存の問題形式契約を優先する。

## 4. 文章の品質基準

1. **問題固有性：** その設問が何を区別させたいかを説明する。汎用の分野紹介だけにしない。
2. **判断可能性：** 選択肢のどの語句・条件が正誤を決めたか、数字の根拠や例外を省略せずに書く。
3. **誤りを教えない：** 正答や原本の条件を変えない。計算問題は途中式と単位を独立検算する。
4. **出題時点を厳守：** 税・年金・法改正・製品仕様などは原本の法令基準日／公表時点と現行制度を混同しない。現行制度との差は必要なら明示する。
5. **簡潔さ：** 判断の決め手が短く伝わるかを確認する。summaryは論点、explanationは根拠、takeawayは再利用できる知識とし、任意項目を埋めるための重複や定型的な前置きを加えない。
6. **学習者への配慮：** 略語は初出で補足し、制度名・数値を似たものと比較して説明する。断定できない条件は断定せず、根拠を示す。
7. **レビュー：** 出典・法令・公式解答・全肢の理由・計算式・強調の適切性を別担当が確認する。太字を付けただけで `reviewed` と扱わない。

過去問の内容確認・正誤判定は原本の基準で行う。現行法令の全問照合を公開の追加条件にせず、最終確認日・改正確認済みの状態は既存の `legalReview` に記録する。未確認という説明や確認日を学習画面へ追加しない。

## 5. 既存教材を改訂するとき

共通表示は [確認記録](explanation-presentation-verification.json)のとおり公開済み。既存教材は作成元・版・独立レビューを保って改訂する。未対応の書式が必要な場合だけ、先に土台側で表示対応と検証を行う。

1. 対象の作成元・最新の版・既存レビューを確認し、生成物へ直接変更を加えない。
2. 存在する解説フィールドの必要な箇所だけを強調する。機械的に数字や用語を一括囲いせず、任意フィールドを埋めるための改稿をしない。
3. 装飾だけの変更なら、**強調のマーカーを除いた文章が元と一致**することを照合する。数式・コード・原本の強調を壊さない。説明そのものを訂正する場合は、装飾変更と区別して根拠と差分を残す。
4. 同じIDの版を増やし、別担当が修正後の内容を確認する。所定のハッシュ・確認台帳を更新し、再生成・対象画面の確認を経て公開する。
5. 内容の独立レビューが終わるまでは草稿のまま扱い、作者自身の確認で承認済みにしない。現行法令の確認は別に管理し、確認根拠がなければ`legalReview.status: unverified`を保持する。内容が承認済みでも現行法令は未確認のままでよい。

## 6. 作問・レビュー担当のチェックリスト

- [ ] `summary` がある場合、「この問題で問う判断・知識」を具体的に示しているか。
- [ ] `explanation` に判断の決め手と根拠があり、理解に必要な途中式・例外が欠けていないか。
- [ ] `takeaway` がある場合、類題で再利用でき、他の説明の単なるコピーではないか。
- [ ] 欄を埋めるための重複や前置きを加えず、短い説明で足りる問題を引き延ばしていないか。
- [ ] すべての `choiceReasons` に各肢固有の正誤理由があるか。
- [ ] `**…**` は正誤の分岐点に絞られているか。閉じ忘れ、HTML混入、強調過多がないか。
- [ ] ヒントは段階的で、強調を含めて答え漏えいがないか。
- [ ] 出題基準日、原本との一致、法令・計算の出典、独立レビュー／版管理が適切か。
- [ ] 強調付き教材の公開前に、共通表示対応の公開・確認が済んでいるか。
