# 解答解説の共通記述ルール — すべての資格・科目

> **対象：** 応用情報・AB-730・FP2級などの全資格、選択式と記述／実技の解説、既存教材の改稿と今後の新規作問。
> **状態：** 作問ルールの提案。表示の実装要件は [解答解説の全資格共通仕様](explanation-presentation-spec.md) を参照。**実装・既存教材80問の改稿・レビューは別PR**で実施する。

## 1. 一問に三つの異なる役割を持たせる

| フィールド | 読者の疑問 | 記述ルール |
| --- | --- | --- |
| `summary` | **「この問題は何を問うているのか？」** | 問われる概念・判断基準・区別すべき制度を、原則1〜2文で示す。解答番号や解説全文は書かない |
| `explanation` | **「なぜこの答えになるのか？」** | 用語定義→判断・計算の手順→結論の根拠→誤認しやすい例外の順で、問題固有の説明を書く。必要な途中計算を省略しない |
| `takeaway` | **「次の問題でも使える知識は何か？」** | ルール・数値・見分け方を、原則1〜3文で再利用できる形にまとめる。summaryを単に言い換えない |

これらは**表示を分割するための独立した意味のフィールド**。同じ文章を3回複製しない。教材契約上の任意フィールドはそのまま任意とする。ただし**解説を新規に作成・充実させるときは、存在する3フィールドに役割どおりの内容を入れる**。設問や解答形式により該当しない場合は、無理な重複を作らない。

### `choiceReasons[]`（選択式）

選択肢の**順番と1対1**で、各肢が適切／不適切である理由を記す。正答肢だけでなくすべての肢について、比較対象・法的要件・例外・誤りの箇所を説明する。

- 問題が「最も適切」か「最も不適切」かを最初に確認する。単純に「正解」だけで理由を代用しない。
- 「この選択肢は公式正答ではない」「独立レビューで検証する」といった定型文で埋めない。
- 1肢につき根拠が分かる独立した文章にする。選択肢本文の長い引用を繰り返すのではなく、正誤の分岐点を示す。
- `choiceReasons` の位置と `choices[].id`・公式正答を一致させる。複数選択でも各肢の理由を記載する。

### `hints[].text`（段階ヒント）

解答前に見せる情報。第一段階は**どの観点で考えるか**、第二段階は**どの条件を比較するか**とし、正答番号・正答の全文・正答だけを識別できる直接的な手掛かりを出さない。`revealsAnswer:false` は見かけだけでなく実際の内容で保証する。ヒントに重要語の強調を付ける場合も、強調自体が答えの漏えいにならないことを確認する。

### 記述式・ケース／実技

既存の大問、設例、解答欄の `explanation` には、**問われる内容・判断／計算の順序・答えに到達する根拠**をその欄に固有の形で記述する。`rubric[]` に採点観点がある場合は、解答に必要な条件だけを提示する。三つの新フィールドを全解答欄へ機械的に新設する要件ではない。必要な説明が一つの `explanation` にまとまることを優先し、共通の太字書式だけを適用する。

## 2. 強調方法：Markdownの太字だけ

**重要なのは文章自体で、太字は判断の決め手を見つける補助。**

### 書いてよい記法

- `**判断基準**`、`**5年以下**`、`**例外：条件を満たす場合**` のように、同じ行で閉じる `**…**`。
- 原則として `summary` は**1か所程度**、`explanation` は**2〜4か所程度**、`takeaway` は**1〜2か所程度**、`choiceReasons` は**必要な箇所だけ（0〜2か所程度）**。これは読みやすさの目安で、機械的な最低数・上限ではない。
- 強調するのは **概念名・数値・判定時点・要件・例外・比較の決定的な違い**。文章全体を囲わず、短い意味単位に限定する。
- 装飾のない過去の説明は**そのままで正しく表示**されるべきであり、無理に太字を追加する必要はない。

### 書かない記法

- 生HTML：`<b>`、`<strong>`、`<br>`、`<span>`、任意のHTMLタグや属性。
- 自動リンク、画像、見出し、テーブル、脚注、フルMarkdownは**解説の強調用として要求しない**。問題文でサポートされる限定書式・数式とは別に扱う。
- `****` のような空の強調、閉じていない `**`、過度なネスト、大半の単語を太字にする記述。
- 色の指定や「正解は3」といった装飾目的のネタバレ。太字のみを根拠の代わりにしない。

## 3. JSONの作問例

### 選択問題の例（例示用の架空設問）

~~~json
{
  "summary": "この問題は、デビットカードとクレジットカードの**支払い時点の違い**を問う。",
  "explanation": "クレジットカードは商品を購入したあとで代金を支払う**後払い**。これに対し、デビットカードは原則として利用時に銀行口座から引き落とす**即時払い**。支払手段の名称ではなく、資金がいつ移動するかを確認して判断する。",
  "choiceReasons": [
    "適切。カード会社がいったん立て替える**後払い**の仕組みを説明している。",
    "不適切。デビットカードを後払いとしているが、原則として**利用時の即時引落し**である。"
  ],
  "takeaway": "クレジット＝**後払い**、デビット＝**即時払い**、チャージ型プリペイド＝**前払い**。",
  "hints": [
    {
      "title": "比較の軸",
      "text": "買い物の前・その場・後のうち、いつ利用者のお金が動くかを考えよう。",
      "revealsAnswer": false
    },
    {
      "title": "仕組みを分ける",
      "text": "カード会社による立替と、銀行口座からの直接引落しの違いを整理しよう。",
      "revealsAnswer": false
    }
  ]
}
~~~

※ `choiceReasons` は仕組みを示す**抜粋例（2肢）**。実際の登録では問題の全選択肢に1件ずつ理由を付け、公式正答ID・説明を照合する。

### 数式・手順がある問題の例

~~~text
summary:
  この問題は、割合を算出する際の**分母に何を使うか**を判断する。
explanation:
  まず必要な値を抽出する。次に**対象の合計値を分母**に置く。
  例えば対象40件／全体200件なら、40÷200×100＝20％。
  **「全体」と「対象」を逆にしない**ことが重要。
takeaway:
  割合（％）＝**対象÷全体×100**。計算後に単位を確認する。
~~~

数学・IT・会計・法律・医療や語学など、試験ごとに別の強調方法を採用しない。数式そのものの表記・実装は既存の問題形式契約を優先する。

## 4. 文章の品質基準

1. **問題固有性：** その設問が何を区別させたいかを説明する。汎用の分野紹介だけにしない。
2. **判断可能性：** 選択肢のどの語句・条件が正誤を決めたか、数字の根拠や例外を省略せずに書く。
3. **誤りを教えない：** 正答や原本の条件を変えない。計算問題は途中式と単位を独立検算する。
4. **出題時点を厳守：** 税・年金・法改正・製品仕様などは原本の法令基準日／公表時点と現行制度を混同しない。現行制度との差は必要なら明示する。
5. **簡潔な視覚階層：** summaryは問題の論点、explanationは思考の道筋、takeawayは一行で持ち帰る規則。太字以外の強い装飾に頼らない。
6. **学習者への配慮：** 略語は初出で補足し、制度名・数値を似たものと比較して説明する。断定できない条件は断定せず、根拠を示す。
7. **レビュー：** 出典・法令・公式解答・全肢の理由・計算式・強調の適切性を別担当が確認する。太字を付けただけで `reviewed` と扱わない。

## 5. 過去の教材への適用手順（別PR）

**既存80問をこの仕様PRで直接書き換えない。** 実装・作問・確認担当に引き渡す作業は次の順とする。

1. **共通の表示処理**を実装し、安全な太字変換・既存の無装飾テキスト・診断や模試の解答非表示をテストする。
2. **FP2級過去問の作問Draft PR #38** にある2025年1月の学科60問、2024年9月の学科20問を、`summary` → `explanation` → `takeaway` → 必要な `choiceReasons` の順に丁寧に強調する。機械的に数字や用語を一括囲いしない。
3. 原文・正答・選択肢ID・根拠URL・法令基準日を変えずに、**装飾を取り除いた文章が元と一致**することを照合する。装飾が既存の原本テキストや式の構造を壊していないかも確認する。
4. 既存のAP・AB-730・その他公開教材は、同一の表示仕様を利用しつつ、公開済みのレビュー済み教材として既存の版・ハッシュ・独立レビュー・生成フローに従って順次対応する。
5. `enrichment:draft`、`legalReview.status:unverified` は第三者の実検証が終わるまで保持する。作問者自身の確認で承認済みにしない。

## 6. 作問・レビュー担当のチェックリスト

- [ ] `summary` は「この問題で問う判断・知識」を具体的に示しているか。
- [ ] `explanation` に結論だけでなく**根拠、途中式、例外**があるか。
- [ ] `takeaway` は類題で再利用でき、summaryの単なるコピーではないか。
- [ ] すべての `choiceReasons` に各肢固有の正誤理由があるか。
- [ ] `**…**` は正誤の分岐点に絞られているか。閉じ忘れ、HTML混入、強調過多がないか。
- [ ] ヒントは段階的で、強調を含めて答え漏えいがないか。
- [ ] 出題基準日、原本との一致、法令・計算の出典、独立レビュー／版管理が適切か。
