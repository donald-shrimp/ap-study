P0・P1を実装 2026-10-07（日本時間）。開始一本化・受験日・フェーズ計画・AI入出力・診断を追加。週別目標と手動予定、計画の前提の保存・AI出力、診断専用教材の追加基盤も実装。公開派生問題は0問です。最新版Rulesは2026-10-07に利用者が公開を報告済みです。前提の本番同期は確認待ちです。 同期で届いた計画が画面に反映されない問題を修正しました。未保存の入力がなければ自動表示し、編集中は内容を保護します。

01 / 開始ボタン

始める前に、問題数を選ばなくていい。

当初の1／3／5問の選択は、開始時に区切りの目安を変えるだけでした。通常学習の入口は、「とりあえずはじめる」ひとつにしました。

開始

押すと1問目を表示。設定や確認画面を挟みません。復習日が来た問題・未着手など、現在の出題優先順位を保ちます。

回答後

「次の問題」と「今日はここまで」。自動で次に進めず、いつでも終えられます。回答途中は「中断」で保存します。

自由に続けることと、終えやすいことを両立。

「今回4問」は表示できますが、「あと1問」「目標未達」は通常学習には出しません。回答後の終了ボタンは、次へ進むボタンと一緒に残します。

分野別演習も、分野を選んだら「この分野をはじめる」に統一します。分野内を一巡した後も、その分野で解き直せる現在の挙動を保ちます。

以前の1／3／5問では何が違った？
  • session.goal と次回用の目安を保存する。
  • 上部の「今回○問・目安○問」が変わる。
  • 目安に到達すると「○問の目安完了」を表示する。

出題順は基本的に同じです。目安を超えても「次の問題」は押せます。上部が「中断」から「ホーム」になるのは、問数ではなく回答確定の前か後かで決まります。

確認箇所：src/ui/views.js の studyHTML（目安完了表示は廃止）、src/app.js の start-session・pickQuestion。

一本化するときに整理するデータ

通常学習の session.goal と settings.sessionSize、目安完了表示を廃止します。まとまりとしての attemptIds と分野指定は、今回の取り組み数や同じ問題の連続出題を避けるために残します。

診断の固定問題数や計画の目標回数は、通常セッションとは別に保存します。既存の履歴・ヒント・学習中の問題は保持します。

02 / ホーム

開始ボタンが、いつも最優先。

診断と計画を大きなカードで並べると、始める前に読む量が増えます。現在のホームを土台に、下側にコンパクトな入口をひとつ追加します。

  • 中断中：「続きから」を最上部に表示。新しい問題もすぐ始められます。
  • 未登録：下側に「受験日・計画を登録」「30問で実力診断」の入口。設定や診断を先に行う必要はありません。
  • 登録済み：同じ位置を、試験までの日数と現在のフェーズ・実績に置き換えます。
  • 診断済み：大きな案内を繰り返さず、結果・再診断は詳細画面に置きます。

初回ウィザードなし。登録・診断・ログインは任意。

計画の読み込みや通信の完了も、開始ボタンの待ち時間にしません。ホームに週別グラフやフェーズ一覧を展開しません。

ホームで増やさないもの

新しい上部ナビを一度に増やさず、計画の詳細画面から診断・AI入出力へ進める形にします。達成の詳細や履歴は現在の入口を使います。

「今日のおすすめ」は後の段階で、理由が分かる任意の入口として追加します。計画の都合で通常の開始ボタンの出題を勝手に変更しません。

03 / 実力診断

手助けなしで、確認が必要な分野を探す。

標準診断は30問です。診断では、今どこまで自分で解けるかを確認します。問題表示・採点・保存の部品は共有し、学習を助けるUIは表示しません。

通常学習

問題数は決めず、1問ずつ続ける。ヒント・解答閲覧・解説を使って学び、いつでも終えられます。

診断

開始時に30問の一覧を確定。ヒント・解答閲覧ボタンを表示せず、正誤・正解・解説は終了後にまとめて確認します。

出題と結果のルール

  • 複数分野から30問を抽出する。配分は資格定義に置き、通常の復習優先の出題処理と分ける。
  • 未着手を優先する。既出が含まれたら、その件数を表示する。別年度の類似問題まで初見とは断定しない。
  • ヒント・解答閲覧・正解の強調・要点・関連解説は、診断中に表示しない。途中の正答率も出さない。
  • 回答は未採点で保存し、診断終了時にまとめて採点する。画面で隠すだけでなく、診断用の操作処理・保存検証でも回答前の支援利用を認めない。
  • 「中断」は再開用に保存し、結果を表示しない。「ここまでで診断終了」を選べば部分結果を見られるが、その診断は終了し、答えを見てから続行できない。
  • 未回答は不正解にしない。オフラインで問題が足りない場合、出題範囲を黙って変更しない。

30問中27問回答：正解18、不正解9、未回答3。

データベース：5問回答中2問正解。「次に重点確認する候補」として示します。分野別の件数を添え、未出題は「未確認」。少数の回答だけで分野全体の習熟や合格可能性は断定しません。

診断結果と、普段の復習をどう共存させる？

診断終了時の不正解は、通常の復習候補にも入れます。終了後に「この分野を学習」「間違えた問題を解き直す」へ進めば、通常学習のヒント・解説を使えます。学習は別の試行に記録し、過去の診断結果は変えません。

診断記録には、ID、対象パート、出題方針の版、支援なし・終了後採点の方針、確定した問題一覧・版、各枠の試行ID・回答確定状態、中断／完了／途中終了、開始・終了日時を保存します。別端末での継続が分かれたときも、同じ出題枠を二重に数えない設計が必要です。

診断の結果は正解・不正解・未回答で示し、ヒント付き正解・解答閲覧の欄は設けません。正答率は回答確定した件数を分母とし、回答数／出題数を併記します。未回答は分母に含めず、別に件数を表示します。途中終了の結果には「部分結果」と表示します。

診断専用の派生問題を、少しずつ追加する

2026-10-07に追加基盤を実装しました。公開の派生問題は0問で、現在の診断は既存過去問のみです。別問題集の読み込み・分野別優先・通常学習からの分離は、公開しない検証用教材で確認済みです。

普段の問題には混ぜません。

数値や問い方を変えた独自問題は、診断専用の問題集として別に管理します。作成・検算・確認を済ませたものだけ、段階的に追加します。

  1. 最初：既存問題のみ。現在の30問診断を使い、分野内で未着手を優先します。
  2. 追加し始め：派生問題を優先し、既存問題で補う。各分野の出題枠を保ち、派生問題がない分野も確認します。
  3. 充実後：派生問題の割合をさらに増やす。合計件数だけで切り替えず、分野ごとの確認済み問題数と、同じ元問題に偏らないかを見て配分を決めます。
出題・記録で守ること
  • 通常学習・検索・通常の復習候補に、診断専用の派生問題を入れません。派生問題の誤答は診断結果から振り返り、普段の学習には対応する元問題や分野への入口を用意します。
  • 同じ元問題とその派生問題、同じ元問題から作った別派生を、同じ診断内に重ねて出しません。足りない場合の既存問題への補完や開始可否は、出題方針で明示します。
  • 派生問題ごとに独立ID・教材の版・元問題ID・分野・パート・確認記録を持たせます。元問題を見た経験と、その派生問題を解いた経験を分けて記録します。アプリ外での既視経験までは判定しません。
  • 開始時の問題と版を固定し、教材を追加しても中断中の診断は変えません。診断だけの取り組みと通常学習の集計を区別します。
  • 結果とAI向けExportには、既存／派生の出題数・回答数・正解数、既出件数、出題方針の版を添えます。異なる構成の診断を同じ難易度とは扱いません。
  • 数字を変える場合は式・条件・丸め・図・正解の一意性・各誤答理由を確認します。選択肢の並べ替えだけで、理解を測れたとはしません。診断開始時の未確認な自動生成は行いません。

追加初期の上限は各分野1問です。分野ごとの教材がそろったら資格定義で上限を増やし、方針の版も上げます。未着手の派生→未着手の既存→既出の派生→既出の既存の順です。派生問題への回答は診断結果に分け、通常履歴・計画実績には混ぜません。作成・独立確認・教材追加の手順。「合計何問なら十分」という閾値や、一定割合を現時点で固定しません。

04 / 受験日・学習計画

日々のノルマではなく、期間の目安を持つ。

計画は「フェーズ＋目標」が基本です。1日休んでも、その日の未達を翌日に積み上げる仕組みにはしません。診断を受けずに計画を登録しても構いません。

まず表示する

現在のフェーズ、期間、目標回数、実績、残り回数、重点分野。

任意で追加できる

明示的な週別目標、外部模試・教科書の読了など、手動で完了にするマイルストーン。

「300問」の意味を先に決める

初期版の目標は、解き直しを含む「取り組み300回」にしました。既存の完了4状態を数える場合、解答閲覧も含むと明記し、内訳を見られるようにします。「異なる問題300問」は別の指標です。

重点分野はおすすめの対象であり、実績の集計条件とは分けます。初期版では、対象パート内の取り組みを数え、重点分野以外を解いても実績になります。

計画の目標は、開始前に選ぶ問題数ではありません。

「今の期間で120回」を目指していても、今日は1問だけで終了できます。計画達成のために学習セッションを強制継続させません。

受験日・科目・複数資格

試験パートのIDと表示名は資格定義の examParts に置きます。問題にも examPartId を付けます。年度・春秋の教材パックとは別概念です。

受験日は利用者がパートごとに登録。同日でも別日でも扱えます。教材を提供していないパートは、初期版では日付・手動予定を管理し、アプリ内診断の対象にはしません。

APの制度や日付を共通コードに固定しません。残日数は計画のタイムゾーンの暦日で計算します。過去の日付の計画も履歴として読めます。

週別目標と、実績の数え方

「12日間で300回」だけでは「今週120回」は決まりません。フェーズ内に1〜7日の週別目標を明示的に登録できます。未達を次週へ足さず、ホームの「今週」は今日を含む登録済み期間です。日数で配分するなら「按分した目安」と表示します。

開始・終了日は両端を含み、初期版はフェーズの重複を認めません。実績は完了日時・対象パート・タイムゾーンから集計します。進捗カウンター自体は保存・同期せず、履歴から再計算します。計画の編集で履歴をリセットしません。

別パートの重複フェーズや複数の有効計画は初期版の範囲外にし、同時に数えるルールが必要になってから追加します。

05 / AI入出力

AIとの往復は、公開JSONで。

AI APIへの直接接続は後回しにします。公開フォーマットとJSON Schema、例、プロンプトを用意し、ChatGPT・Claude・Geminiなどから同じ形で取り込めるようにします。

公開形式の仕様 · Schema · 登録できるサンプル

ひと問の状況をコピー → AIへ相談 → 計画JSONを貼る → 検証 → プレビュー → 登録

  • プロンプトに、その資格で有効なパートID・分野ID・対応版を含める。
  • JSON Schemaで型・必須項目・長さ・件数を検証する。
  • 別途、参照ID、実在する日付、期間の逆転・重複、ID重複を検証する。
  • 未知の版・項目は黙って捨てない。エラーは場所と直し方を表示する。
  • 登録前に、変更する受験日・フェーズ・目標を人間向けに見せる。

検証に失敗しても、現在の計画と学習記録は変更しません。

計画importは、既存の学習記録バックアップの読み込みとは別の入口にします。

提案する StudyPlan JSON を見る

公開v1の最小例です。日付は説明用の仮値。目標は取り組み回数。週別目標・予定・計画の前提は任意項目で、形は公開Schemaに定義しています。

{
  "format": "hitomon-study-plan",
  "version": 1,
  "qualificationId": "ap",
  "timeZone": "Asia/Tokyo",
  "examDates": [
    { "examPartId": "objective", "date": "2026-11-04" }
  ],
  "phases": [
    {
      "id": "foundation",
      "name": "基礎確認",
      "start": "2026-10-07",
      "end": "2026-10-18",
      "examPartIds": ["objective"],
      "targets": { "completedAttempts": 300 },
      "focusTopicIds": ["security", "network", "database"]
    }
  ]
}

公開用JSONにUID・端末ID・同期の版番号・計算済み実績は入れません。公開形式の version と、内部の更新競合に使う revision は別です。

v1のフェーズに任意のweeklyTargetsとmilestonesを追加しました。既存項目の意味は変えず、Schema・サンプル・対応機能を明示しています。AIに未対応項目や完了の推測を作らせません。

AIへ渡す学習状況と、エラー表示の例

学習状況は別の hitomon-study-summary 形式で出します。資格、集計日時・タイムゾーン、受験日と残日数、累計・直近7日／28日の取り組み回数、異なる問題数、結果の内訳、分野別の母数・自力正解数、復習候補数、現在の計画と実績を含めます。

診断結果は診断日時・回答数／出題数・未回答数・分野別件数・「支援なし」の方針とともに分離します。通常履歴の正答率は「解き直し・支援利用を含む学習履歴」であることを明示し、自力正解などの内訳を付けます。学習と診断の集計定義をそれぞれ画面とExportで共有します。アカウントのメール・UID・問題本文・教科書メモは、相談用Exportに自動で入れません。前提に記入した文章は含めます。

フェーズ2の終了日が開始日より前です。

phases[1].end を、開始日以降の日付に変更してください。

学習済み範囲・使用教材・使える時間・休む予定・計画を立てた理由を、任意の「計画の前提」として保存・Exportできます。AI相談の欄で渡す内容と全JSONを確認できます。前提に記入した文章は出力に含まれますが、アプリがAIへ自動送信することはありません。計画JSONに前提がなければ現在の前提を引き継ぎ、空のcontext:{}なら明示的に消す内容をプレビューします。

計画の調整は、まず外部AIへの相談と利用者による採用で行います。アプリ内の自動調整提案は保留。診断と状況のExportを先に整え、母数の少ない48%だけでDBを苦手と決めません。

既存コードで先に整えるべきところ
  • 共通集計：通常演習では attempt.topicId が空になる場合があります。分野集計には記録時点の questionSnapshot.topicId を使います。
  • 問題の所属：資格定義だけでなく、教材・軽量インデックス・試行スナップショットへパートIDを通します。
  • 通常セッション：目安を廃止するため、保存検証とバックアップの形も見直します。診断を既存の最大5問の制約へ押し込みません。
  • 同期：試行とは別に計画・診断の送信待ち・カーソル・版番号比較・Firestore Rulesを追加しました。前回Rulesは利用者が公開済み。週別目標・予定の追加時は変更不要でしたが、今回の計画の前提に対応した最新版Rulesも2026-10-07に利用者が公開を報告済みです。
  • 競合：計画は版番号で検出し、クラウドと端末の案を選べるようにします。試行用の別記録作成を流用すると、有効計画が二つになるため避けます。

既存の学習記録は保持します。後方互換・大規模な移行機構は目的にせず、今回の変更に必要な保存処理だけ整えます。

確認箇所：試行、端末保存、保存検証、同期、Rules、資格定義。

どのレイヤーを変える？
  • 資格定義・教材生成：試験パート、所属、診断配分。共通コードにAPの条件を書かない。
  • 共通ドメイン：集計、計画検証、実績計算、診断の出題・結果。画面や通信なしで計算できる形。
  • 保存・同期：新しい保存先、送信待ち、更新競合、所有者検証、Rules。
  • 共通UI：一本化した開始、下側の入口、診断・計画詳細、importプレビュー。
  • アプリ制御：操作を各機能につなぐ。計画や集計を src/app.js に詰め込まない。

全部を一度に実装しません。P0も、下の順に実装・確認しています。開始一本化・受験日・フェーズ計画・AI入出力・30問診断は実装しました。週別目標と手動予定、計画の前提の保存・Export、診断専用教材の追加基盤も実装しました。P2は保留です。

80問チェック・自動調整提案・計画履歴

必要性を利用状況から判断し、個別に追加します。アプリ内の自動調整提案は必須にせず、まず外部AIへ相談できる材料を整えます。AI APIやMCPの直接接続も必須範囲にしません。

最新版Rulesは、公開の報告を受けています。

前回は利用者がルール公開・同期済み表示を確認済み。週別目標・予定の追加時は変更不要でしたが、今回の計画の前提と診断の出題情報に対応した最新版Rulesも、2026-10-07に利用者が公開を報告済みです。端末内保存・バックアップは使え、通常の演習同期も保持します。同期とインデックス除外の確認手順。前回の本人による同期済み確認とは別に、今回の前提の本番同期は未確認です。本番の別端末復元も別途確認します。

診断より先に計画を使える理由

既にある学習履歴からAIへ相談できます。診断の新しい出題・再開・同期を完成させるまで、受験日と計画を待たせる必要はありません。

各段階で確認すること
  • 未登録・未診断・未ログインでも、開始は1操作。
  • 計画の読込失敗やオフラインが通常学習を止めない。
  • 通常学習は回答後に終了でき、途中の選択・ヒントも再開できる。
  • 既存800問の教材、回答表示、PWAのID・スコープ・オフライン動作を保つ。
  • 不正な計画importで既存計画・履歴が変わらない。
  • 別資格・別利用者のデータを混ぜない。端末間の計画競合を黙って上書きしない。
  • 診断中はヒント・答え・途中の正誤を表示せず、支援付き試行を診断結果として受け付けない。
  • 診断の中断で結果を見せず、結果閲覧後に同じ診断を続行させない。
  • 診断の問題一覧を途中で変更せず、未回答や継続記録を誤集計しない。
  • 小さい画面・大きな文字でも開始が探しやすく、結果の母数が読める。
  • 画面、StudyPlanの実績、AI用Summaryで同じ集計定義を使う。
