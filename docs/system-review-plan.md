## 目的と進め方

学習の使いやすさ、記録の安全性、変更のしやすさを点検し、根拠のある問題をGitHub Issueにして小さなPRで解決する。既存の教材作成Draft PR #37 / #48 / #49 / #50は別担当の作業として保持する。既存Issue #34はFP追加の経緯として参照し、今回の不具合Issueと重複させない。

1. 対象の仕様・実装・テスト・実画面を読む。
2. 問題候補を合成データで再現する。実機や本番権限が必要な確認は未確認として残す。
3. 影響、再現条件、根拠、対応方針、完了条件をIssueに記す。
4. データ保全に関わる問題から、1つの原因・目的ごとにPRを作る。
5. 必要な回帰検証、最新refとの整合、非force反映、公開確認を終えてIssueを閉じる。

確認済みは「記載した範囲を確認した」という意味であり、その領域の不具合がゼロという宣言ではない。実施コマンド・対象・結果は [点検記録](system-review-findings.md) に残す。

## 優先度とIssueの単位

- P0：記録消失、重大な誤採点、主要な学習が不能。優先して封じ込め・修正する。
- P1：記録の復旧・同期・学習を繰り返し妨げる問題。次の小PRの候補。
- P2：性能、操作、テスト不足、実際の変更を難しくする構造。依存関係を整理して順番に直す。
- P3：低頻度の不便や文書整理。通常の改修と合わせる。

Issueに必須：基準commit、確認した事実、利用者への影響、再現方法または測定、コードの根拠、完了条件、関係Issue。仮説は確認済みの不具合と区別する。項目の数を埋めるためのIssueや、具体的な効果のない分割・置き換えは作らない。

## 保持するもの

- 公開教材・正答・図・レビュー根拠・安定IDと版。教材自体を変える必要がある場合は教材レビュー手順を適用する。
- AP A/Bで異なる記録・中断・復習・集計、資格単位の共通計画。問題数と大問数を混ぜない。
- 自動判定と自己評価、通常演習と診断・模試の区別。
- 端末・アカウント・資格の保存境界。個人記録や認証情報を公開リポジトリに置かない。
- 最上段からすぐ始められる導線と、科目Aを基準とする共通デザイン。

後方互換のために旧形式をアプリへ戻す必要はない。既存v2記録は保存したまま改善する。本番の本人別端末照合は未確認であり、合成データのテストを本人記録の照合として扱わない。
