# 科目Bの小問解説と答え合わせの作成基準

初学者が答え合わせの画面だけで、**正答の中身と、本文のどこからその答えを導けるか**を理解し、次の問題でも自分で考えられるようにする。この基準は科目Bの小問・回答欄に適用する。大問全体の読み物は [大問解説の作成手順](../work/ap/case-explanations/README.md) に従う。

## 毎回参照する手本

ユーザーがローカル画面を確認した2022年春期・問11（`ap-r04h-pm11`）と2023年春期・問1（`ap-r05h-pm1`）を手本にする。着手時とレビュー時に、[改稿データ](../content/ap/written-feedback.json) の次の欄を原文で読み、[承認記録](../content/ap/written-feedback-reviews.json) と照合する。途中の回にできた文章を手本に昇格させる場合はユーザーの判断を受ける。

| 手本 | 何を手本にするか |
| --- | --- |
| 2022年春期・問11 設問4 e・f（`q4--ef`） | 出荷指図と出荷実績を語句で表示する。10個の指示と8個の実績の例で、バッチが正常に動いても売上が実績とずれる理由を説明する。確認ポイントは省く |
| 同 設問2（`q2--answer`）と設問3（`q3--cd`） | 記述では答案に担当者と権限の関係があるかで自己評価できる。照合の設問は、記録が何を元に作られたかを矢印で書き出す手順を任意の確認ポイントとして残す |
| 2023年春期・問1 設問4(1)（`s4-1--answer`） | 図中の記号アを「検知／通報（受付）」に結び付け、元の図を結果から確認できる。本文の連絡の遅れと、従業員が担う作業をつなげて説明する |

手本から引き継ぐのは、正答の見せ方と、初学者が根拠を追える説明の深さです。題材に応じて順序と分量を決めます。例えば出荷の設問では「カ・キの両方が必要」と書くだけでは元の選択肢を探し直すことになります。正答欄に二つのデータ名を出し、解説で日次バッチがどちらのデータを読み、両者がずれると売上にどう表れるかを説明します。この説明を読めば判断をたどれるので、確認ポイントは省きます。

## 読者に届けるもの

| 要素 | 作成基準 |
| --- | --- |
| 正答・公式解答例 | 選択肢の語句を主に、記号や項番を補助にする。構造化された選択肢は既存データを使う。図表の記号・項番は原本から対応を確認し、必要な欄に表示語句を登録する。順不同の組は組で示す。数値は根拠と必要な単位を確認する |
| 解説 `explanation` | 原問の決め手を拾い、その条件から正答に至る道筋を書く。用語は使う箇所で意味を説明する。計算は何を求める式かと途中の単位を示す。比較が必要なら、迷いやすい候補のどの条件が違うかを書く |
| 自己評価の基準 `rubric` | 自分の答案に主語・対象・条件・理由のどれが必要か、合っていると判断できる形で示す。別表現でも意味が同じか確かめられる基準にする。登録外の短答や旧版など、自己評価に進み得る欄にも用意する。自動判定した場合は画面で省く |
| 確認ポイント `reviewPoint` | 類題に使える具体的な操作を追加できるときだけ書く。何を先に見るか、何をそろえどう比べるかを読者が実行できるようにする。解説の再掲・言い換え、一般的な心得、字数や採点の定型説明で欄を埋めない |

- 日常の言葉と原問の用語をつなぎ、「です・ます」調で書く。理解の助けになる場合に具体例・途中式を使う。原問の判断に必要な範囲で説明し、専門的な周辺知識、内部作業向けの注意や予防線、採点基準に関する定型文は加えない。固定の段落数・文字数・見出しを設けない。
- 正答記号の列挙で説明を終えない。判断を左右する違いが一つなら、そこを詳しく書けば十分。表にまとめる場合も、どの列・条件を比較すれば答えが出るかを本文で示す。
- 記述では、判断の過程から何を答案に残せばよいかを示す。字数・単位・指定語句は原本で確認し、答案を組み立てるうえで役立つ箇所にだけ書く。採点用の文字列や選択肢IDには手を加えない。
- 既存の説明がこの基準を満たす場合は、その根拠と点検した欄を記録して採用できる。満たさない場合は原問から組み立て直す。

## 手本との比較で見ること

レビュワーは全欄を読み、次の観点で手本から外れた箇所を具体的に指摘します。点数や文字数での一律判定は設けません。

- **初学者が理由をたどれるか。** 正答に使う本文・図表の条件が分かり、必要な用語や仕組みを押さえて、照合・計算・答案につなげられるか。結論の一文に飛んでいたら、不足する条件や途中の判断を指摘する。
- **説明が原問の理解に収まっているか。** 専門用語・例・補足ごとに、それがなければ読者がどの判断で迷うかを考える。判断に寄与しない補足は省き、必要な用語は問題中で何を指すか説明する。
- **答え合わせだけで用が足りるか。** 正答記号を問題文で引き直さずに中身が分かり、自己評価の基準を自分の答案に当てはめられるか。確認ポイントは次の問題で実行できる手順を加える場合に残す。解説の言い換えと採点に関する定型の但し書きは省く。

判定の根拠は、既存のレビュー記録に該当欄と修正点、または手本に照らして妥当と判断した代表箇所を記します。前回の改稿を基準に昇格させず、同じずれが複数の欄に出たら、その組の全欄を手本と照らし直します。

## 作業と判定の記録

1. 作業の事実は [進捗台帳](../work/ap/written-feedback/progress.json)、内容承認は [承認記録](../content/ap/written-feedback-reviews.json) で確認する。残数は台帳の `targetCount` と実際に完了した題から求める。台帳と実ファイルが食い違う場合は実ファイル・ハッシュ・生成物を照合して解消する。チャットの長い経緯や前回の要約だけで作業状態を決めない。文脈が要約・圧縮された後も、この基準・手本・進捗・対象原本を読み直す。
2. 1回に最大2大問を扱う。前回の作業が途中なら同じ組の続きを優先し、別の組への着手を重ねない。台帳の `activeBatch` に今回の対象、着手時点のハッシュ、途中の段階、保存済みの下書き、残る確認を記録する。他担当の編集中・予約中の題を飛ばした場合は理由と次に確認する条件を残す。
3. 作者が原問・全図表・公式解答・採点講評を照合する。別のレビュワーエージェントには、選べる場合は履歴を引き継がない文脈を使い、最初に原本とこの基準を渡す。レビュワーの独立解答を得てから作者の原稿を共有する。レビュワーは全欄の根拠・表示・計算・単位・字数に加え、初学者が小問の画面で考え方を追えるか、説明が試行2題より専門に寄りすぎていないか、自己評価と確認ポイントにそれぞれ用途があるかを確認する。修正後の最終版を再確認し、承認した版のハッシュを受け取る。
4. 改稿には `content/ap/written-feedback.json` の表示用改訂を使う。使用する各教材版のハッシュと全欄の対応を照合し、正規化した各大問エントリーの SHA-256 を独立レビューの承認に結び付ける。正規化は `tools/written_content.py` の `canonical` に従う。機械チェックは重複・欠落・ハッシュを検出し、説明の妥当性はレビューで判断する。途中の草稿はこの作業フォルダーの `drafts/` に別ファイルとして置く。
5. 承認済みの改訂を既存の教材生成でローカル版へ反映する。新しく改稿した各大問を開き、代表欄で正答内容・解説・実際の判定に応じた基準を確認し、改訂した全欄の対応を検査する。選択・自己評価・図表参照のうち、その回で変えた種類をブラウザで試す。共通の開示・保存・旧版の互換性は既存の回帰テストで検証する。保存した原稿、原問、採点、学習記録、大問全体解説、他担当の変更は保全する。
6. 結果を台帳に記録する。表示まで終えた改稿は `reviewed_local`、原本から全欄を点検し現行で利用できるとした題は `accepted_as_is` とする。完了の裏付けには対象版、版のハッシュ、レビュワー、検査・表示結果を残す。途中の題は `activeBatch` に残し、次回に何を確認すればよいかまで記す。作業者の解釈や一時的な問題はここに記録し、ユーザー承認済みの基準を書き替える理由にしない。

## 調査から取り入れた点

- 長い入力で重要情報の位置によって精度が変わる実験を踏まえ、目的・禁止事項にあたる範囲・固定の手本を各回の入力の先頭に置く。本作業での効果は、試行との差とレビュー結果から確かめる。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)
- リポジトリに短い入口と必要な情報を置くOpenAIの実践、長期作業で進捗の記録を別に持つAnthropicの実践を参考に、作成基準・進捗・承認の記録を分ける。[OpenAIの実践](https://openai.com/index/harness-engineering/) · [Anthropicのコンテキスト管理](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
- 少量ずつ進め、実際の画面を開いてから完了とする方法を、毎回最大2大問の独立レビューとローカル検証に適用する。[Anthropicの長期タスク検証](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- 生成する担当と評価する担当を分け、評価は固定の実例でそろえる。評価の文言でも結果が偏るという報告を踏まえ、ひと問では抽象的な品質評価や点数より、該当欄と読者がたどれない判断を記録する。[Anthropicの長期タスクの設計と評価](https://www.anthropic.com/research/harness-design-long-running-apps)
