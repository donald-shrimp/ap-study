# 応用情報・科目B：大問全体の解説と振り返りの改善案

2026-11-08。検討案。アプリ・公開教材は未変更。

対象読者は初学者。略語・仕組み・計算方法を知っていると仮定せず、必要な知識を本文の具体例と一緒に説明する。単語の一覧や正答の言い換えで終わらせない。

試行教材：[2025年春の全11題・大問全体の解説草案](../work/ap/case-explanations/pilot-2025-spring/README.md)。3題ずつ試作し、最後にソフトウェア開発とサービスマネジメントを追加して、同試験回の全大問へ広げた。アプリ本体への組込み・公開は別の段階。

## 推奨する変更

**大問を学習のまとまりとして扱い、最後に「この問題は何を問うていて、どう読んで、どの知識を使えば解けたか」を振り返る画面を置く。**

小問の答え合わせを終えるだけでは、個々の正答は分かっても、次の初見問題で同じ考え方を使えるとは限らない。大問全体の見取り図と、その事例を解きほぐす手順を教材として追加する。画面の導線と解説の内容を一緒に改善する。

まず2025年春のセキュリティ・データベース・プロジェクトマネジメントの3題で試す。全88題への追加は、この3題の説明と読後の分かりやすさを確認してから進める。

## 2. 学習後に分かるようにしたいこと

1. この事例の登場人物・システム・課題は何だったか。
2. 各設問は、その課題のどこを確かめていたか。
3. 本文のどの条件が決め手になり、それをどう解釈したか。
4. 事前に知る必要のある知識と、本文から読み取れる情報は何か。
5. その情報を、理由・対策・計算結果など、求められた答えへどう加工するか。
6. 次の類題でも使える考え方は何か。

「サイバー攻撃への対策を問う問題です」のような題名の言い換えや、全小問の正答を並べた一覧だけでは、この目的を満たさない。

## 3. 大問全体の解説に入れる内容

以下は編集時の確認観点。六つの長いカードを全題へ機械的に作る指定ではない。論点が重なる場合はまとめ、問題の性質に合わせて説明する。

| 内容 | 書くこと | 避けること |
| --- | --- | --- |
| この問題の見取り図 | 事例の目的・問題点・問われる判断を短く説明する。必要なら構成図や時系列を使う | 本文全体の再掲、題名だけの言い換え |
| 解き方の流れ | 読む対象→着目条件→判断→答案の順に、実際の本文・表・図を使って説明する | 「丁寧に読む」「重要語を探す」で終わる一般論 |
| 設問どうしの関係 | 設問ごとの役割や、共通する条件・異なる条件を示す | 独立した設問を無理に一本の因果関係にする |
| 必要な知識 | 用語の意味、その知識を使う箇所、適用できる条件や限界を説明する | 略語や単語の一覧だけ、関係のない教科書の章を丸ごと追加 |
| 答案の組み立て方 | 本文の事実をどう理由・対策・効果に変換し、指定語や字数へ収めるかを例示する | 公式例の丸暗記、非公表の採点基準や部分点の創作 |
| 次にも使う考え方 | 類題で再利用できる判断と注意点を少数に絞る | 解説の繰り返し、全題共通の標語 |

説明の中心は、**本文の事実 → 知識を使った解釈 → 答案に必要な要素**という橋渡し。本文参照は、小問や該当箇所へ戻る操作と結び付ける。

小問の解説は引き続き、各欄の正答に至る固有の根拠を担当する。大問解説では、複数の欄で共通して使った考え方や事例全体の構造を扱う。ただし、欄の解説に欠けている途中計算や定義を、大問解説だけで補って済ませない。

## 4. 画面と導線

通常の学習では次の流れを基本とする。

```text
問題文・小問を解く
  → 各欄の答え合わせ・必要な自己評価
  → 大問全体の振り返り
  → 次の大問／今日はここまで
```

大問の完了時には、現在の小問から振り返り画面へ移り、見出しへフォーカスする。最後に押すボタンの行き先が変わる場合は「大問の振り返りへ」と表示し、別画面へ進むことを分かるようにする。自己評価の完了で大問が完了する場合も、保存成功後に同じ画面へ進む。

振り返り画面の先頭では、「この問題で考えたこと」と「解き方の流れ」を開いて示す。詳しい知識や答案比較は、その後に必要に応じて開く。小問一覧には本人の回答・自動判定／自己評価を示し、各小問の既存解説へ戻れるようにする。

全体の説明を最後の小問の下へ追加すると、長い小問解説に埋もれやすい。独立した表示にして、スマホでも問題文との切替に邪魔されず読めるようにする。本文参照から戻った場合は、振り返りの元の位置へ戻す。

「今日はここまで」は左、「次の大問」は右。次題の分野・試験回・番号順は従来の範囲を引き継ぐ。読了チェックや待ち時間は設けず、その場で次へ進める。振り返り画面を開いただけで理解済みとは記録しない。

### 開示と未完了の扱い

| 状態 | 推奨動作 |
| --- | --- |
| 未確定の欄が残る | 大問解説はまだ出さない。小問ごとの既存の開示条件を維持する |
| 全欄が確定し、自己評価が残る | 「大問全体の解説を見る」から開ける。評価待ちの欄に戻れるようにし、大問を完了扱いにしない |
| 全欄の回答・評価が完了 | 振り返りを標準の終了画面とし、ここに終了・次題への操作を置く |
| 「最後にまとめて」で学習 | 全欄確定前は大問解説も出さない。折りたたみ本文・AI質問にも答えを先出ししない |
| 一部だけ解いて終了 | 最初の実装では大問解説を出さない。全体を確認したい場合は残りを「分からない」で確定できる。未回答を無言で不正解にしない |
| 振り返りから小問へ戻る | 確定した回答・評価を保持し、「大問の振り返りに戻る」を置く |
| 振り返りで中断・再読み込み | 同じ取り組み・表示位置から再開する。完了済みでも記録一覧から再閲覧できる |
| 全体解説の未提供題 | 空の振り返り画面や共通の定型文で埋めない。既存の終了導線を使う |

全欄確定後の開示なので、大問解説を読んでも同じ取り組みに未確定回答は残らない。将来、未回答のまま全体解説を開けるようにする場合は、後続回答の支援閲覧の記録も別途設計する。

## 5. 実際の大問を使った解説の草案

対象：2025年春期 問1「サイバー攻撃への対策」／`ap-r07h-pm1`。

以下は現行本文・欄別解説を基にした、内容の方向性を示す草案。公開教材としての追加や、原本・全図表に対する独立レビューは未実施。

### この問題で考えたこと

この問題では、提携先からの侵入が自社のサーバ被害へ広がった事例を読み、侵入の仕組み、認証対策の限界、復旧と調査を可能にする条件を考えます。「対策を導入しているか」だけでなく、**その対策が今回の攻撃や保存条件に対して働くか**を確かめる問題です。

### どう読めばよかったか

まず、関係する機器と攻撃の順序を分けます。提携先P社側のVPN・PC-Pから、C社内のPC-R、PC-S、各サーバへと被害が広がっています。PC-PからPC-Rへの接続は、本文のリモートデスクトップという記述と表1のTCP/3389からRDPに結び付きます。

次に、それぞれの段階で「何を使い回し、何を変えて試しているか」を読みます。PC-Pでは同じIDに異なるパスワードを多数回試しています。一方、PC-Sへのリバースブルートフォース攻撃では、一つのパスワードを異なるIDに試しています。どちらも認証への攻撃ですが、IDごとの失敗回数を数えるロックアウトが効くかどうかは同じになりません。

最後に、復旧と調査に必要なデータが残る条件を確認します。バックアップの保存世代と実施時刻、ログの保存上限と上書き条件は、単なるシステム紹介ではありません。設問4で「なぜ復旧や調査ができなくなるのか」を説明するための条件です。

### 設問をつなげて見る

| 設問 | 確かめていたこと | 読む場所・使う知識 |
| --- | --- | --- |
| 1 | 初動で行う調査の名称と役割 | 電磁的記録の証拠保全・調査・分析とデジタルフォレンジックス |
| 2 | 攻撃方法と接続手段の特定 | ログイン失敗の記録、接続説明、FWの許可ルール |
| 3 | 認証対策が効く条件・効かない条件 | 同じIDでの失敗回数と、試行するIDの分散 |
| 4(1) | バックアップから戻せなくなる条件 | 暗号化の時刻、月曜のフルバックアップ、1世代への上書き |
| 4(2) | 過去の攻撃を調査できなくなる条件 | ログ上限到達時に古い記録を上書きする設定 |
| 5 | 復旧用データの変更を防ぐ仕組み | イミュータブルバックアップと保存世代 |

### 必要だった知識と、その使い方

**アカウントロックアウト**は、一定回数ログインに失敗したIDの利用を制限する仕組みです。この問題では、同じIDへの連続試行を抑える一方、IDを変えながら行う攻撃には限界があることを判断するために使います。

**フルバックアップと差分バックアップ**では、何を基準にどのデータを保存するかが異なります。ただし、この設問の決め手は方式名だけではありません。前日に暗号化されていたという仮定と、月曜のフルバックアップで前の世代を上書きする条件を組み合わせる必要があります。調査された今回の侵入時刻と、設問が仮定する前日感染を混ぜないことも大切です。

**イミュータブル**は、書込み後のデータを変更できない性質です。古い時点に戻るために複数世代を残すことと、残したデータ自体の書換えを防ぐことは、それぞれ違うリスクへの対策です。変更できないだけで、必ず感染前のデータが存在するとまでは言えません。

### 本文から答案を作る例

設問3の「防御できない理由」では、次の順に考えます。

1. 本文の事実：漏えいしたパスワードを使い、異なるIDでログインを試す。
2. 仕組み：ロックアウトは同じIDへの失敗回数で働く。
3. 判断：一つのIDで失敗を重ねないので、しきい値に届かないおそれがある。
4. 答案：指定語「同一」を使い、25字以内で理由を述べる。公式例の一つは「同一のパスワードで異なるIDにログイン試行するから」。

「リバースブルートフォース攻撃だから」だけでは、対策が効かない理由を説明できていません。逆に、対策を追加する提案を書くと、問われている「理由」から外れます。

### 次の問題でも使うこと

- 対策名を見たら、「何を単位に、どの条件で働くか」を確認する。
- 復旧・調査を問われたら、「必要な時点のデータが、改変されずに残っているか」を確認する。
- 理由の記述では、本文の事実と仕組みをつないで説明する。

この草案を実画面へ入れる際は、先頭の見取り図と解き方を開き、用語の補足や答案例を必要に応じて展開する。全文を長い一枚の必読文として表示しない。

## 7. 実装へ進む際の設計案

### 教材

- caseに任意の `caseExplanation` を追加する案を推奨する。既存の `fields[].explanation` と `rubric` は各欄の説明として使う。
- 大問解説は、短い導入と順序を持った説明ブロックで表現する。各ブロックに、小問ID・回答欄ID・本文参照を必要に応じて持たせ、参照先を検証する。
- 作成時は論点・解き方・知識・答案・再利用の観点を点検するが、全項目の固定字数・固定個数は要求しない。表示できる表・図・数式等は既存の制限された描画方式に合わせる。
- `schemas/case-material.v2.json`、`tools/written_content.py`、ランタイムの検証、教材ハッシュ・確認台帳を一緒に更新する。JSONへ項目を足すだけで公開対応済みとはしない。
- 作成元の版を上げ、追加内容を独立レビューした教材だけを生成する。既存の内容承認を大問解説の承認に読み替えない。

### 記録・再開

- 回答・評価の完了と、振り返りの表示は分ける。`completed` の意味を変更せず、計画実績を二重に数えない。
- 新規の取り組みでは、大問解説を教材スナップショットに含める。教材更新で、進行中の回答と本文が差し替わらないようにする。
- 最初の実装では、表示段階・振り返り位置は既存の端末内チェックポイントの拡張を候補とする。これなら新しい読了イベントを学習記録へ追加する必要はない。
- 現在のFirestore Rulesは `progress` や `assistance` のキーを限定している。同期する段階や閲覧時刻を追加する場合は、Rules・検証・バックアップを含めて契約を更新する必要がある。
- 端末内だけに表示位置を保存する案では、別端末に振り返りの細かいスクロール位置は引き継がれない。完了済みの取り組みから振り返りを開ける導線は各端末に用意する。
- 古い取り組みには大問解説のスナップショットがない。初期実装では従来どおり閲覧でき、新しく解き直すと新解説を使える。古い履歴にも新解説を補助表示したい場合は、対応する問題・版を照合する仕組みを追加し、履歴の教材自体は書き換えない。

### AI・オフライン

標準の説明はレビュー済みの教材として提供し、オフラインでも読めるようにする。AIは、全欄確定後に大問全体や本人の疑問点を追加で尋ねる任意の補助とする。初期実装では既存の欄別AI質問を使い、全体AI質問の拡張は後続でもよい。

## 8. 進める順序と確認すること

### 第1段階：3題の草案で説明内容を決める

セキュリティ・DB・PMの3題を作り、本文・図表・公式例・採点講評と照合する。作成者と別の確認者が、本文から解答に至る説明、用語の定義、適用条件、未公表の採点基準を作っていないかを確認する。

確認したいのは「長くなったか」ではなく、学習者が本文を見ながら解法をたどれ、どの知識が必要だったかを説明できるか。先に説明内容を固め、画面を定型文で埋めない。

### 第2段階：表示・保存・開示を実装する

3題を対象に、大問解説の受け入れ、振り返り画面、完了時の導線、本文と小問への往復、再開を実装する。既存の未提供題も混在して学習できることを確認する。

必要な検証は、全欄確定前の漏えい防止、評価待ちの維持、最終確定・評価時の表示、保存失敗時の入力保持、戻る操作、次題の範囲維持、古い教材・履歴、オフラインとバックアップの往復。320／390px・PCで科目Aの既存の色・文字倍率・操作配置と比較する。状態契約を変更した場合は同期とRulesも検証する。

### 第3段階：効果を見て分野ごとに広げる

3題で試した後、他の分野も代表題を作り、その分野に必要な図解や説明を決めてから残りへ進める。最初から88題へ同じ文型を一括生成しない。

評価には、振り返りから本文・小問へ戻って理解を確かめられるか、同じ考え方を使う未見の課題で根拠を説明できるかを使う。確認用の問いを用意する場合も、振り返りを読むための必須操作にはしない。

閲覧時間や再回答の正解だけでは、読みにくさや正答の記憶と区別できない。これらだけを改善効果にせず、試用時の発言や答案の根拠も確認する。恒常的な計測や新しい学習記録の追加は、試用で必要性が分かってから判断する。
