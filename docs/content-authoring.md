# 問題を追加する手順

**先に受け入れる土台を整え、その仕様に合わせて各問題を作る。** 土台の担当と作問の担当を分けて進める。既存資格に年度・試験回を追加する場合は、今ある土台を確認して再利用する。

この文書が作業の入口。[JSON・生成・取り込みの詳細](content-format-reference.md)、[ヒントの共通ルール](hint-authoring.md)、[解説の記述ルール](explanation-authoring-rules.md)、[FP2級の個別仕様](fp2-authoring.md)は必要な箇所を参照する。

| 段階 | 担当の仕事 | 引き渡すもの |
| --- | --- | --- |
| 1. 土台を整える | 資格・科目・形式・保存先・検証方法を決め、必要な機能だけ整える | 資格設定、作成元の枠、作問依頼、検証方法、未対応事項 |
| 2. 各問題を作る | 原本を読み、本文・図・正答・解説を作る | 未確認の草稿、原本・根拠、作成担当と進捗 |
| 内容レビュー・公開 | 作者とは別担当が確認し、修正後の内容を統合する | 確認台帳、版・ハッシュ、生成物、公開確認 |

## 1. まず土台を整える

### 1-1. 既存の実装と作業を確認する

最新main、`AGENTS.md`、作業ツリー、対象資格の `qualification.json`、公開教材、進捗、未確認草稿を読む。既存IDと担当範囲を確認し、同じ試験回・問題の重複登録や作業の競合を避ける。

既存資格では **年度の追加だけで新しい資格や科目を作らない**。資格設定を正本として使い、不足する形式・分野・出典の扱いだけを整える。APのA/Bのように記録と受験対象を分ける必要がある場合は、同じ資格の別 `examPartId` とする。計画は資格単位で共有し、選択問題の問数とcaseの題数を足さない。

### 1-2. 作問前に決めること

| 項目 | 決める内容 |
| --- | --- |
| 対象 | 資格ID、科目ID、試験回・年度、原本の問番号、今回作る範囲 |
| 由来・用途 | 公式過去問／独自問題／派生、通常学習／診断／固定模試。提供されたオリジナル問題を公式問題扱いしない |
| 分類 | `topicId`、必要なら対象シラバス・言語・学習目標。分類名だけで別IDを増やさない |
| 問題形式 | 選択問題か、本文→小問→回答欄を持つcaseか。採点・自己評価の方法、字数・単位・丸め指示 |
| 識別子 | 問題・case・小問・回答欄・選択肢のID規則。出典の番号やコードから安定して付け、表示順やランダム順に依存させない |
| 原本 | 問題・解答例・提供されている講評等のURL、保存先、SHA-256、利用条件、第三者資料の扱い |
| 納品 | 草稿・図・確認台帳の保存先、担当範囲、検証コマンド、保留の記録方法 |

図を使う問題、複数選択、数値や記述など、今回の範囲にある形式を先に洗い出す。未対応形式があれば、作問側の都合で既存形式へ押し込まず、土台側で対応するか今回の対象から外す。

### 1-3. 現在使える形式を選ぶ

| 教材 | 作成元の形式 | 採点・注意点 |
| --- | --- | --- |
| 一つ選ぶ | 通常問題の `singleChoice`、`choices`、`correctChoiceId` | 正答は選択肢IDで指定 |
| 複数選ぶ | 通常問題の `multipleChoice`、`correctChoiceIds`、`selection` | 指定数／すべて選択を区別。組み合わせの完全一致で、部分点なし |
| 共通本文に複数小問 | `case-material.v2` の `body`→`items`→`fields` | 1case全体で最大20回答欄。大問・小問・欄数を区別する |
| case内の選択・短答 | `singleChoice`／`shortText`、`referenceAnswers` | 選択と、短答を登録例で照合する場合は `exactText`。短答は `self` も使え、未登録表現は自己評価へ |
| 自由記述 | case内の `freeText`、`grading.method: self` | 公式解答例・根拠・`rubric`で自己評価。AIの自動採点を前提にしない |
| 数値 | case内の `numeric`、`grading.method: exactDecimal` | 十進文字列で照合。単位・桁・丸め指示を明記する |

通常問題配列の `freeText`／`deferred` は草稿保管用で、公開する記述式の入れ物ではない。記述・数値学習にはcasesを使う。Schemaは [選択問題](../schemas/question-format.v1.json)・[case](../schemas/case-material.v2.json)・[回答欄](../schemas/case-field.v1.json)を参照。

通常問題の正答は選択肢IDで指定する一方、caseの選択欄の `referenceAnswers` には正答の表示ラベルを保存する。二つの形式を混同しない。

### 1-4. 枠と検証方法を用意する

新しい資格では `content/<資格ID>/qualification.json` に名称、分野、科目、出典表示と各作成元のパスを定義する。一般的な作成元の構成は次のとおり。ファイル名の正本は資格設定であり、APなどの既存配置をこの例に合わせて移動しない。

```text
content/<資格ID>/
  qualification.json       # 科目・分野・参照する作成元を定義
  questions.json           # 選択問題。枠だけなら []
  question-reviews.json    # 別担当の確認台帳。未確認なら []
  cases.json               # caseSourceでこの名前を使う場合
  case-reviews.json        # caseReviewSourceで参照する確認台帳
  README.md                # 対象、ID規則、納品先、検証方法、未対応事項
```

原本は `sources/<資格ID>/`、図は対象形式に合う `assets/` 以下の保存先を決める。草稿の納品フォルダ内でも、統合後と同じ相対配置を使う。原本・図・草稿がどれに対応するかを土台側で定義してから引き渡す。

ケースを扱う場合だけ `caseSource`・`caseReviewSource` を設定し、対象科目を `unit: cases` とする。選択問題は `questionSource`・`questionReviewSource` で参照する。新設する資格は `requiresReviewedContent: true` として、確認済み解説と確認台帳を公開条件にする。法令の時点を持つ資格は `requiresLegalContext` と [法令情報の契約](../schemas/legal-context.v1.json)も定める。

**土台だけの資格は本番の `content/qualifications.json` へ登録しない。** 公開教材がある科目だけを選択画面へ出す。空の配列や合成テストを公開問題として埋めない。必要な確認は一時ディレクトリの合成教材で行い、内容承認の記録と区別する。

既存エンジンで表現できれば資格別の画面や採点処理を増やさない。新しい形式が必要なら、生成・表示・採点／自己評価・保存再開・同期とRules・バックアップ・AI質問・オフラインまで同じ契約で扱えるようにする。機能が未提供なら入口も作らない。

### 1-5. 土台の完了条件と作問への引き渡し

- 資格・科目・分野・ID・保存先が確定している。
- 今回使う形式を受け入れ、図を表示し、保存・再開できる。新設・改修した箇所を必要なテストで確認している。
- 草稿は公開元から分離でき、未確認教材を本番へ混ぜない。
- 作者が使える納品例、チェック方法と、レビュー担当が確認する対象を文書化している。
- 未対応・未確認の項目と次の担当を残している。

FP2級は [個別仕様](fp2-authoring.md)と既存の [資格設定](../content/fp2/qualification.json)を使う。既存のAP・AB-730に追加する場合も、まずその資格設定と既存台帳を引き渡す。

## 2. 次に各問題を作る

### 2-1. 草稿の保存先と担当を確認する

今回の試験回・問番号・担当範囲を決め、既存教材や他担当と重ねない。新しい納品は `deliveries/<資格ID>-<試験回等>/` など、引き渡し時に決めた場所へ保存する。外注する範囲は本文・正答・解説・必要な図までで、アプリや資格設定の変更は土台担当へ戻す。

AP科目Aの既存解説は `data/lessons/<回>.json`、文字起こしは `data/transcription-drafts/` から始める。AP科目Bの追加は [保存済み計画と担当](written-expansion-2021-2023.md)を確認する。生成済みの `data/qualifications/` や資格別HTMLを直接編集しない。

### 2-2. 一問ごとに行うこと

1. **原本を読む。** 問題文・全選択肢・表・図・注記・単位・字数制限を確認する。OCRやAI抽出は補助とし、読めない部分を推測で完成させない。
2. **本文と必要な図を作る。** 原本の意味・条件・出題上の強調を保持する。図は必要な範囲を切り出し、参照位置と選択肢ラベルを照合する。
3. **正答を照合する。** 公式解答例／正答と対応させ、計算は指定された単位・桁・丸めで検算する。提供された独自問題も、提供正答をそのまま正しいとみなさず根拠を確かめる。
4. **問題固有の解説とヒントを作る。** 判断の決め手・根拠と、理解に必要な途中式を記す。選択問題は全肢、caseは全回答欄について説明する。ヒントを用意・改稿する問題は [共通ルール](hint-authoring.md)でつまずき・段階ごとの新情報・残る判断・開示判定を記録する。
5. **形式と表示を確認する。** IDと正答、図、数式・表・コード、改行、ヒントの開示表示と評価、未開示の解答が先に見えていないことを確認する。
6. **草稿と根拠を保存する。** 作成担当、使った原本・URL・ハッシュ、未確認事項、作成済み／保留の実数と次の対象を残す。作者は内容確認台帳を承認済みとして作らない。

一問完成したら同じ形式で次へ進む。大量作成する前に、代表的な形式の少数草稿を統合担当へ渡し、枠との食い違いを解消する。

### 2-3. 作問・解説のルール

| 対象 | ルール |
| --- | --- |
| 原文・設問 | 条件、語調、選択肢、番号、否定や「最も適切／不適切」を保持する。解き方の補足を設問に混ぜない |
| 単一・複数選択 | 正答は安定したIDで指定する。複数選択の指定数は正答数と一致させ、単一選択の正答項目を混在させない |
| 各肢の理由 | 通常の選択問題は`choiceReasons`を選択肢と同順・同数で用意し、各肢固有の正誤の分岐点を書く。caseの選択欄は既存の`explanation`に各肢の根拠をまとめる。「公式正答ではない」だけで済ませず、「不適切な肢」が設問の正答になる場合も区別する |
| 解説 | `explanation`は「なぜその答えか」。必要な定義・根拠・計算・例外だけを書く。固定の文章量や記述順は求めない |
| 要約・要点 | `summary`は論点、`takeaway`は類題で使える知識。一般の契約では任意。既存形式で必須なら従うが、同じ説明を三回複製しない |
| 強調 | 解説の重要な条件だけを同じ行で閉じる`**…**`で強調する。必須数なし。数値だけを抜き出して条件を落とさず、生HTMLは書かない |
| ヒント | [全資格共通のヒント基準](hint-authoring.md)に従う。初学者に必要な知識・手段を教え、内容に合わせて開示フラグを付ける。段数・任意性は教材契約に従う |
| 記述・実技 | 全欄に解答例・その欄固有の解説・`rubric`を用意する。語句一致と自己評価を区別し、非公表の部分点や100点換算・合否判定を作らない |
| 数値 | 正答は単位なしの十進文字列。単位と小数桁・丸め指示は別項目へ。入力を自動丸め・単位換算して正解にしない |
| 派生問題 | 理解を確かめるため必要な数値・対象等だけを変える。元問題の語調・説明量・構成を尊重し、実際の親だけを関連付ける |
| 修正 | 同じ問題は同じIDを使い、内容改訂時は版を増やす。太字の追加でも完成内容のハッシュ・レビューを更新する |

詳しい例は [解説の記述ルール](explanation-authoring-rules.md)、APの派生問題は [診断用の作問手順](diagnostic-authoring.md)を使う。

### 2-4. 文字・図とオフラインのルール

書式はフィールドごとに使い分ける。新規の本文は学習用テキストと必要な図を用意し、原本ページだけを本文の代わりにしない。

| 表示箇所 | 使える書式 |
| --- | --- |
| 通常問題の`stem`・`choices[].text`、caseの`body`・`items[].prompt`・`fields[].explanation` | 段落、太字、数式 `$…$`／`$$…$$`、パイプ表、コードブロック、原本の下線 `++…++` |
| 通常問題の`summary`・`explanation`・`takeaway`・`choiceReasons`・`hints[].text` | インライン太字`**…**`。数式・表のMarkdownは数式・表として表示されない |
| caseの選択肢テキスト、正答ID・`referenceAnswers`・採点用数値・`rubric`・ラベル | プレーンテキスト。装飾しない |

学習に必要な本文・解説・図・選択肢画像はオフラインでも読める構成にする。原本ページ全体は任意のオンライン参照とし、必要な図や条件が原本を開かないと分からない状態にしない。図はリポジトリ内の実ファイルを参照し、代替テキスト・対応ラベル・切り出し範囲を確認する。

通常問題の選択肢画像は `choices[].image` を使う。casesの図は選択肢図も含めて `bodyFigures` に、画像・本文内の一意な `anchor`・`alt`・`caption`を記録する。本文の位置・図の順序と一致させ、選択肢ラベルと対応させる。case画像は既存契約の `assets/written/` 以下のPNGとする。改訂時に古い記録が参照する図や原本を上書きしない。APの詳細は [文字起こし手順](transcription-authoring.md)を参照。

図表内の空欄・下線など、本文テキストにない参照先は、`caseCatalogSource` の対象entryに任意の `referenceTargets` を記録する。形式は `{"blank-a":"figure-1"}`（参照ID→図表の参照ID）。両IDはそのcaseの `bodyRefs` に存在し、対応先は `bodyFigures` のキャプションと一致し、原本ページが重なることが必要。原本画像で対象文字と対応を確認し、別担当の確認を残す。本文が検索できないことだけを根拠に図へ推定対応しない。確認済み本文・正答・図・レビュー済みcanonicalは書き換えない。`tests/body-reference-targets.py` が対応情報と別担当確認を、`tests/body-references.py` が実DOM上の全参照を確認する。

### 2-5. 出題時点と現行法令を混ぜない

過去問は原本の法令基準日・製品仕様等に沿って正答と解説を作る。確認できない日付は推測せず、法令情報を持つ形式では `null` にする。現行法令との照合は別の確認であり、過去問公開の必須条件にはしない。

最終法令チェックと改正確認済みの状態は既存の `legalReview` に記録する。根拠がなければ `unverified` のまま。改正が確認できても当時の公式正答を書き換えず、既存の学習非推奨・除外の仕組みで扱う。未確認という注意書きや確認日を学習画面に追加しない。

### 2-6. 納品時の状態と形式チェック

共通形式の納品は、通常問題を `enrichment: draft`、caseを `status: draft`で渡す。APの専用草稿・台帳はその形式を維持し、独立レビュー前に公開へ反映しない。新しい納品の確認台帳は空配列とし、作者・出典・検算・保留は別の作業記録に残す。既存台帳を空にしたり、チェックを通す目的で `reviewed` に変更したり、架空のレビュワー・日付・ハッシュを作ったりしない。

FP2級の納品例は次のコマンドで確認できる。他資格では資格ごとの納品契約と検証方法を使う。FP専用チェッカーを他資格に流用しない。

```sh
python tools/check-fp2-delivery.py /path/to/delivery
```

形式チェックは本文・根拠・正答が正しいことの承認ではない。HTMLの取り込みも未確認草稿を作る工程に過ぎない。対応する入力構造と重複・改訂の扱いは [取り込みの詳細](content-format-reference.md)を参照する。

## 3. 別担当がレビューし、確認済みの教材だけ公開する

作者とは別の担当が、原本と公式解答例から全本文・図表・全肢・全回答欄・解説・計算・強調を確認する。ヒントは [共通の問題別受入チェック](hint-authoring.md#一問ごとの作成と受入チェック)で、初学者への足場と開示判定も確認する。提供された独自問題は参照した一次資料と設問の成立も確認する。未確認部分が残れば、その問題を保留にして実数と理由を記録する。人数・並列度は依頼の範囲に従う。

指摘は作者が修正し、別担当が**修正後の最終版**を再確認する。承認済みの完成内容に対し、実際の作者・確認者・確認日時・方法と、所定の教材／原本／図のハッシュを記録する。レビュー形式は [詳細契約](content-format-reference.md)を参照し、APの既存台帳は従来の形式を維持する。

統合担当が確認済み教材と台帳・原本・図を既存の作成元へ取り込み、版とハッシュを更新する。新しい資格のカタログ登録はこの段階で行う。未確認草稿は混ぜず、既存の教材・レビュー根拠・個人記録を保持する。

共通の生成は次のコマンド。APの既存解説・文字起こしは、それぞれの専用反映手順を先に使う。

```sh
python tools/build-content.py
```

変更に応じて確認する。以下のテストは内容の独立レビューの代わりにはならない。

| 変更 | 主な確認 |
| --- | --- |
| 共通生成・資格追加 | `tests/content.py`、`tests/qualifications.py`、追加資格の原本・正答・レビュー照合 |
| AP科目A | `tests/corpus.py`、`tests/content.py`、解説／文字起こしの専用チェック |
| AP科目B | `tests/written-content.py`、該当バッチの確認台帳・図・原本照合 |
| AB-730 | `tests/ab730-content.py`、該当の取り込み・承認記録 |
| FP2級 | `tools/check-fp2-delivery.py . --reviewed`、`tests/fp2-content.py` |
| 画面・保存・オフライン | 対象形式のブラウザ、保存再開、バックアップ、必要な同期、PWA・必須図のオフライン表示 |

最新mainとPRの対象版を照合し、必要なCIを通して非forceで反映する。Pagesの成功だけで終わらず、公開ファイルと実画面を確認する。未開示のヒント・正答・解説が先に見えていないことと、答えを含むヒントの表示・評価・記録が整合することも確認する。個人のバックアップや学習記録は公開リポジトリに入れない。

## 依頼文のひな形

### 土台担当へ

> 対象は〈資格・科目・追加範囲〉。まず `AGENTS.md` と `docs/content-authoring.md` を読み、最新main・資格設定・進捗・既存草稿を確認してください。各問題の作成に入る前に、形式・ID規則・作成元／納品先・原本の扱い・レビュー台帳・検証方法を整えてください。既存機能を再利用し、不足する機能は保存・採点・同期・バックアップ・AI質問・オフラインまで揃えてください。枠の確認には非公開の合成テストを使い、未確認教材を公開カタログへ登録しないでください。完了した土台と未対応事項、次の作問担当が使える依頼仕様を残してください。

### 問題担当へ

> 対象は〈資格ID・科目ID・試験回・問番号〉、保存先は〈今回の納品先〉。`AGENTS.md`、`docs/content-authoring.md`、`docs/explanation-authoring-rules.md`、`docs/hint-authoring.md`と、土台担当が用意した〈資格別仕様〉に従ってください。まず少数の草稿で形式を確認し、その後に担当範囲を作成してください。原本の本文・全図表・全肢・全回答欄・解答例を読み、正答と計算を照合し、問題固有の解説と全肢／全欄の理由を作ってください。ヒントは初学者のつまずきから設計し、問題IDごとに各段階の新情報・残る判断・開示判定を作業記録に残してください。既存のヒントも同じ基準で点検してください。原文の条件と強調を保持し、解説は必要な条件だけ `**…**` で強調してください。納品はdraftとし、原本・根拠・担当・保留事項・次の対象を残してください。アプリ・資格設定・公開作成元の変更や、自分の草稿の承認済み化は行わず、内容レビュー担当へ引き渡してください。

### レビュー担当へ

> 対象は〈資格・科目・問題ID・版・草稿／根拠の場所〉。`docs/content-authoring.md`、`docs/explanation-authoring-rules.md`、`docs/hint-authoring.md`と〈資格別仕様〉に従い、作者とは別担当として最終版を確認してください。原本・全肢・全欄・公式解答・解説・計算を照合し、ヒントは問題ごとに初学者が得る新情報、残る判断、開示フラグを確認してください。「正解が選べる」という理由だけで学習上必要な定義・公式を削らず、答えを実質的に渡す場合はtrueとしてください。指摘はID・版と根拠へひもづけ、修正後に再確認し、未確認を承認済みにしないでください。実画面や初学者による確認を実施していない場合は、その事実も区別して残してください。
