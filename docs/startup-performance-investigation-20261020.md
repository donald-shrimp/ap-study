# アプリ起動時の読み込み調査（2026-10-20）

対象は「インストール初回」ではなく、保存済みのひと問を開き直してから、ホーム／中断画面を操作できるまで。調査対象の公開版・mainは `520ed218c0326e384c76088840448002778eb64e`、リリース `20261019-answer-options`。アプリのコードや公開内容は変更していない。

## 結論と優先順位

最も有力なのは、保存済みでもネットワーク応答を待つ設計。これに、起動前に読み込む機能・教材の量と直列の初期化が重なる。CPU処理だけで長く待っているとは限らず、回線が遅い・接続だけ残って応答しない場合に特に悪化する。

1. **キャッシュへのフォールバックが通信失敗後だけ。** `sw.js:53-99` の `networkFirst` はHTML、アプリのモジュール、教材、画像で `fetch(...,{cache:'no-cache'})` を優先し、例外になるまで保存済みデータを返さない。アプリ側 `src/content/catalog.js:7-28` も同様。アプリ固有のタイムアウト／キャッシュへ切り替える期限がない。`no-cache` は毎回全量転送するという意味ではなく、HTTPキャッシュの再検証でも往復待ちは発生する。ブラウザがメモリ／ディスクキャッシュから直接満たすリソースはあり、全ファイルが毎回ネットワーク転送されるわけではない。
2. **起動完了までの待ちが直列。** `src/app.js:455-500` では資格一覧→manifest→問題index→紙ペン分類→各保存先の初期化→認証復元→初回描画となる。科目Bには大問bankも加わる。`render()` は `initializing` 中に描画を抑制する（175行）。このため最後の処理が終わるまで「読み込んでいます」が残る。認証SDKの読み込み開始もこの後半（`src/sync/account.js:45`）で、`await account.ready`（`src/app.js:488`）が初回描画を止める。ホームが一瞬出てから元の問題へ切り替わる現象を防いだコミット `465af3c` は、この待ちを見えるようにしている。保存先を確認せずホームを先に出す方式への逆戻りは避け、必要処理の先行・並列化で短縮する。
3. **初回描画に必須な読み込み範囲が広い。** 公開版ではホーム表示までに約60個のJavaScriptモジュールと、約603KBのKaTeX、約624KBのFirebase SDKを読み込んだ。KaTeXは `src/ui/question-text.js:1` の静的importなので数式のないホーム／AB-730／資格選択画面でも起動前の依存に含まれる。`src/app.js` も科目B・計画・単語帳・診断等を静的importしている。Firebaseは動的importだが、起動後半で表示前に待つ。
4. **教材indexが大きく、科目Bにも科目Aの一覧が必要になっている。** AP indexは800問・1,287,639 bytes。検索文字列だけで約455KBあり、問題文・選択肢も含む。APは紙ペン分類185,335 bytesも起動前に読み込む。科目Bではこれらに加えて88大問一括bank 1,713,671 bytesを読む。AB-730 indexは174問・288,663 bytes。これらはファイルの非圧縮サイズで、毎回の実転送量ではない。通常学習800問分の全解説パック、PDFや原本画像全部を起動時に読み込む挙動は確認されなかった。中断問題／単語帳の復元では対象パック／カードの追加読み込みがあり得る。
5. **更新がある起動では先読みも通信を増やす。** SWの `CORE` は132ファイル・2,861,242 bytes。うちKaTeXフォントが60ファイル・1,076,572 bytesで、同じフォントのttf/woff/woff2まで保存対象。インストール／新SW更新時の処理であり、毎回全ファイルを再インストールするという意味ではない。バックグラウンド処理だが、起動通信と競合し得る。
6. **記録量に応じたローカル処理もある。** `src/storage/local.js:45-52` は全学習記録を読み出し、復元・並べ替え・JSON化する。その後の検証・集計も初回描画前。合成1,000件＋CPU4倍の条件で約1.15秒となり、長いタスク合計約603msを観測した。利用者本人の記録やログイン状態での時間は測っておらず、本人の主因と断定しない。

クラウドからの学習記録の同期完了を初回描画で待つ実装ではない。`src/sync/account.js:55-56` は各同期を開始した後に `ready` を解放する。認証復元・ローカル所有者の切替は待つため、SDK準備やログイン復元に時間がかかれば表示待ちには影響する。本人のログイン済みアカウントでの認証待ち時間は未計測。

### 保存済み・サーバ応答を意図的に遅らせた比較

HTTP/1.0のローカルサーバで各レスポンスに遅延を挿入。SW・教材キャッシュ・ゲストの保存済みホームを保持。

| 対象 | 各応答を0.5秒遅延 | manifestだけ2秒遅延 | 完全オフライン |
| --- | ---: | ---: | ---: |
| 科目Aホーム | 2.86秒 | 2.25秒 | 0.25秒 |
| 科目Bホーム | 3.41秒 | 2.22秒 | 0.22秒 |
| AB-730ホーム | 2.15秒 | 2.11秒 | 0.17秒 |

問題一覧等のfetchはAが4段階、Bが5段階、AB-730が3段階。manifestだけ遅くしてもほぼその2秒が表示待ちに加算され、保存済み教材では先に表示できていない。

別のブラウザプロセスを保存プロファイルで開き直す試験でも、通信の遅延により待ちが増加。通常は約1.2〜1.5秒、500ms/応答の人工条件ではA約25.4秒、B約20.3秒、AB-730約3.6秒。全リソースへ遅延を入れるHTTP/1.0の実験で、GitHub Pagesの実回線を模した予測値ではない。プロセス再起動後にはモジュール群の通信待ちも発生し、メモリ／ディスクキャッシュの効き方で大きく変動することを確認した。

CDPでページだけのネットワーク速度制限を設定した試験はSW内通信へ十分適用されず、低速回線の根拠から除外した。

## 改善するなら

1. リリース単位で揃ったシェル／JSと、SHA付きの教材bankをキャッシュから即座に返す。更新判定は画面表示後に回す。HTML・manifest・bankの整合性と教材のSHA検証、既存の明示的PWA更新操作は保持する。ネットワーク優先を残す箇所には、保存済み表示へ切り替える上限時間を設ける。
2. 認証復元・SDK準備と教材一覧の読み込みを可能な範囲で並列化。表示前には正しい所有者と中断画面の復元だけを揃え、非表示機能の準備を後へ回す。クラウド同期は既に表示の必須待ちではないので、同期を止めて速くする方針ではない。
3. 起動モジュールをまとめる／機能別に後からimportする。KaTeXは数式を表示する際に準備する。APのA/B教材取得経路を分け、BホームのためにA800問indexと紙ペン分類を待たない。大問bankは一覧用と本文用を分ける。検索用文字列の後読みも検討する。
4. SWのフォント先読みを利用形式へ絞る。記録量による遅延は上記を改善した上で、本人の件数に近い条件で個別に再計測する。

アプリをOSが破棄した後の再開では、上記の起動処理が再実行される。一方、単なる `visibilitychange` は同期のrefreshが中心で、それ自体が全教材の再読み込みやブラウザ再読込を指示しているわけではない。
