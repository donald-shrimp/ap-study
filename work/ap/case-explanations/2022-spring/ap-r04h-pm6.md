# 問6 クーポン発行サービス

## この問題は、何を考える問題だった？

この問題は、ホテルやレストランの予約サイトに「会員向けの割引クーポン発行サービス」を追加するにあたり、**データベースのテーブル設計・制約（E-R図・UNIQUE制約）で業務ルールをどのように保証するか**、そして**クーポンの獲得申込みが同時に殺到したときに、発行上限枚数を守りながら重複のない連番を安全に採番するにはどのようなSQL（トランザクションとロック）を書けばよいか**を考える問題です。

K社のサービスでは、施設や自治体などの提携スポンサーが「発行上限枚数」や「1人1枚限り」といった発行条件を設定し、会員が事前にクーポンを獲得してから施設予約時に利用します。人気のクーポンでは発行開始直後に多数の会員からの獲得アクセスが集中するため、データベース設計とSQLの両面で次の3つの課題に向き合う必要があります。

1. **E-R図とテーブル制約による業務ルールの強制（設問1）**：予約がどの利用プランを指すかを表す外部キーの設計と、「1人1枚限り」「1枚のクーポンは1つの予約にしか使えない」というルールをデータベースの **UNIQUE制約** で確実に守る方法を考えます。
2. **ロックなし方式での採番SQLと同時実行時の弱点（設問2）**：既存の明細から最大番号（MAX）を調べて＋1する方式のSQLを読み解き、同時アクセス時に同じ連番を取り合ってエラー（再操作）が起きる仕組みを確認します。
3. **ロックあり方式での採番SQLとCRUD図の更新（設問3・設問4）**：親テーブル（クーポン管理）の「発行済枚数」を先に UPDATE して行ロックを掛ける方式のSQLを完成させ、方式変更に伴ってテーブル操作（CRUD）がどう変わるかを整理します。

## まず、クーポンを獲得する条件と、予約に使う条件を分ける

設問に入る前に、クーポンの「獲得」と「予約での利用」という2段階の業務の流れと、図1のE-R図に登場する主要テーブルの役割を整理しておきましょう。

表1・表2にあるとおり、会員はまず獲得可能期間内にクーポンを**獲得**し、そのあと利用期間内に施設を**予約**するときに獲得済みのクーポンを指定して割引を受けます。「獲得」と「予約での利用」は別のタイミングで行われる操作であり、もし予約をキャンセルした場合は、有効期間内であればそのクーポンを別の予約に再び使うことができます。

図1のE-R図では、箱がテーブル（エンティティ）、箱の中の項目が列（属性）を表しています。特にクーポンのデータを管理する2つのテーブルの役割分担が重要です。

| テーブル名 | 主キー（実線の下線） | 記録する内容（1行が表すもの） |
| --- | --- | --- |
| **クーポン管理** | クーポンコード | クーポンの**種類ごと**のルール（発行上限枚数、獲得制限_1枚限り、割引額など）を1行ずつ記録する親テーブルです。 |
| **クーポン明細** | クーポンコード、クーポン発行連番 | 会員がクーポンを獲得するたびに、**実際に発行した1枚ごと**の記録（誰が獲得したか、何枚目か）を追加する子テーブルです。 |
| **予約** | 予約コード | 会員が行った施設予約1件ごとの記録です。利用したクーポン明細（クーポンコード＋クーポン発行連番）を外部キーとして持ちます。 |

ここで、行を一意に特定するための列（または複数列の組）を**主キー**といい、別のテーブルの主キーを参照するために持たせる列を**外部キー**といいます。例えばクーポン明細では、クーポンコードXの1枚目（連番1）とクーポンコードYの1枚目（連番1）を区別するため、「クーポンコード」と「クーポン発行連番」の2列を合わせた複合主キーで「発行された特定の1枚のクーポン」を識別しています。

## 予約とクーポンの関係を、図と制約で表す

### 設問1(1) a〜c｜予約にどの利用プランを選んだか記録する

設問1(1)では、図1のE-R図において「予約」テーブルの中の空欄 a・b に入る属性名（下線の種類を含む）と、「利用プラン」と「施設」の間の空欄 c に入る関連（矢印の向き）を答えます。

まず空欄 a・b を考えます。会員が予約を行うときは、どの施設のどの「利用プラン」を選んだかを「予約」テーブルに記録する必要があります。

- 参照先である「利用プラン」テーブルの箱を見ると、**施設コード** と **プランコード** の2つに主キーを示す実線の下線が付いています。プランコード（01、02など）だけでは別施設の同じ番号と区別できないため、「施設コード＋プランコード」の2列の組で1つの利用プランを特定しているからです。
- あるテーブルの行を参照するときは、**参照先の主キーを構成するすべての列を、参照元のテーブルに外部キーとして持たせる**のがリレーショナルデータベースの基本ルールです。
- また、図1の凡例では「主キーには実線の下線、外部キーには**破線の下線**を引く」と定められています。「予約」テーブル自身の主キーは「予約コード」だけであり、追加する2列は主キーではなく外部キーなので、どちらも破線の下線を付けます。

したがって、aとbには **施設コード** と **プランコード** をいずれも外部キーを示す**破線の下線**付きで入れます（aとbの順序は入れ替えても構いません）。

次に空欄 c（施設と利用プランの間の関連）を考えます。

- 1つの「施設」は複数の「利用プラン」を提供しますが、それぞれの「利用プラン」は特定の1つの「施設」に属します。つまり、施設と利用プランは **1対多** の関係です。
- 図1の凡例を確認すると、1対多の関連線は「1」の側から「多」の側へ向かって矢印を引きます。
- 図1では「利用プラン」（多の側）の箱が上で、「施設」（1の側）の箱が下に配置されているため、下から上へ向かう矢印である **↑** が c に入ります。

### 設問1(2) d｜既存のクーポン明細に重複を防ぐ制約を加える

設問1(2)では、既存の「クーポン明細」テーブルに対して「1人1枚限り」の獲得制限を実現する制約を追加するSQL文（図2）の空欄 d を埋めます。

図2のSQL文は、すでに作成されているテーブルの定義を変更して新しい制約を追加する ［ d ］ クーポン明細 ADD CONSTRAINT ... UNIQUE (...) という形をしています。SQLにおいて、既存のテーブルに列や制約を追加・変更するときに使う命令は **ALTER TABLE** です。したがって、空欄 d には **ALTER TABLE** が入ります。

ここで追加している UNIQUE (クーポンコード, 獲得会員コード, 獲得制限_1枚限り) という **UNIQUE制約（一意制約）** がどのように働くのかも確認しておきましょう。

- **1枚限りの制限があるクーポン（獲得制限_1枚限り ＝ 'Y'）の場合**：
  - 会員AがクーポンXを1回獲得すると、3列の値は ('X', '会員A', 'Y') として記録されます。
  - 同じ会員Aがもう一度同じクーポンXを獲得しようとすると、再び ('X', '会員A', 'Y') を追加しようとして3列の組が完全に一致するため、UNIQUE制約違反となって2枚目の獲得を確実にブロックできます。
- **1枚限りの制限がないクーポン（獲得制限_1枚限り ＝ NULL）の場合**：
  - 値が存在しないことを表す NULL には、「制約の対象列に1つでも NULL が含まれている行同士は、UNIQUE制約の重複とみなさない」というDBMSの仕様があります。
  - そのため、制限がないクーポンでは同じ会員が ('Y', '会員A', NULL) を何行追加しても制約違反にならず、何枚でも獲得できます。

### 設問1(3)｜1枚を二つの予約に同時に使えないようにする

設問1(3)では、下線①「予約テーブルの（クーポンコード，クーポン発行連番）の組にUNIQUE制約を設定する」ことが、どのような業務要件を実現するためのものかを30字以内で答えます。

「予約」テーブルにある（クーポンコード，クーポン発行連番）の2列の組は、会員が獲得した**特定の1枚のクーポン**（クーポン明細の1行）を指す外部キーです。

もしこの2列の組にUNIQUE制約がなければ、ある会員が獲得した「クーポンXの1枚目」を使ってホテルAを予約したあと、同じ「クーポンXの1枚目」をもう一度指定してホテルBも予約する、といったように**1枚のクーポンを複数の予約に二重使いすること**ができてしまいます。

予約テーブルの（クーポンコード，クーポン発行連番）にUNIQUE制約を設定しておけば、ある予約ですでに使われているクーポン（同じクーポンコードと連番の組）を別の予約の行に書き込もうとした瞬間に重複エラーとなり、二重利用を防げます。なお、クーポンを使わない通常の予約ではこの2列が NULL になるため何件でも予約でき、また予約をキャンセルして予約テーブルから行が削除されれば、そのクーポンを別の新しい予約に再び使うこともできます。

**答案の組み立て方**

データベースの用語（UNIQUE制約や重複など）ではなく、表2にある**利用上の業務ルール（業務要件）**の言葉で、「1枚のクーポンが」「いくつの予約に利用できるか」を30字以内でまとめます。

- 対象：**1枚のクーポンは**
- 制限内容：**一つの予約だけに利用できる。**
- つなげると **1枚のクーポンは一つの予約だけに利用できる。**（「1枚のクーポンは一つの予約だけに利用できる。」（22字））となり、30字以内で業務要件を正確に表せます。

## 連番を、明細から計算する方式と管理行で更新する方式を比べる

### 設問2 e｜今までの最大番号の次を割り当てる

設問2からは、会員がクーポンを獲得したときに「発行上限枚数を超えないようにチェックしながら、1から始まるクーポン発行連番を順番に割り当てる」2つの方式を比較します。

図3の処理一覧を見ると、画面上で獲得ボタンを押す前の「クーポン獲得チェック」と、同意ボタンを押して実際に明細行を追加する「クーポン獲得」が別々の処理になっています。事前チェックの時点では残り枚数があっても、同意ボタンを押すまでのわずかな間に他の会員が最後の1枚を獲得してしまうことがあるため、**実際に行を追加する「クーポン獲得」のSQLの中でも発行上限枚数をチェックする**必要があります。

まず検討された「ロックなし方式」（図4）のSQLを読み解きましょう。

- WITH 発行枚数 (枚数) AS (SELECT COALESCE(MAX(［ e ］), 0) FROM クーポン明細 WHERE クーポンコード = :クーポンコード)
- この共通表式（WITH句）では、「クーポン明細」テーブルから対象のクーポンコードの行だけを集め、**これまでに発行された連番の最大値**を求めて「現在の発行済枚数」としています。
- クーポン明細テーブルで1枚ごとの通し番号を記録している列名は **クーポン発行連番** なので、MAX関数の引数である空欄 e には **クーポン発行連番** が入ります。

このSQLの動きを具体的にたどってみましょう。

1. **まだ1枚も発行されていないとき（1枚目の発行）**：
   - 該当する明細行が0件なので MAX(クーポン発行連番) は NULL になります。
   - COALESCE(値, 0) は「最初の値が NULL なら 0 に置き換える」関数なので、発行枚数.枚数 は 0 になります。
   - 続く INSERT 文の中の副問合せ SELECT 枚数 + 1 FROM 発行枚数 WHERE 枚数 < :発行上限枚数 によって、0 + 1 ＝ 1 が新しいクーポン発行連番として挿入されます。
2. **すでに発行上限枚数に達しているとき**：
   - WHERE 枚数 < :発行上限枚数 の条件を満たさないため、副問合せの結果が0行（つまり NULL）になります。
   - 主キーの一部である「クーポン発行連番」に NULL を入れて INSERT しようとすることで、表3のとおり**主キー制約違反**が発生し、上限を超えた発行が阻止されます。
3. **ロックなし方式の弱点（同時申込みが重なったとき）**：
   - 例えば現在2枚まで発行済み（最大値が2）のときに、会員Aと会員Bの獲得処理がほぼ同時に実行されたとします。
   - どちらもロックを掛けずに MAX(クーポン発行連番) を読み取るため、両方のトランザクションが「現在の最大値は 2 だから、次は 3 番だ」と計算してしまいます。
   - その結果、2人とも同じ連番 3 で INSERT を実行し、後から実行された方が**主キーの重複エラー**で弾かれてしまいます。まだ発行上限枚数に達していないのにエラーになって会員に最初からやり直し（再操作）をさせてしまうのが、ロックなし方式の問題点です。

### 設問3 f・g｜管理行をロックし、発行済枚数を一つずつ増やす

設問3では、同時申込みによる番号の取り合い（主キー重複エラー）を防ぐために考案された「ロックあり方式」（図5）のSQLの空欄 f・g を埋めます。

ロックあり方式では、「クーポン管理」テーブルに **発行済枚数**（初期値0）という列を追加します。そしてクーポンを獲得する際、明細行を INSERT する**前**に、まず親テーブルである「クーポン管理」の該当行を **UPDATE文** で更新します。

1. **空欄 f（UPDATE文で更新する内容）**：
   - クーポンを新たに1枚発行するので、「クーポン管理」テーブルの 発行済枚数 の値を現在の値から 1 増やします。
   - UPDATE文では更新内容を SET 列名 = 新しい値 の形で書くため、空欄 f は **SET 発行済枚数 = 発行済枚数 + 1** となります。
2. **空欄 g（UPDATE文を実行する上限チェック条件）**：
   - すでに上限に達しているときは 発行済枚数 を増やしてはいけません。
   - WHERE句の条件 WHERE クーポンコード = :クーポンコード AND 発行済枚数 < ［ g ］ を見ると、更新前の 発行済枚数 が上限未満のときだけ更新するようになっているため、空欄 g には「クーポン管理」テーブルの列名である **発行上限枚数** が入ります。

なぜこの「先に UPDATE する」手順だと、同時申込みが重なってもエラーにならないのでしょうか。「ロックなし方式（図4）」と「ロックあり方式（図5）」の動作を比べてみましょう。

| 確認する場面 | ロックなし方式（図4のSQL） | ロックあり方式（図5のSQL） |
| --- | --- | --- |
| **同じクーポンの獲得申込みが同時に2件来たとき**（例：上限5枚、現在2枚発行済み） | 2件とも明細の最大値「2」を同時に読み取り、同じ連番「3」を INSERT しようとして片方が主キー制約違反（再操作）になります。 | 先に UPDATE を実行した方が管理行に**行ロック**を掛けて発行済枚数を「2→3」に更新し、連番「3」で明細を追加します。もう一方はロックが解けるまで待ってから「3→4」に更新するため、連番「4」で正常に獲得できます。 |
| **すでに発行上限枚数に達しているとき**（例：上限5枚、現在5枚発行済み） | 副問合せが NULL を返し、連番に NULL を INSERT しようとして主キー制約違反で停止します。 | 発行済枚数 < 発行上限枚数 を満たさないため UPDATE が0件更新となり、発行済枚数は「5」のまま増えません。続く INSERT で既存の連番「5」を重複追加しようとして主キー制約違反で停止します。 |

このように、ロックあり方式では最初の UPDATE 文によって対象のクーポン管理行に排他ロック（トランザクションが終わるまで他の処理を待たせる仕組み）が掛かるため、同時アクセスが来ても1件ずつ順番に 発行済枚数 がカウントアップされ、上限に達するまでは誰一人エラーにならずに連番を割り当てることができます。

### 設問4 下線②・③｜図5を表ごとの操作に分けてCRUD図を更新する

設問4では、下線④「ロックあり方式（図5）を採用したことに伴い、図3のCRUD図の『クーポン獲得』の行にある下線②（クーポン管理欄）と下線③（クーポン明細欄）を修正する」問題です。

CRUD図とは、各処理がどのテーブルに対して **C（Create：追加）**、**R（Read：参照）**、**U（Update：更新）**、**D（Delete：削除）** のどの操作を行うかを表にまとめたものです。ロックなし方式（図4）からロックあり方式（図5）へ変わったことで、「クーポン獲得」処理の中で実行されるSQLが各テーブルに何をしているかを1文ずつ確認しましょう。

1. **下線②：「クーポン管理」テーブルに対する操作**：
   - 図5の1文目の UPDATE クーポン管理 ... で、クーポン管理テーブルの 発行済枚数 を**更新（U）**しています。
   - さらに図5の2文目の INSERT INTO クーポン明細 ... SELECT ..., 発行済枚数, ..., 獲得制限_1枚限り FROM クーポン管理 WHERE ... の中で、更新後の 発行済枚数（これが新しい連番になります）と 獲得制限_1枚限り をクーポン管理テーブルから**参照（R）**しています。
   - したがって、参照（R）と更新（U）の両方を行うため、下線②は **RU** となります。
2. **下線③：「クーポン明細」テーブルに対する操作**：
   - ロックなし方式（図4）では、最大の連番を調べるためにクーポン明細テーブルを参照（R）してから行を追加（C）していたため CR でした。
   - しかしロックあり方式（図5）では、新しい連番を「クーポン管理」テーブルの 発行済枚数 から取得するため、**クーポン明細テーブルを参照（SELECT）する処理がなくなりました**。
   - 図5でクーポン明細テーブルに対して行っているのは INSERT INTO クーポン明細 ... による新しい行の**追加（C）**だけなので、下線③は **C** となります。

## 次の問題でも使うこと

- **複合主キーを参照する外部キーの設計**：参照先のテーブルが2列以上の複合主キー（例：施設コード＋プランコード、クーポンコード＋クーポン発行連番）になっているときは、参照元のテーブルにも同じ列の組を外部キーとして持たせます。
- **UNIQUE制約とNULLの性質**：複数列の組に対するUNIQUE制約は、「同じ会員が同じクーポンを複数回獲得できない」「同じクーポン1枚を複数の予約に使えない」といった重複防止ルールをDB側で保証するときに使われます。また、対象列に NULL が入ると重複チェックの対象外になる性質もよく問われます。
- **採番処理における行ロック（先にUPDATEする方式）**：MAX＋1 を SELECT で読むだけの方式は同時実行時に同じ番号を読んで重複エラーを起こします。親テーブルのカウンタ列を UPDATE ... SET 枚数 = 枚数 + 1 WHERE 枚数 < 上限 で先に更新して行ロックを取る方式は、同時アクセスを順番にさばく定石パターンです。
