# 問6 販売管理システムの構築

## この問題は、何を考える問題だった？

釣り具を販売するH社は、値引きキャンペーンの案内を葉書や広告などで出しています。しかし、お金をかけても売上に結び付かないものがありました。そこで、**どの案内方法にどれだけ費用をかけ、どれだけ売れたか**を調べ、次のキャンペーンを改善したいと考えています。

そのためには、商品や売上のデータを適切に保存し、調べたい条件で取り出して集計する必要があります。この大問は、次の三つを業務の目的とつなぐ問題です。

- データをどのような表と関係で持つか。
- 表から必要なデータをどう取り出し、集計するか。
- 集められるデータの細かさと、保存する単位が合っているか。

SQLの単語を知っていても、**集計結果に何を残したいか**が分からなければ、適切な処理を選べません。最初に「会社が何を知りたいのか」を押さえましょう。

## 表を読むときは「1行は何を表すか」から

関係データベースでは、データを行と列からなる表で管理します。例えば商品表なら、商品番号・商品名・原価などが列で、個々の商品が行です。

この問題のE-R図は、管理する対象と、対象どうしの関係を表した図です。ここでは、図の箱に当たる対象をエンティティ、箱の中の項目を属性と呼びます。本文の指定により、新システムではエンティティ名が表名、属性名が列名になります。

### 設問1 a｜なぜ郵便番号にも主キーの印が必要？

主キーは、表の中の各行を他の行と区別するための項目です。一つの列だけで区別できなければ、複数列の組合せを主キーにできます。

店舗エリアは、店舗へ来てくれそうな会員の居住範囲です。一つの店舗エリアに複数の郵便番号を登録するので、「店舗エリア詳細」は、例えば次のようになります。番号・郵便番号は説明用の架空例です。

| 店舗エリア番号 | 店舗エリア郵便番号 |
| --- | --- |
| 10 | 1110001 |
| 10 | 1110002 |
| 20 | 1110002 |

店舗エリア番号だけでは、上の2行を区別できません。郵便番号だけでも、下の2行を区別できません。**店舗エリア番号と郵便番号の組合せ**で、そのエリアに含める一つの郵便番号を識別します。

したがって、設問1のaに入る属性は「店舗エリア郵便番号」で、既にある店舗エリア番号と一緒に主キーになります。原図では実線の下線が主キーの印なので、追加する属性にもその印が必要です。属性名だけ書いて終わると、どの行を区別するための項目かが表せません。

### 設問1 b｜関連の向きは、片側から両方考える

図1の「商品」と「キャンペーン商品」の関係では、一つの商品が複数のキャンペーン商品として登録されることがあります。一方、各キャンペーン商品の行が指す商品は一つです。このような関係を「1対多」と呼びます。

図の凡例では、多くなる側に向かう矢印が1対多の関連です。商品が左、キャンペーン商品が右なので、bは右向きの「→」です。矢印の意味は図の記法ごとに確認し、データが流れる向きだと思い込まないようにします。

## SQLは、必要な結果から逆に考えよう

SQLは、データベースへ検索や集計などを指示する言語です。まず、この問題に出る句の役割を押さえます。

| 書き方 | 役割 |
| --- | --- |
| SELECT | 出力する列や計算結果を指定する |
| FROM | データの取得元を指定する |
| JOINとON | 表どうしを、条件に従って組み合わせる |
| WHERE | 対象とする行の条件を指定する |
| GROUP BY | 同じ値を持つ行を、集計のためのグループに分ける |
| SUM／COUNT | 合計／行数などを求める関数 |
| ORDER BY | 結果の並び順を指定する |

図2のCKとUKは、括弧内のSELECT文で作った結果に付けた名前です。このようにSQL文の中に置いた別の問合せを、副問合せといいます。元の表を一度集計し、その結果を別の表のように扱っています。

図2では、二つの集計結果を組み合わせます。

- CK：キャンペーンを実施した種別ごとの、実施金額の合計。
- UK：売上がある種別ごとの、売上と原価の合計。

### 設問2 c｜外側のSELECTの取得元を指定する

外側のSELECTが、このCKなどを取得元として指定する箇所がcです。取得元を導く句は「FROM」になります。

### 設問2 d｜「実施したのに売れなかった種別」を消さない

説明用に、小さな架空データで考えましょう。以下の数値は原問の実績ではありません。

CKには、葉書Hの実施金額150円と、電子メールEの実施金額50円があるとします。しかしUKにあるのは、葉書Hの売上400円・原価140円だけです。電子メールEからは売上が生じていないので、その種別の行がUKにありません。

**内部結合（INNER JOIN）**は、指定した条件で両方に対応する行がある組合せを残します。これを使うとHは残りますが、Eが結果から消えます。

一方、**左外部結合（LEFT OUTER JOIN）**は、左側の行を残し、右側に対応する行があれば組み合わせます。対応する行がなければ、右側の列はNULLになります。NULLは値がないことなどを表すもので、数値の0とは異なります。

図2ではCKが左側です。CKを残す左外部結合なら、「50円使ったのに売上がない」というEの結果も表示できます。だからdに入るのは「LEFT OUTER JOIN」です。**売れなかったキャンペーンも改善の判断に必要**なので、この行を残す意味があります。

本文で定義された「COALESCE(UK.売上計,0)」は、UKの売上計がNULLなら0を返します。左外部結合で行を残した上で、売上がない箇所を0として表示できるわけです。

| 種別 | 売上計 | 原価計 | 粗利計 | 実施金額計 |
| --- | --- | --- | --- | --- |
| H | 400 | 140 | 260 | 150 |
| E | 0 | 0 | 0 | 50 |

COALESCEだけでは、内部結合で消えた行を復活させることはできません。「行を残す処理」と「残った行の値を0で表示する処理」を分けて考えましょう。

### 設問2 e｜売上・原価・粗利は、何を掛けて合計する？

売上明細の1行は、売れた商品の個数や販売時の単価を持っています。売上を求めるなら、個数に販売時の単価を掛けます。原価を求めるなら、この問題では個数に商品表の1個当たりの原価を掛けます。

例えば架空の明細で、2個の商品を1個200円で販売し、1個当たりの原価が70円なら、次のようになります。

```text
売上：2個 × 200円／個 = 400円
原価：2個 × 70円／個 = 140円
粗利：400円 − 140円 = 260円
```

図2のMは売上明細、Sは商品の別名です。複数の明細の原価を足すので、eは「SUM(M.商品個数 * S.商品原価)」になります。SUMは各行で求めた金額を合計します。

このSQLの粗利計は、売上計から原価計を引いたものです。キャンペーンの実施金額は別列で表示しています。**この問題の粗利の式に、実施金額まで勝手に引かない**ようにしましょう。

## 葉書の送付先を見直すには、どの行を数える？

図3では、店舗エリアを見直すために「対象店舗の、過去1年間の、葉書キャンペーンによる売上」を郵便番号ごとに数えます。

### 設問3 f｜葉書キャンペーンに対象を絞る

店舗と期間は、既にWHERE句に書かれています。残っている条件は「葉書キャンペーン」です。表1によると、葉書を表す種別はHなので、fは「AND U.キャンペーン種別 = 'H'」になります。

ここで列に入っているのは「葉書」という日本語ではなく「H」という分類コードです。**その列がどんな値を持つかを、表1と対応させる**必要があります。

### 設問3 g｜郵便番号ごとの件数を多い順に並べる

次に、売上と会員のデータを結び付け、「GROUP BY K.会員郵便番号」で郵便番号ごとのグループにします。「COUNT(*)」はグループ内の行数を数え、その結果には「売上実績数」という名前を付けています。このSQLは売上の行を数えるので、同じ会員に複数の売上があれば、それぞれ数えます。会員の人数や商品個数の合計を求めているわけではありません。

最後に多い順へ並べます。大きい値から小さい値への順を降順といい、SQLでは「DESC」を使います。gは「ORDER BY 売上実績数 DESC」です。GROUP BYで集計することと、ORDER BYで並べることは役割が異なります。

## 設問4｜集計する細かさは、入手できるデータに合わせる

設問4での決め手は、T社から届くレポートが**週次で集計されている**という記述です。週次は1週間ごと、日次は1日ごとを意味します。データをどの細かさでまとめるかを、集計粒度と呼びます。

仮に「今週は広告が700回表示された」と分かっても、その数字だけから「月曜日は何回だったか」は分かりません。700を7で割っても、各曜日の実績を復元したことにはなりません。

今回の表は日次の実績を集計する想定になっています。週次の実績しか受け取れないなら、その単位に合うように見直します。レポートにない日別データを推測して埋める変更ではありません。

### 設問4の対応内容の答案を作ってみよう

設問4は、対応した内容を35字以内で答える指定です。

1. 本文から拾う条件：T社のレポートは週次。設計した表は日次を想定。
2. 解消すべき食い違い：受け取るデータより細かい日次の実績を保存しようとしている。
3. 対応として書く内容：Webキャンペーン実績表の集計単位を、日次から週次へ直す。
4. 答案例：公式例は「Webキャンペーン実績表の集計粒度を日次から週次に修正する。」（30字）。

「表を修正する」だけでは何を変えるかが分かりません。「T社へ日次レポートを依頼する」とすると、本文にない対応を追加してしまいます。**何を、どの状態からどの状態へ変えるか**を入れると、具体的な答案になります。

## この大問から持ち帰ること

- 表やE-R図では、1行の意味と、その1行を区別する項目を確認する。
- 集計では、対象条件・集計単位・結果に残す対象・並び順を、業務の言葉で説明してからSQLへ置き換える。
- データの保存・分析の単位は、実際に入手できる情報に合わせる。

余裕があれば、「電子メールのキャンペーンを実施したのに売上がなかったとき、なぜ結果に残す必要があるか」を説明してみましょう。「費用を使ったが売れなかった事実も、次の配分を見直す判断材料になるから」と説明できれば、外部結合の目的と業務がつながっています。
