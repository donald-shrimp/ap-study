# 問6 販売管理システムの構築

## この問題は、何を考える問題だった？

釣り具メーカーのH社は、葉書や電子メール、Webバナー広告などで値引きキャンペーンの案内を出しています。しかし、費用をかけて案内を出しても、まったく売上に結び付かないケースがありました。そこで、**「どの案内方法にいくら費用をかけ、その結果どれだけ売上が上がったか」**を正確に集計し、今後のキャンペーン計画を見直したいと考えています。

この目的を果たすには、売上やキャンペーンのデータを適切な表（テーブル）に分けて記録し、SQLを使って必要な条件で集計する必要があります。本問では次の3つを考えます。

- **表の設計（E-R図）**：テーブルの「1行」をどうやって一意に特定するか、テーブル同士がどんな関係にあるか
- **SQLによる集計**：売上がゼロだったキャンペーンも消さずに一覧へ残すにはどう結合するか
- **集計の粒度（細かさ）**：外部から受け取るデータの単位と、データベースに保存する単位が合っているか

SQLの文法知識だけでなく、**「業務上、どんな集計結果を見たいのか」**という目的から逆算して考えるのがこの大問のコツです。

## 表を読むときは「1行は何を表すか」から

関係データベース（リレーショナルデータベース）では、データを行と列の「表」で管理します。図1の**E-R図**は、管理する対象（**エンティティ**＝四角い箱）と、それが持つ項目（**属性**＝箱の中の項目名）、および対象どうしの関係（**関連**＝矢印）を表した設計図です。本問では、エンティティ名がそのままテーブル名、属性名が列名になります。

### 設問1 a｜なぜ郵便番号にも主キーの印が必要？

テーブルの中の各行を「この1行だ」と特定するための項目を**主キー**といいます。1つの列だけで特定できない場合は、複数の列を組み合わせた**複合主キー**にします。

「店舗エリア」は、ある店舗に来店が見込める会員の居住地域（郵便番号の集まり）です。1つの店舗エリアには複数の郵便番号が含まれ、逆に同じ郵便番号が複数の店舗エリアに含まれることもあります。理解しやすいよう、架空のデータで表を作ってみましょう。

| 店舗エリア番号 | 店舗エリア郵便番号 |
| --- | --- |
| 10 | 1110001 |
| 10 | 1110002 |
| 20 | 1110002 |

この表を見ると、「店舗エリア番号（10）」だけでは1行目と2行目を区別できません。逆に「店舗エリア郵便番号（1110002）」だけでも2行目と3行目を区別できません。**「店舗エリア番号」と「店舗エリア郵便番号」の2つをセットにして初めて、1行を特定できる**ことが分かります。

したがって、設問1のaには属性名「**店舗エリア郵便番号**」が入り、既存の「店舗エリア番号」と合わせた複合主キーとなるため、主キーを表す**実線の下線**を引きます。属性名だけを書いて下線を忘れると「主キーの一部である」という設計情報が抜けてしまうので注意しましょう。

### 設問1 b｜関連の向きは、片側から両方考える

図1の「商品」と「キャンペーン商品」の関係を考えます。1つの商品は、時期やキャンペーンを変えて何度も「キャンペーン商品」として登録されることがあります。一方、「キャンペーン商品」の1行（あるキャンペーンの対象になった1つの商品指定）に対応する「商品」は1つだけです。このような関係を**1対多**と呼びます。

本問のE-R図の凡例では、「1対多」の「多」の側へ向かって矢印を引くルールです。左側に「商品（1）」、右側に「キャンペーン商品（多）」が配置されているため、bには右向きの矢印「**→**」が入ります。「データがどちらへ流れるか」というイメージではなく、**「1つの相手に対して、こちらが複数存在する側（多の側）はどちらか」**で向きを決めましょう。

## SQLは、必要な結果から逆に考えよう

設問2・設問3では、データを集計するSQL文の空欄を埋めます。まず、登場する主なSQLの句の役割を確認しておきましょう。

| SQLの句・関数 | 役割 |
| --- | --- |
| **SELECT** | 結果として取り出したい列や計算式を指定する |
| **FROM** | データをどこ（どの表・副問合せ）から取り出すかを指定する |
| **JOIN ～ ON** | 2つの表を、ONで指定した条件で横につなぎ合わせる（結合する） |
| **WHERE** | 集計や取得の対象にする行の絞り込み条件を指定する |
| **GROUP BY** | 同じ値を持つ行どうしをグループにまとめる（種別ごと、郵便番号ごとなど） |
| **SUM / COUNT** | グループごとの「合計値」や「行数（件数）」を計算する集計関数 |
| **ORDER BY** | 結果の並び順を指定する（DESC を付けると大きい順＝降順） |

図2のSQLでは、括弧の中に書いた2つのSELECT文（**副問合せ**）の結果に、それぞれ CK と UK という名前を付けて一時的な表のように扱っています。

- **CK**：「キャンペーン実施」表から、キャンペーン種別ごとに**実施金額（費用）の合計**を集計した表
- **UK**：「売上」表と「売上明細」表などから、売上があったキャンペーン種別ごとに**売上と原価の合計**を集計した表

### 設問2 c｜外側のSELECTの取得元を指定する

図2の一番外側にある SELECT 文は、この CK と UK をつなぎ合わせたものから最終的な一覧を取り出しています。データの取得元を指定する箇所なので、cには「**FROM**」が入ります。

### 設問2 d｜「実施したのに売れなかった種別」を消さない

ここが設問2の最大の山場です。小さな架空データを使って、なぜ結合方法に工夫が要るのかを見てみましょう（数値は仕組みを理解するための架空の例です）。

いま、葉書（H）に150円、電子メール（E）に50円の費用をかけてキャンペーンを実施したとします。ところが、葉書（H）では売上400円（原価140円）が上がったものの、**電子メール（E）からは1件も売上が出なかった**とします。このとき、副問合せの CK と UK の中身は次のようになります。

- **CK（実施費用）**：H（150円）、E（50円）の2行がある
- **UK（売上・原価）**：H（売上400円・原価140円）の1行しかなく、**売上がゼロだった E の行は存在しない**

もしここで、両方の表に共通して存在する行だけを残す**内部結合（INNER JOIN）**を使うと、UK に存在しない E の行は結果から消えてしまいます。しかし、会社が知りたいのは「費用をかけたのに売れなかったキャンペーンはどれか」です。E が消えてしまったら、50円が無駄になった事実に気付けません。

そこで、左側の表（CK）の行をすべて残し、右側の表（UK）に対応する行があればつなぎ、なければ空っぽ（NULL）として残す**左外部結合（LEFT OUTER JOIN）**を使います。したがって、dには「**LEFT OUTER JOIN**」が入ります。

| 種別 | 売上計 | 原価計 | 粗利計 | 実施金額計 |
| --- | --- | --- | --- | --- |
| H | 400 | 140 | 260 | 150 |
| E | 0 | 0 | 0 | 50 |

なお、外側の SELECT にある COALESCE(UK.売上計, 0) は、「もし UK.売上計 が NULL（値なし）だったら数値の 0 に置き換えて表示する」という関数です。**LEFT OUTER JOIN で売上のない行を消さずに残し、COALESCE でその空欄を 0 に整える**という2段構えになっているわけです。

### 設問2 e｜売上・原価・粗利は、何を掛けて合計する？

副問合せ UK の中では、キャンペーン種別ごとの「売上計」と「原価計」を計算しています。

売上明細（別名 M）の1行には、売れた「商品個数」と販売時の「商品単価」が入っています。一方、1個あたりの「商品原価」は商品表（別名 S）にあります。たとえば、1個200円（原価70円）の商品を2個売った明細なら、計算は次のとおりです。

```text
・売上：商品個数 2個 × 販売時の商品単価 200円 ＝ 400円
・原価：商品個数 2個 × 商品表の商品原価  70円 ＝ 140円
・粗利：売上 400円 − 原価 140円 ＝ 260円
```

これを複数の明細行にわたって合計するため、原価計を求める空欄eは「**SUM(M.商品個数 * S.商品原価)**」となります。

なお、外側の SELECT で求めている「粗利計」は「売上計 − 原価計」であり、キャンペーンの実施金額はその隣の列に別枠で並べて比較する設計になっています。原価計の式の中にキャンペーン実施金額まで混ぜないよう気をつけましょう。

## 葉書の送付先を見直すには、どの行を数える？

図3のSQLは、店舗エリアを見直すために「対象店舗における、過去1年間の、葉書キャンペーンによる売上件数」を会員の郵便番号ごとに集計し、件数の多い順に並べる処理です。

### 設問3 f｜葉書キャンペーンに対象を絞る

図3の WHERE 句を見ると、「対象店舗（U.店舗番号 = :店舗番号）」と「過去1年間（U.売上年月日 >= :一年前年月日）」の条件はすでに書かれています。ここへさらに「葉書キャンペーンによる売上」という条件を付け加えます。

表1を確認すると、葉書キャンペーンを表す種別コードは 'H' です。すでにある条件に続けて絞り込むため、fには「**AND U.キャンペーン種別 = 'H'**」が入ります。列に格納されている値は日本語の '葉書' ではなくコードの 'H' なので、表1の定義どおりに指定しましょう。

### 設問3 g｜郵便番号ごとの件数を多い順に並べる

GROUP BY K.会員郵便番号 で郵便番号ごとにグループ化し、COUNT(*) AS 売上実績数 で各郵便番号の売上件数（売上行の数）を数えています。

最後に、この「売上実績数」が多い順（大きい順＝**降順**）に並べ替えます。SQLで降順を指定するキーワードは DESC なので、gには「**ORDER BY 売上実績数 DESC**」が入ります。

## 設問4｜集計する細かさは、入手できるデータに合わせる

設問4は、Webバナー広告の効果を管理する「Webキャンペーン実績」表の設計を見直す問題です。本文を読むと、広告代理店のT社から提供される実績レポートは**「週次（1週間単位）」で集計されたデータ**だと分かります。このように、データをどの単位（日ごと、週ごと、月ごとなど）でまとめるかを**集計粒度**と呼びます。

たとえば、T社から「今週1年間のバナー表示回数は合計700回でした」という週次レポートを受け取ったとしましょう。この合計値だけを見ても、「月曜日に何回表示され、火曜日に何回表示されたか」という1日ごとの内訳（日次データ）を知ることはできません。

ところが、当初設計していた「Webキャンペーン実績」表は、日次で実績を記録する前提になっていました。手に入らない日次データを記録しようとしても表を埋められないため、**受け取れるレポートに合わせて、表の集計粒度を「日次」から「週次」へ修正する**必要があります。

### 設問4の対応内容の答案を作ってみよう

設問4は、行った対応を35字以内で記述する問題です。

1. **本文の事実**：T社から届くレポートは週次集計だが、設計した表は日次集計を想定していた。
2. **解消すべき食い違い**：入手できるデータの粒度（週次）と、保存先の表の粒度（日次）が合っていない。
3. **具体的な対応**：Webキャンペーン実績表の集計粒度を、日次から週次に修正する。
4. **字数に合わせてまとめる**：公式解答例は「Webキャンペーン実績表の集計粒度を日次から週次に修正する。」（30字）です。

単に「表を修正する」だけでは何をどう変えるのかが伝わらず、「T社に日次レポートを出してもらう」では本文の前提（週次で提供される）を変えてしまいます。**「どの表の何を、どう変えるか（日次→週次）」**を明確に書きましょう。

## この大問から持ち帰ること

- **主キーと関連の向き**：その表の「1行」を特定するためにどの列の組合せが必要か（複合主キー）を具体例で確かめる。1対多の矢印は、どちらが「複数になる側」かで決める。
- **外部結合（LEFT OUTER JOIN）を選ぶ理由**：「実績がゼロだった項目（売上がなかったキャンペーン種別など）も消さずに一覧へ残したい」ときは、基準となる表の行を残す外部結合を使う。
- **データの粒度**：「細かいデータ（日次）を後から粗い単位（週次）にまとめる」ことはできても、「粗い集計値（週次）から細かい内訳（日次）を復元する」ことはできないため、入手できるデータの粒度に表の設計を合わせる。

余裕があれば、「電子メールのキャンペーンで売上が0円だったとき、なぜその行を消さずに集計表へ残す必要があるのか？」を業務の視点で説明してみてください。「50円の費用をかけたのに売上が0円だったという事実が見えなければ、次のキャンペーンで予算配分を見直す判断ができないから」と説明できれば、SQLの LEFT OUTER JOIN と業務目的がしっかり結び付いています。
