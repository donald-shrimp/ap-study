# 問10 容量・能力管理

## この問題は、何を考える問題だった？

A社では、製造部の生産管理と、営業部の販売管理を、一台のサーバで動かしています。注文データが増え、昼休みに終えるはずの販売分析処理が延びると、生産管理の応答まで遅くなりました。

キャパシティは、システムが処理したり保存したりできる容量・能力のことです。CPU、ストレージなどの計算・保存に使う資源をリソースと呼びます。必要な量を見込み、監視し、適切に割り当てることがキャパシティ管理です。

この大問では、**目の前の障害への対応と、将来も業務を支えるための計画をつなぐ**ことを考えます。機器の使用率だけでなく、部門間の業務のつながり、追加資源の費用、需要の変化まで読みます。

## 販売の処理が、翌日の製造へつながっている

オンライン処理は、利用者の要求などに応じてその都度行う処理です。バッチ処理は、データをまとめて処理する方式です。本問では、昼休みの12～13時にHバッチを動かし、前日の注文情報を分析します。

Hバッチの結果は、当日の13時30分までに生産管理へ渡し、Pバッチが翌日の生産計画案を作るために使います。製造部は、その案に基づいて翌日の生産計画を策定します。

```text
前日の注文情報
  → 当日12～13時：販売分析のHバッチ
  → 当日13時30分まで：生産管理へ結果を送信
  → Pバッチ：翌日の生産計画案を作成
  → 製造部：翌日の生産計画を策定
```

SLAは、サービスの提供条件などを取り決める合意です。本問のオンライン処理では、「要求の95％を3秒以内に応答する」というサービスレベル目標値があります。トランザクション要求は、システムへ依頼される処理の単位です。この目標は平均応答時間が3秒という意味ではなく、要求のうち一定の割合を指定時間内に処理するという条件です。

例えば説明用の100件で、94件が1秒、6件が4秒だったとします。平均は1.18秒でも、3秒以内は94％なので、この割合の条件を満たしません。これは目標値の意味を説明する架空例で、原問で観測された応答時間ではありません。

## 使用率の警告が、業務のインシデントへつながる

インシデントは、サービスの中断や品質低下など、通常どおりの利用を妨げる事象です。今回の流れを、表3から整理します。

| 時刻 | 起きたことと影響 |
| --- | --- |
| 12時00分 | Hバッチ開始 |
| 12時40分・50分 | ストレージ使用率の警告。中断して割当てを増やし、再開 |
| 13時00分 | Hバッチと生産実績のオンライン処理が重なり、CPUが高負荷に |
| 13時05分 | 生産管理の応答が遅れ、例外のメッセージを出力 |
| 13時10分 | 関係者を招集し、解決策の検討を開始 |
| 13時15分 | Hバッチが終わり、応答遅延も解消 |

ストレージの不足でHバッチを中断・再開したことが、CPUを使う時間帯の重なりにもつながっています。「ストレージの問題だから、ほかのリソースやサービスには影響しない」とは限りません。

### 設問1(1)｜遅延時にも、翌日の生産計画を立てられるよう協議する

実際の事例ではHバッチは13時15分に終わりました。その後の振返りでは、オンライン処理を守るためにデータ量を操作する対応を行うと、13時30分以降まで延びる場合もある、と検討しています。この二つを区別しましょう。

13時30分までに結果を送れなければ、翌日の生産計画づくりへ影響するおそれがあります。運用課だけで決められる技術上の設定に閉じず、注文を扱う営業部と、製造を行う製造部とで、業務への影響と対応を協議する必要があります。

設問は、その場で協議する内容を25字以内で答える指定です。例えば、公式例の一つは「前日の注文情報に基づく翌日の生産計画」です。「どの情報を使い、いつの何を守るか」を入れることで、具体的な業務の話になります。もう一つの公式例は、バッチ処理遅延による業務影響と対策を表すものです。二つを一つの欄へ両方書く必要はありません。

「SLAを変更する」と書くだけでは、翌日の工場の製造をどう守るかが決まりません。また、本文にない具体的な生産量や代替データの扱いを、既に合意された対策として作る必要もありません。

### 設問1(2)｜複数回の警告を、インシデント対応へつなぐ例外として扱う

表2のイベントタイプは、次のように分かれています。イベントは、監視で検知する出来事です。

| 種類 | 本問での扱い |
| --- | --- |
| 情報 | バッチの正常終了など。即時の対応は不要 |
| 警告 | リソースのしきい値超えなど。あらかじめ決めた対応を行う |
| 例外 | サービスの障害や目標値未達など。インシデント管理手順を開始する |

Sメッセージは、単独ではストレージ使用率のしきい値超えを示す警告です。しかし、Hバッチ中に繰り返し出る状況は、中断による遅延を重ね、生産管理の品質低下へつながりました。

そこで、**「Sメッセージが複数回出力されるイベント」**を例外として設定し、インシデント管理へつなげます。公式例は「例外になるように設定する。」です。すべての警告を一律に例外へ変える指示ではありません。

## クラウドでは、増やす契機と戻す契機を決める

オンプレミスは、自社の拠点などにサーバを設置して運用する方式です。本問では、従来の需要見込みでも2年後にはキャパシティが不足すると分かっています。既存機器は販売中止で増強できず、システム更改を検討しています。更改は、システムを新しい構成などへ置き換えることです。

IaaSは、仮想サーバやストレージなどの基盤をサービスとして利用する形です。A社は、OSとアプリケーションの間で働くミドルウェアの仕様に指定があるため、IaaSが適していると判断しています。

Fクラウドのリソースオンデマンドは、管理ツールを使い、必要に応じて資源を増減できる仕組みです。ただし、契約モデルを超えた増強分には追加の利用料がかかります。自動でいつでも無料の容量が増える、という条件ではありません。

### 設問2(1) a｜Sメッセージを認識した時点で、容量を増強する

オンプレミスでは、Sメッセージを認識した後にHバッチを止め、不要なデータを消してストレージの割当てを増やしていました。Fクラウドなら、その認識を契機に管理ツールでストレージを増強できます。

したがってaは、本文の字句を用いて「Sメッセージの出力を認識」です。空欄の後に「した時点で」と続くので、文章へ戻して確認します。

この認識をさらに遅らせ、サービスの応答遅延が起きてから初めて対処するのでは、Hバッチの遅延防止という目的に合いません。**何を見たら、どの操作をするか**を結び付けます。

### 設問2(2)（実施内容・理由）｜不要になった増強分を戻し、追加費用を抑える

Hバッチが正常終了した時点では、その処理のため一時的に増やした容量を元へ戻します。公式例の実施内容は「増強したストレージの容量を元に戻す。」です。

理由は、Fクラウドでは増強に応じた利用料が加算されるからです。公式例は「クラウド利用料が加算されるから」です。実施内容と理由は、それぞれ20字以内で別の欄に書きます。

```text
Sメッセージを認識 → 必要な容量を増やす → Hバッチを実行
  → 正常終了 → 一時的な増強分を元へ戻す
```

ここで行うのは、管理ツールで元のキャパシティへ戻す操作です。保存してある必要なデータを削除することや、何もせず自然に契約容量へ戻るのを待つことと、取り違えないようにします。

## 将来の需要を見直してから、契約と増強方法を計画する

### 設問2(3) b｜需要予測に基づく、リソース使用量の見積りを見直す

当初は「3年後に売上が2割増える」という見込みを使っていました。しかし、今月の経営会議で新製品の販売早期化が決まり、販売管理サービスの需要も変わると考えられます。

利用者数や要求件数、保存するデータ量などの需要予測から、どれだけのリソースを使うかを見積もります。見直すbは、本文の字句で「需要予測に基づくリソースの使用量の見積り」です。

売上が2割増えるからCPUも必ず2割、という単純な比例関係は指定されていません。販売の時期や使い方の変化も踏まえ、サービスの利用計画から見積もる順序を押さえます。

### 設問2(4) c｜見積りと目標値を基に、キャパシティ計画を策定する

キャパシティ計画は、リソース使用量の見積りとサービスレベル目標値などを基に、将来必要な容量・能力と増強方法を定める計画です。cは「キャパシティ計画」です。

```text
事業環境や利用計画の変化
  → 需要予測
  → リソース使用量の見積りを更新【b】
  → 目標の応答時間などと照合
  → 契約モデルと増強方法を含むキャパシティ計画【c】
```

F1～F5のどれが正解かを直接答える設問ではありません。各モデルの容量や金額が示されていないので、想像で選ばず、適切に決定するための前提と計画を答えます。クラウドの柔軟な増減と追加料金の特性も、その計画に反映します。

## この大問から持ち帰ること

- 処理の遅れを、依存する業務と締切までたどって考える。
- 監視イベントは、単独の警告と、重なって業務へ影響する状況を区別する。
- 資源の追加には、増やす契機だけでなく、元へ戻す契機と費用も組み合わせる。
- 将来の計画は、事業の変化から需要・使用量・サービス目標へ順につなぐ。

余裕があれば、「クラウドで必要なだけ増やせても、なぜキャパシティ計画が要るのか」を説明してみましょう。「必要なサービス水準を満たしつつ、どの契約と増強方法で適切な容量・費用にするかを決めるため」と説明できれば、目の前の対応と将来の計画がつながっています。
