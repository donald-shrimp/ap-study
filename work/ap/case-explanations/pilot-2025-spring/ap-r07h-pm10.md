# 問10 容量・能力管理

## この問題は、何を考える問題だった？

製造業のA社では、製造部が使う「生産管理サービス」と営業部が使う「販売管理サービス」を1台のサーバ上で動かしています。ところが、注文データの増加によって昼休み中に終わるはずの販売分析バッチが長引き、午後1時からの生産管理のオンライン処理と重なって応答遅延を引き起こしてしまいました。

システムが処理・保存できる容量や能力のことを**キャパシティ**といい、CPUやメモリ、ストレージといった計算・保存用の資源を**リソース**と呼びます。必要なリソースを見積もり、監視し、過不足なく割り当てる活動が**キャパシティ管理**です。

この大問では、**「目の前で起きた容量不足トラブルへの対処」**から出発し、**「クラウド移行後の柔軟な増減運用」**、さらに**「事業計画の変化を踏まえた将来のキャパシティ計画」**へと視野を広げて考えていきます。

## 販売の処理が、翌日の製造へつながっている

まず、2つの処理方式と、A社における部門間の業務のつながりを整理しましょう。

- **オンライン処理**：利用者が画面から操作するたびに、その場でリアルタイムに応答を返す処理
- **バッチ処理**：溜まったデータを決まった時刻にまとめて一括処理する方式

A社では、昼休み（12時〜13時）に販売管理の **Hバッチ** を動かして前日の注文情報を分析し、その結果を**当日の13時30分まで**に生産管理側へ渡すルールになっています。生産管理側ではそれを受け取って **Pバッチ** を動かし、翌日の生産計画案を作ります。

```text
前日の注文情報
  → 当日 12:00～13:00：販売分析の「Hバッチ」を実行
  → 当日 13:30（締切）：分析結果を生産管理サービスへ送信
  → 生産管理の「Pバッチ」：翌日の生産計画案を作成
  → 製造部：翌日の工場の生産計画を策定
```

また、オンライン処理の **SLA**（サービス品質合意）では、「トランザクション要求（画面からの処理要求）の**95%を3秒以内に応答する**」という目標値が定められています。これは「平均応答時間が3秒以内」という意味ではなく、「100件の要求があったら95件以上は3秒以内に返さなければならない」という**件数の割合**の条件です（たとえば100件中94件が1秒で返っても、残り6件に4秒かかれば平均は1.18秒ですが、3秒以内は94%なので目標未達となります）。

## 使用率の警告が、業務のインシデントへつながる

サービスの中断や品質低下など、通常の業務利用を妨げる出来事を**インシデント**と呼びます。表3の記録から、当日何が起きたのかを時系列で追ってみましょう。

| 時刻 | 起きた事象とシステムの状態 |
| --- | --- |
| 12:00 | 販売管理の **Hバッチ** を開始 |
| 12:40 / 12:50 | ストレージ使用率の警告（**Sメッセージ**）が2回発生。その都度Hバッチを中断し、不要データを消して割当てを増やし再開 |
| 13:00 | 中断のせいで終わらなかったHバッチと、午後の生産実績オンライン処理が重なり、**CPUが高負荷**に陥る |
| 13:05 | 生産管理のオンライン応答が遅れ、SLA目標未達を示す例外メッセージが出力される |
| 13:10 | 関係者を招集し、対策の検討を開始 |
| 13:15 | Hバッチが完了し、オンライン処理の応答遅延も解消 |

注目したいのは、**「最初はストレージ容量の不足だったのに、その対応でバッチが中断・延びた結果、13時以降のCPU負荷とオンライン応答遅延を引き起こした」**という連鎖です。1つのリソースの不足が、時間帯のズレを通じて別のリソースや他部門の業務へ波及する好例です。

### 設問1(1)｜遅延時にも、翌日の生産計画を立てられるよう協議する

当日のトラブルではHバッチは13時15分に終わりましたが、その後の振り返りでは「もしオンライン処理への影響を避けるためにHバッチの処理データ量を調整する対応をとった場合、**Hバッチの完了が締切の13時30分以降にずれ込むおそれもある**」と分かりました。

もし13時30分までに分析結果が届かなければ、製造部は翌日の生産計画を立てられなくなってしまいます。これはシステム運用課だけで勝手に決められる話ではなく、注文データを出す営業部と、それを使って生産計画を立てる製造部との間で、「バッチが遅れたときに翌日の生産計画をどう立てるか（業務への影響と対策）」を話し合って決めておく必要があります。

したがって、設問1(1)で協議すべき内容（25字以内）の公式解答例の一つは「**前日の注文情報に基づく翌日の生産計画**」です（もう一つの公式解答例のように、バッチ処理遅延による業務影響と対策という観点でまとめることもできます）。「SLAの目標値を緩める」といったシステム側の都合ではなく、**13時30分の締切に間に合わなかったときに影響を受ける「翌日の生産計画」の業務をどう守るか**に焦点を当てましょう。

### 設問1(2)｜複数回の警告を、インシデント対応へつなぐ例外として扱う

表2では、監視ツールが検知する出来事（**イベント**）を重要度に応じて3種類に分けています。

| イベントタイプ | このシステムでの位置付けと対応 |
| --- | --- |
| **情報** | バッチの正常終了などの通常記録。特別な対応は不要 |
| **警告** | リソース使用率のしきい値超過など。あらかじめ決めた手順で対処する |
| **例外** | サービス障害やSLA目標未達など。直ちに**インシデント管理手順**を開始する |

ストレージ使用率の上限超過を知らせる **Sメッセージ** は、1回出ただけなら「警告」として容量を広げる定型対処で済みます。しかし、今回のように**Hバッチの実行中にSメッセージが複数回出力される状況**は、バッチの中断・延長を繰り返して13時以降のオンライン処理の障害（インシデント）へ直結する危険な兆候です。

そこで、**「Sメッセージが複数回出力されるイベント」**については、単なる警告ではなくインシデント管理を開始する「例外」として扱うように見直します。したがって、設問1(2)の公式解答例は「**例外になるように設定する。**」です。

## クラウドでは、増やす契機と戻す契機を決める

A社では、従来の需要予測のままでも2年後には現在のオンプレミス機器の容量が限界に達し、しかも機器が販売終了で増設できないことから、クラウドサービス（Fクラウドの **IaaS**）へのシステム更改（置き換え）を検討しています。

Fクラウドの「リソースオンデマンド」機能を使えば、管理ツールから必要なときにストレージ容量などを柔軟に増減できます。ただし、**基本の契約モデルを超えて増強した分には追加のクラウド利用料がかかる**仕組みです。

### 設問2(1) a｜Sメッセージを認識した時点で、容量を増強する

オンプレミス環境では、Sメッセージが出たときにHバッチをわざわざ中断して不要データを削除していました。一方、Fクラウドへ移行したあとは、管理ツールからオンラインのままストレージ容量を増強できます。

では、いつのタイミングで増強操作を行えばよいでしょうか。Hバッチの遅延を防ぐためには、応答遅延が起きてからでは遅すぎます。ストレージ逼迫の兆候である「**Sメッセージの出力を認識**」した時点で直ちに増強を行います。空欄aの直後に「した時点で」と続いているため、本文の表現に合わせて「**Sメッセージの出力を認識**」を入れましょう。

### 設問2(2)（実施内容・理由）｜不要になった増強分を戻し、追加費用を抑える

Hバッチのために一時的にストレージを増強したあと、Hバッチが正常終了したらどうすべきでしょうか。増強したまま放置すると、使っていない余分な容量に対して追加料金が発生し続けてしまいます。

```text
Sメッセージの出力を認識（a）
  → 管理ツールでストレージを一時的に増強してHバッチを完走させる
  → Hバッチが正常終了した時点で、増強した容量を元の契約サイズへ戻す
```

したがって、Hバッチ正常終了時に行う実施内容は「**増強したストレージの容量を元に戻す。**」（20字以内）、その理由は「**クラウド利用料が加算されるから**」（20字以内）となります。「必要な業務データを削除する」のではなく、「一時的に広げたストレージの契約枠（容量）を管理ツールで元に戻す」操作である点を押さえましょう。

## 将来の需要を見直してから、契約と増強方法を計画する

### 設問2(3) b｜需要予測に基づく、リソース使用量の見積りを見直す

A社では当初、「3年後に売上が2割増加する」という従来の見込みを基にリソース使用量を見積もっていました。ところが今月の経営会議で「新製品の販売時期を前倒し（早期化）する」ことが決まり、販売管理サービスの利用時期やデータ量の増え方が当初の想定と変わることになりました。

事業の予定が変われば、当然システムにかかる負荷の見通しも変わります。そのため、Fクラウドのどの契約モデル（F1〜F5）を選ぶかを決める前に、まず前提となる「**需要予測に基づくリソースの使用量の見積り**」（b）を見直す必要があります。

### 設問2(4) c｜見積りと目標値を基に、キャパシティ計画を策定する

見直した「リソース使用量の見積り（b）」と「サービスレベル目標値（SLA）」を照らし合わせ、将来にわたって必要な容量・能力をどの契約モデルと増強方法でまかなうかをまとめた計画を**キャパシティ計画**といいます。したがって、cには「**キャパシティ計画**」が入ります。

```text
新製品の販売早期化（事業計画の変化）
  → サービスの需要予測を更新
  → 「需要予測に基づくリソースの使用量の見積り」を見直す【b】
  → サービスレベル目標値と照らし合わせる
  → 契約モデルや増強方法を定める「キャパシティ計画」を策定する【c】
```

## この大問から持ち帰ること

- **システム負荷と業務締切の連鎖**：バッチ処理の遅れが他部門のオンライン処理や後続業務の締切（13時30分の生産計画データ連携など）にどう影響するかを時系列でたどる。
- **警告と例外の使い分け**：単発なら定型対処で済む「警告」も、複数回重なってサービス品質低下につながる場合は「例外」としてインシデント管理を発動させる。
- **クラウドの弾力性とコスト管理**：クラウドでは「いつ増強するか」だけでなく、「処理が終わったらすぐ元に戻して追加費用を抑えること」までセットで設計する。
- **キャパシティ計画の順序**：「事業計画の変化 → 需要予測 → リソース使用量の見積り → キャパシティ計画」という上流からの順序を押さえる。

余裕があれば、「クラウドなら足りなくなったときにいつでも容量を増やせるのに、なぜ事前のキャパシティ計画が必要なのか？」を考えてみてください。「行き当たりばったりで増強を繰り返すと追加料金が膨らんだり、いざというとき目標の応答時間を守れなかったりするため、あらかじめ需要を見積もって最適な基本契約モデルと増強ルールを決めておく必要があるから」と説明できれば、キャパシティ管理の本質をしっかり理解できています。
