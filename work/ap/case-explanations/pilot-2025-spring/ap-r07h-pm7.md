# 問7 電動キックボードのシェアリングシステム

## この問題は、何を考える問題だった？

電動キックボードを、スマホで借りて走行し、決められた場所へ返却するシステムを作ります。車体のモーターやロック、センサーなどを制御するためのソフトウェアが、組込みシステムの題材です。

この大問では、**利用者の操作を、車体の状態・タスク間の情報・機器間の通信へ置き換える**ことを考えます。「走っているから走行中だろう」と日常の言葉だけで判断せず、本文が決めた状態の意味を使うのが大切です。

前半では状態の変化を読み、次に各処理へ必要な情報を渡し、最後に通信と処理にかかる時間を求めます。同じ仕様を、三つの角度から確かめる問題です。

## 車体・スマホ・サーバを分けて読む

利用者が使うアプリはスマホ上にあります。スマホは、近くの車体とはBLE（Bluetooth Low Energy）という近距離無線で、管理サーバとはインターネットで通信します。

```text
電動キックボード ← BLE → スマホのアプリ ← インターネット → 管理サーバ
```

この問題のメッセージは、相手へ送る指示や結果などのひとまとまりの情報です。車輪を実際にロック・解除するのは車体で、利用者や予約した返却ポートなどを管理するのはサーバです。アプリが両者の間でやり取りをつなぎます。

さらに、車体の制御部では、複数のタスクに仕事を分けています。タスクは、状態管理、速度の計測、表示などを担当する処理の単位です。リアルタイムOSは、こうした処理を必要なタイミングで実行するために使います。ここではOSの内部方式を推測せず、表4で各タスクが何を受け取り、何をするかを読みます。

## 状態は、操作や条件によって変わる

図3の箱が状態、矢印が状態の変化を表します。矢印には、変わるための操作や速度条件があります。

| 状態 | この問題での意味 |
| --- | --- |
| 待機中 | 貸出し前など、車輪をロックしている |
| 停止中 | 貸出し後、ロックは解除されているが動き始めていないなどの状態 |
| 走行準備 | 手押しなどで0.3km／時以上になった状態 |
| 加速可能 | 手押しなどで3km／時以上になり、アクセルで加速へ進める状態 |
| 走行中 | アクセルを押して、モーターのトルク発生を制御する状態 |

トルクは回転させる力に関わる量です。ここでは、モーターが車体を加速させるために発生するものと捉えましょう。速度と同じ値ではありません。

### 設問1｜アクセルを戻すと、加速可能へ戻る

手押しで走行準備から加速可能へ進み、アクセルを押すと走行中になります。そこからアクセルを戻して惰性で進むと、図3では加速可能へ戻ります。

```text
走行準備 → 加速可能 → 走行中 → 加速可能
```

したがって答えは「ウ」です。アクセルを戻すだけで、さらに走行準備まで戻る矢印はありません。**物理的に車体が動いているかと、ソフトウェアがどの状態を持つかは別**なので、状態図の矢印を一つずつたどります。

### 設問2(1) a｜停止へ戻す条件は、低速の継続

動作概要には、走行準備・加速可能・走行中のいずれからも、「0.1km／時未満が一定時間継続」すると停止中になるとあります。図3で共通のaが付いた矢印は、この条件に対応します。

「0.1未満」と「0.3以上」は、別の遷移の条件です。また、一瞬0.1未満になっただけではなく、一定時間続く必要があります。本文はその秒数を指定していないので、10秒などを補いません。

0.1km／時ちょうどは「未満」に含まれず、0.3km／時ちょうどは「以上」に含まれます。条件に使われている境界の言葉も、そのまま保持しましょう。

### 設問2(2)｜返却場所を確認するため、位置情報を使う

車体IDと利用者IDで、どの車体を誰が利用しているかは識別できます。しかし、返却できるのは予約した返却ポートです。場所を確かめるため、返却要求に含まれる「位置情報」が必要です。

この位置情報はスマホのアプリが使う情報です。本問ではスマホと車体のBLE通信は安定していると仮定されていますが、それだけで、予約したポートにいるとまでは分かりません。通信できることと、返却場所の条件を満たすことを分けます。

## タスクへは、その判断に必要な情報を渡す

### 設問3(1) b｜ロックを解除した直後は、停止中

待機中の車体へ車輪ロック解除指示が届くと、ロックを解除して停止中へ進みます。したがってbは、図3の字句で「停止中」です。

まだ手押しで速度が上がったとは書かれていません。貸出しができたことを、走行中や加速可能になったことと取り違えないようにします。

### 設問3(1) d｜現在速度を必要とするメインへ通知する

速度計測タスクが測った現在速度は、モーター制御だけでなく、状態の遷移を判断するためにも必要です。状態管理を担当するのはメインタスクなので、dは「メイン」です。

表4ではメインから表示タスクへ現在速度と電池残量を通知します。画面で速度を表示するからといって、dを「表示」とはしません。**受け渡しの経路を、表4の担当に沿って読む**必要があります。

### 設問3(2) c｜モーターには、速度や操作量に加えて状態も必要

モータータスクは、アクセル操作量と現在速度だけでなく、トルクを発生させてよい状態かも知る必要があります。例えば、貸出し前の待機中と、走行中では扱いが異なります。

状態を管理するメインから渡すcは、「電動KBの状態」です。必要な情報の出所を並べると、役割が分かります。

| 情報の出所 | モータータスクへ渡す情報 |
| --- | --- |
| メイン | 電動KBの状態 |
| 速度計測 | 現在速度 |
| アクセル | アクセルの操作量 |

「モーターへ何か通知する」とだけ読まず、**何を判断するための、どんな情報が不足しているか**を、制御の仕様から考えましょう。

## メッセージは、送信元と送信先を付けて並べる

### 設問4(1) e・f・g｜貸出しの許可から、解除結果の報告まで

管理サーバが貸出しを指示しても、車体のロックが実際に解除されたことを確認し、サーバへ結果を戻す必要があります。表3のメッセージを、通信相手と一緒に並べます。

| 順序 | 送信元→送信先 | メッセージ |
| --- | --- | --- |
| 1 | アプリ→管理サーバ | 貸出し要求 |
| 2 | 管理サーバ→アプリ | 貸出し指示 |
| 3 | アプリ→車体 | 車輪ロック解除指示：e＝エ |
| 4 | 車体→アプリ | 車輪ロック解除応答：f＝オ |
| 5 | アプリ→管理サーバ | 貸出し応答：g＝ア |

ここではロック解除が失敗せず、正常に進むという条件です。ロックする指示と解除する指示、車体からの応答とサーバへ返す応答を、名前の似ているものとして混同しないようにします。

## 通信時間は、聞かれた区間の始まりと終わりを決める

設問4(2)は返却時の話に切り替わります。今度はロックに一度失敗し、再送して二度目で成功します。

この設問では、指定された通信・ロック処理・再送待ち以外の、管理サーバ・アプリ・車体の処理時間は無視できる条件です。その条件に従い、区間内の指定された時間を足します。

200ミリ秒は0.200秒、10ミリ秒は0.010秒です。1秒＝1,000ミリ秒なので、割る数は1,000になります。足し算の前に単位を秒へそろえましょう。

### 設問4(2) ①｜返却要求と返却指示の二つの通信を数える

区間①は、アプリで返却を選択してから、管理サーバの返却指示を受信するまでです。アプリとサーバの間で、行きと帰りの二つのメッセージが必要です。

```text
アプリ → 管理サーバ：返却要求　0.200秒
管理サーバ → アプリ：返却指示　0.200秒
合計：0.200 ＋ 0.200 ＝ 0.400秒 → 答案は0.40
```

まだ車体へロック指示を送る前なので、車体でのロック処理1秒は区間①には入りません。

### 設問4(2) ②｜失敗・再送待ち・成功を、順に足す

区間②は、アプリが返却指示を受信した後から、成功の車輪ロック応答を受信するまでです。通信はアプリと車体の間です。

| 順序 | 処理・通信 | 所要時間 |
| --- | --- | --- |
| 1 | アプリ→車体：車輪ロック指示 | 0.010秒 |
| 2 | 車体：ロック処理に失敗 | 1.000秒 |
| 3 | 車体→アプリ：失敗の車輪ロック応答 | 0.010秒 |
| 4 | 再送まで待つ | 0.500秒 |
| 5 | アプリ→車体：車輪ロック指示を再送 | 0.010秒 |
| 6 | 車体：ロック処理に成功 | 1.000秒 |
| 7 | 車体→アプリ：成功の車輪ロック応答 | 0.010秒 |

```text
合計：0.010 ＋ 1.000 ＋ 0.010 ＋ 0.500 ＋ 0.010 ＋ 1.000 ＋ 0.010
    ＝ 2.540秒 → 答案は2.54
```

成功の応答を受信した後に、アプリから管理サーバへ返却応答を送りますが、それは区間②の終わりより後です。その200ミリ秒は足しません。逆に、失敗した一度目の処理時間と応答時間は、区間内なので省略できません。

答えは、小数第3位を四捨五入し、小数第2位まで示す指定です。①は0.4ではなく「0.40」、②は「2.54」と、数値だけでなく表記もそろえます。メインタスクの10秒間隔の現在情報送信は、このロック指示・応答の通信時間に追加する指定ではありません。

## この大問から持ち帰ること

- 状態図は、日常の印象ではなく、矢印の条件と操作を順にたどる。
- タスク間では、担当する判断と、必要な情報の出所を対応させる。
- 通信では、指示・応答の名前と、送信元・送信先を一組で確認する。
- 時間計算では、対象区間・再試行・待ち時間・単位・丸め指定をそろえる。

余裕があれば、「区間②に管理サーバへ送る返却応答の200ミリ秒を入れない理由」を説明してみましょう。「問われている終点は、アプリが車体から成功の応答を受信した時点で、サーバへの報告はその後だから」と説明できれば、時間計算の範囲を正しくつかめています。
