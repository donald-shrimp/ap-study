# 問7 電動キックボードのシェアリングシステム

## この問題は、何を考える問題だった？

スマートフォンのアプリを使って電動キックボード（電動KB）を借り、走行後に予約したポート（駐輪場所）へ返却するシェアリングシステムが題材です。車体のモーターや車輪ロック、速度センサーなどを制御するソフトウェアは、典型的な**組込みシステム**です。

この大問では、利用者の「借りる・走る・返す」という一連の操作を、次の3つの視点からプログラムと通信の仕様に落とし込みます。

- **状態遷移**：車体が今どの「状態」にあり、どんな操作や速度条件で次の状態へ移るか
- **タスク間の情報連携**：車体内部の各処理（タスク）が、判断に必要なデータをどこから受け取るか
- **機器間の通信と所要時間**：スマホ・サーバ・車体の間でどの順番でメッセージをやり取りし、何秒かかるか

「動いているから走行中だろう」といった日常の感覚で判断せず、**本文と図表で定義されたルールを一つずつ正確にたどる**のが、組込みシステムの問題を確実に解くコツです。

## 車体・スマホ・サーバの役割分担を整理する

まず、登場する3つの機器がどのようにつながっているかを押さえましょう。利用者のスマホにあるアプリは、近くの電動KB本体とは **BLE**（Bluetooth Low Energy：省電力の近距離無線通信）で通信し、遠くの管理サーバとはインターネット経由で通信します。

```text
電動キックボード（車体） ← BLE → スマホ（アプリ） ← インターネット → 管理サーバ
```

車輪のロックを物理的にかけたり外したりするのは「車体」の仕事であり、利用者の認証や返却ポートの予約管理を行うのは「管理サーバ」の仕事です。そして、車体と管理サーバの間に入って指示や応答の**メッセージ**を仲介するのが「スマホのアプリ」です。

さらに、車体の制御部の中では、処理をいくつかの**タスク**（役割ごとの処理単位）に分けて動かしています。誰が状態を管理し、誰が速度を測り、誰がモーターを動かすのかを、表4の役割分担に沿って読み解いていきます。

## 状態は、操作や条件によって移り変わる

図3の状態遷移図では、四角い箱が車体の「状態」、矢印が「状態の移り変わり（遷移）」とその条件を表しています。各状態の意味を整理しておきましょう。

| 状態名 | このシステムにおける定義 |
| --- | --- |
| **待機中** | 貸出し前（または返却後）で、車輪がロックされている状態 |
| **停止中** | 貸出し後に車輪ロックが解除されたが、まだ走り出していない（または止まった）状態 |
| **走行準備** | 地面を蹴る（手押し）などして、速度が **0.3km／時以上** になった状態 |
| **加速可能** | 手押しなどで速度が **3km／時以上** になり、アクセル操作を受け付けられる状態 |
| **走行中** | アクセルを押して、モーターの**トルク**（車輪を回転させる駆動力）を発生させている状態 |

### 設問1｜アクセルを戻すと、加速可能へ戻る

停止中から手押しを始めて「走行準備」→「加速可能」へと進み、アクセルを押すと「走行中」になります。では、そこから**アクセルを戻して惰性で進んでいるとき**、車体はどの状態になるでしょうか。

図3の「走行中」から出る矢印をたどると、「アクセルを戻す」という操作の矢印は「**加速可能**」へ向かっています。

```text
走行準備 → 加速可能 →（アクセルを押す）→ 走行中 →（アクセルを戻す）→ 加速可能
```

したがって答えは「**ウ：加速可能**」です。惰性で走っているからといって「走行中」のままでもなければ、一気に「走行準備」まで戻る矢印もありません。**物理的にタイヤが回っているかどうかと、ソフトウェア上の状態名は別物**なので、必ず図3の矢印の向きを確認して答えましょう。

### 設問2(1) a｜停止中へ戻す条件は「低速の一定時間継続」

本文の動作概要には、「走行準備・加速可能・走行中のいずれの状態からも、**0.1km／時未満が一定時間継続**すると停止中に遷移する」と書かれています。図3でこれら3つの状態から「停止中」へ向かう矢印に共通して付いている条件aは、まさにこの記述に対応します。

したがって、aに入る条件は「**0.1km／時未満が一定時間継続**」です。

ここで大切なのは、次の2点です。
1. **境界の表現（未満／以上）を正確に保つ**：「0.1km／時以下」と書いてしまうと0.1km／時ちょうどを含んでしまい、原文の「未満」と意味が変わってしまいます。
2. **「一定時間継続」を省かない**：一瞬だけ0.1km／時を下回っただけでは遷移せず、一定時間続くことが条件です。

### 設問2(2)｜返却場所を確認するため、位置情報を使う

利用者が電動KBを返却できるのは、**あらかじめ予約した返却ポートの中**にいるときだけです。

返却要求メッセージに含まれる「車体ID」と「利用者ID」だけでは、「誰がどの車体を返そうとしているか」は分かっても、「いま予約した返却ポートの場所にいるかどうか」は分かりません。そのため、スマホのアプリが取得して送信する「**位置情報**」が必要になります。

なお、スマホと車体がBLEで通信できているからといって、正しい返却ポートにいる証明にはなりません（利用者がポート以外の場所で車体のすぐ横に立っていてもBLE通信はできてしまうためです）。「車体の近くにいること」と「指定の返却場所にいること」を分けて考えましょう。

## タスクへは、その判断に必要な情報を渡す

### 設問3(1) b｜ロックを解除した直後の状態は「停止中」

「待機中（ロック状態）」の車体がアプリから車輪ロック解除指示を受け取ると、ロックを解除して次の状態へ移ります。図3の矢印のとおり、ロック解除直後に移る状態bは「**停止中**」です。

この時点ではまだ車輪のロックが外れただけで、手押しもアクセル操作も始まっていません。貸出しが始まったからといって「走行準備」や「走行中」と早合点しないよう注意しましょう。

### 設問3(1) d｜現在速度を必要とするメインへ通知する

速度計測タスクが測った「現在速度」は、モーターの制御だけでなく、先ほど見た「0.3km／時以上」「3km／時以上」「0.1km／時未満が一定時間継続」といった**状態遷移の判定**にも不可欠です。

車体の状態管理を担当しているのは**メインタスク**なので、速度計測タスクが現在速度を通知する相手dは「**メイン**」となります。なお、画面に速度を表示する「表示タスク」へは、表4にあるとおりメインタスクから現在速度と電池残量をまとめて通知する仕組みになっているため、dに「表示」を入れないようにしましょう。

### 設問3(2) c｜モーターには、速度や操作量に加えて状態も必要

モータータスクは、アクセルの操作量と現在速度に応じてモーターのトルクを制御しますが、それだけでは「いま本当にモーターを回してよい場面か」を判断できません。たとえば、まだ3km／時に達していないときや待機中にアクセルが押されても、モーターを回しては危険です。

そこで、状態を管理しているメインタスクからモータータスクへ「いま車体がどの状態にあるか」を伝える必要があります。したがって、cには「**電動KBの状態**」が入ります。

| 情報の送り手 | モータータスクが受け取る情報 | 何のために使うか |
| --- | --- | --- |
| **メインタスク** | **電動KBの状態（c）** | モーターを駆動してよい状態（走行中）かどうかを判断する |
| **速度計測タスク** | 現在速度 | 現在の速度に応じた適切なトルクを計算する |
| **アクセルタスク** | アクセルの操作量 | 利用者がどれだけ加速しようとしているかを知る |

## メッセージは、送信元と送信先を付けて並べる

### 設問4(1) e・f・g｜貸出しの許可から、解除結果の報告まで

設問4(1)は、貸出し時のメッセージのやり取りを順番に並べる問題です。管理サーバが「貸し出してよい」と指示を出したあと、アプリが車体のロックを解除させ、その結果を管理サーバへ報告して初めて貸出しが完了します。表3のメッセージ一覧から、**「誰から誰へ送る、何のメッセージか」**を照合して並べましょう。

| 順序 | 送信元 → 送信先 | やり取りするメッセージ |
| --- | --- | --- |
| 1 | アプリ → 管理サーバ | 貸出し要求 |
| 2 | 管理サーバ → アプリ | 貸出し指示 |
| 3 | アプリ → 車体（電動KB） | **車輪ロック解除指示（e ＝ エ）** |
| 4 | 車体（電動KB） → アプリ | **車輪ロック解除応答（f ＝ オ）** |
| 5 | アプリ → 管理サーバ | **貸出し応答（g ＝ ア）** |

「ロック指示（施錠）」と「ロック**解除**指示（解錠）」、また車体からアプリへ返す「車輪ロック解除応答」とアプリから管理サーバへ返す「貸出し応答」は名前が似ているので、必ず表3の送信元・送信先とセットで確認しましょう。

## 通信時間は、聞かれた区間の始まりと終わりを決める

設問4(2)は、返却時の所要時間を計算する問題です。ここでは**「1回目の車輪ロック処理に失敗し、0.5秒待って再送し、2回目で成功した」**という場面を計算します。

計算に入る前に、本文の前提条件と単位を確認しておきましょう。
- 指定された通信時間・ロック処理時間・再送待ち時間以外の処理時間は無視できる。
- 1秒 ＝ 1,000ミリ秒 なので、**200ミリ秒 ＝ 0.20秒**、**10ミリ秒 ＝ 0.01秒** に直して計算する。
- 解答は小数第3位を四捨五入し、**小数第2位まで**（例：0.4 ではなく 0.40）記述する。

### 設問4(2) ①｜返却要求と返却指示の二つの通信を数える

区間①は、「利用者がアプリで返却を選択してから、アプリが管理サーバから返却指示を受信するまで」の時間です。この区間で行われるのは、アプリと管理サーバの間の1往復（行きと帰り）の通信だけです。

```text
1. アプリ → 管理サーバ（返却要求）：200ミリ秒 ＝ 0.20秒
2. 管理サーバ → アプリ（返却指示）：200ミリ秒 ＝ 0.20秒
--------------------------------------------------------
合計：0.20秒 ＋ 0.20秒 ＝ 0.40秒（解答：0.40）
```

この時点ではまだ車体へロック指示を送っていないため、車体でのロック処理時間（1秒）は区間①には含まれません。

### 設問4(2) ②｜失敗・再送待ち・成功を、順に足す

区間②は、「アプリが返却指示を受信した直後から、車体から**成功の**車輪ロック応答を受信するまで」の時間です。ここでの通信はすべてアプリと車体の間（BLE通信：片道10ミリ秒＝0.01秒）で行われます。1回目の失敗から2回目の成功までを順番に書き出して足し合わせましょう。

| 順序 | 発生する通信・処理 | 所要時間 |
| --- | --- | --- |
| 1 | アプリ → 車体：1回目の車輪ロック指示（BLE通信） | 0.01秒（10ミリ秒） |
| 2 | 車体：1回目のロック処理（**失敗**） | 1.00秒 |
| 3 | 車体 → アプリ：失敗の車輪ロック応答（BLE通信） | 0.01秒（10ミリ秒） |
| 4 | アプリ：再送までの待ち時間 | 0.50秒 |
| 5 | アプリ → 車体：2回目の車輪ロック指示を再送（BLE通信） | 0.01秒（10ミリ秒） |
| 6 | 車体：2回目のロック処理（**成功**） | 1.00秒 |
| 7 | 車体 → アプリ：成功の車輪ロック応答（BLE通信） | 0.01秒（10ミリ秒） |

```text
合計：0.01 ＋ 1.00 ＋ 0.01 ＋ 0.50 ＋ 0.01 ＋ 1.00 ＋ 0.01 ＝ 2.54秒（解答：2.54）
```

ここで引っかかりやすいポイントが2つあります。
- **1回目の失敗にかかった時間も忘れずに含める**：失敗したときのロック処理（1.00秒）と失敗応答の通信（0.01秒）、そして再送待ち（0.50秒）もすべて区間②の出来事なので加算が必要です。
- **最後の「管理サーバへの返却応答（0.20秒）」は含めない**：区間②の終点は「アプリが車体から成功の車輪ロック応答を受信した時点」です。そのあとにアプリから管理サーバへ送る返却応答は区間②の外なので足しません。

## この大問から持ち帰ること

- **状態遷移図の読み方**：日常の言葉のイメージではなく、図の矢印に書かれたイベントと数値条件（以上・未満・継続）を忠実にたどる。
- **タスク間のデータ受け渡し**：「どのタスクが何の判断を担当しているか」から、必要なデータとその送り手を特定する。
- **メッセージと時間計算**：誰と誰の通信かを確認し、問われている区間の「始点」と「終点」の間に起きた通信・処理・待ち時間だけを単位をそろえて合計する。

余裕があれば、「区間②の計算に、なぜ管理サーバへ送る『返却応答（200ミリ秒）』を足さないのか？」を説明してみてください。「設問で問われている区間②のゴールは『アプリが車体から成功の応答を受け取った瞬間』であり、管理サーバへの完了報告はその後に起きる処理だから」と説明できれば、区間の切り取り方は完璧です。
