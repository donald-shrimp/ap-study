# 問3 スライドパズルを解くプログラム

## この問題は、何を考える問題だった？

スライドパズルは、空いているマス（空白マス）へ上下左右の隣にある駒をスライドさせ、数字を順番どおりに並べるパズルです。この大問では、開始盤面から完成形（ゴール）へ至る手順のうち、**駒を動かす回数が最も少ない手順（最短手数）**をプログラムで見つけ出します。

ここで求められるのは、パズルを頭の中で解くことではありません。**「次に調べる盤面をどの順番で取り出すか」「空白マスを1回動かした新しい盤面をどうやって作るか」**という考え方を、データ構造とプログラムの命令に落とし込むことです。

設問1で「盤面の動きを二次元配列でどう表すか」を具体例で確認し、設問2でそれを幅優先探索のプログラムとして完成させる構成になっています。

## 最少の回数を探すため、近い盤面から順に調べる

パズルの1つの盤面を「点（ノード）」、1回の移動で移り変われる盤面どうしのつながりを「線（エッジ）」とみなすと、盤面の移り変わりは点と線のつながり（**グラフ**）として表せます。

最短手数を求めるために本問で使うのが**幅優先探索**です。幅優先探索では、開始盤面から「1手で到達できる盤面」をすべて調べ、次に「2手で到達できる盤面」をすべて調べ、その次に「3手で到達できる盤面」……というように、開始地点から近い順に網羅して調べます。手数の少ない順に漏れなく調べるため、**最初にゴールと一致した時点の手数が必ず最短手数になる**という性質があります。

この「見つけた順（浅い順）に調べる」仕組みを実現するデータ構造が**キュー（待ち行列）**です。先に入れたデータを先に取り出す（先入れ先出し：FIFO）入れ物で、新しく作った一手先の盤面を常に末尾へ追加していくことで、先に待っていた浅い手数の盤面から順番に処理できます。

架空の盤面名A〜Dを使って、キューの中身がどう移り変わるかを見てみましょう。

```text
初期状態：              [開始盤面]
開始盤面を取り出す：    []
1手先のA・Bを末尾へ：   [A, B]
先頭のAを取り出す：     [B]
Aの1手先C・Dを末尾へ：  [B, C, D]
→ 次に取り出されるのは先頭のB（2手目のCやDより先に、同じ1手目のBを調べる）
```

## 設問1｜空白と駒を一回交換し、行ごとの配列にする

プログラム上で盤面を扱うため、各行を配列にし、それを上から順に並べた二次元配列で盤面を表現します。3×3の盤面では、数字の1〜8が駒を表し、**空白マスは「9」**で表すルールです（一辺がNマスの場合は、プログラム31行目のとおり board_size × board_size が空白の値になります）。

図2の開始盤面では、空白「9」は3行2列にあります。設問1で問われている盤面②は、その1つ上（2行2列）にある駒「5」を空白マスへ動かした状態です。「駒5が下へ動き、代わりに空白9が上へ移動した」と考えると位置を追いやすくなります。

```text
開始盤面             ②の盤面
8 6 7                8 6 7
2 5 4       →        2 9 4
3 9 1                3 5 1
```

入れ替わるのは2行2列と3行2列の2か所だけで、他の数字は一切変わりません。上の行から順に配列の形式で書き並べると、答えは次のようになります。

```text
{{8, 6, 7}, {2, 9, 4}, {3, 5, 1}}
```

## 次に調べる盤面と、既に見つけた盤面を分けて持つ

図7のプログラムを読む前に、登場する主な変数が「何のデータを持っていて、何のために使うのか」を整理しておきましょう。

| 変数名 | 中に入っているデータ | 使う目的 |
| --- | --- | --- |
| **explore_queue** | 次に調べる BoardState（状態全体）への参照 | 手数の浅い盤面から順番に取り出して探索する |
| **check_list** | 既に発見・登録した board（盤面配列）のリスト | 同じ盤面を何度も重複して探索するのを防ぐ |
| **state** | キューから今取り出した、動かす前の状態 | 1手進めた次の状態を作るための元データにする |
| **new_state** | state から空白を1マス動かして作った新しい状態 | ゴール判定を行い、未探索なら次の探索対象に登録する |

BoardState は、盤面の二次元配列 board だけでなく、空白マスの現在位置 space と、1手前の状態を指し示す prev をセットで持っています。この prev をゴールから逆順にたどることで、開始盤面からどう動かしたかの手順を復元できる仕組みです。

### 設問2 ア｜まだ調べる盤面がある間、繰り返す

20行目の while 文は、「空欄アが false と等しい間、探索を繰り返す」というループ条件です。

図5の説明を見ると、isEmpty() メソッドは「キューが空なら true、空でなければ false」を返します。つまり、**explore_queue.isEmpty()** が false である間は「まだキューの中に調べるべき盤面が残っている」ことを意味します。したがって、アには「**explore_queue.isEmpty()**」が入ります。

なお、check_list は「これまでに見つけた盤面の記録帳」なので、探索が進むほど中身が増えていき、空にはなりません。「これから調べる待ち行列（explore_queue）」と「調べた履歴（check_list）」を取り違えないようにしましょう。

### 設問2 イ｜先頭を取り出し、キューから除く

21行目では、次に調べる状態を explore_queue の先頭から1つ取り出して state に入れます。図5のメソッド一覧のうち、先頭の要素を取り出して返し、かつキューからその要素を削除するのは **poll()** です。したがって、イは「**poll()**」を選びます。

選択肢にある peek() も先頭の要素を返しますが、**キューから要素を削除しません**。もしここで peek() を使ってしまうと、先頭の盤面がいつまでもキューに居座り続け、同じ盤面を無限に調べ続けてしまいます。メソッドを選ぶときは「どんな値を返すか」だけでなく、**「入れ物の中身がどう変化するか」**まで確認するのが鉄則です。

## 空白の移動は、行と列の変化に分ける

プログラムでは、空白マスの位置を space[1]（行番号）と space[2]（列番号）で表しています。要素番号は1から始まり、行番号は下へ行くほど増え、列番号は右へ行くほど増えます。

配列 direction には、空白マスを上下左右の4方向へ1マス動かすときの「行の増減」と「列の増減」が格納されています。ループ変数 i（1〜4）で4方向を順番に試します。

| 方向番号 i | 行の増減 direction[i][1] | 列の増減 direction[i][2] | 空白マスの動き |
| --- | --- | --- | --- |
| 1 | 1 | 0 | 下へ1マス |
| 2 | 0 | -1 | 左へ1マス |
| 3 | -1 | 0 | 上へ1マス |
| 4 | 0 | 1 | 右へ1マス |

### 設問2 ウ｜移動後の行番号を求める

23・24・28行目では、現在の空白の行番号 state.space[1] に移動分の増減を足して、移動後の行番号を計算しています。各方向の第1要素が行の増減を表しているため、ウには「**direction[i][1]**」が入ります。

たとえば、開始盤面のように空白が3行2列にあり、上方向（i = 3）を試す場合、移動後の行番号は 3 + (-1) = 2（2行目）となります。

### 設問2 オ｜移動後の列番号を求める

同様に、25・26・29行目は現在の空白の列番号 state.space[2] に列の増減を足す処理です。各方向の第2要素を使うため、オには「**direction[i][2]**」が入ります。

上方向（i = 3）なら列の増減は 0 なので、移動後の列番号は 2 + 0 = 2（2列目）のままです。行（第1要素）と列（第2要素）を逆にすると移動方向が入れ替わってしまうため、添字の 1 と 2 を丁寧に対応させましょう。

### 設問2 エ｜移動先が盤面の中にあるか確認する

空白マスが盤面の端にあるとき、外に向かって動かそうとすると盤面からはみ出してしまいます。たとえば最上段（1行目）からさらに上へ動くと行番号は 0 になり、最下段から下へ動くと盤面のサイズを超えてしまいます。

そこで23〜26行目の if 文では、「移動後の行番号と列番号が、ともに 1 以上、かつ盤面の一辺のマス数以下か」をチェックしています。盤面の一辺のマス数を表す変数は **board_size** なので、エには「**board_size**」が入ります。

```text
3×3の盤面（board_size = 3）で、空白が左上（1行1列）にある場合：
・下へ移動：(2, 1) → 行・列ともに 1〜3 の範囲内なので移動できる
・左へ移動：(1, 0) → 列が 0 になるため盤面外（除外）
・上へ移動：(0, 1) → 行が 0 になるため盤面外（除外）
・右へ移動：(1, 2) → 行・列ともに 1〜3 の範囲内なので移動できる
```

「試す方向が4つだから4」と混同しないよう、「方向の個数（4）」と「盤面の一辺の長さ（board_size）」を明確に区別しましょう。

## 作った状態を、判定してから登録する

移動先が盤面の中にあれば、27行目で新しい状態 new_state を作り、28〜32行目で空白と駒を入れ替えます。そして最後に、「ゴールに到達したか」と「すでに調べた（または順番待ちしている）盤面と同じではないか」を確認します。

### 設問2 カ｜動かした後の盤面をゴールと比較する

33行目は、完成した盤面に到達したかを調べる条件式です。表2にある関数 checkGoal は、引数として渡された2つの盤面配列が一致していれば true を返します。

いま比較したいのは、1手動かして新しく作った盤面 new_state.board と、完成形の盤面 goal_board です。したがって、カには「**checkGoal(new_state.board, goal_board)**」が入ります。動かす前の state.board を渡してしまうと新しい盤面を判定できないため、**「いつの時点の、どのデータを渡すか」**に注意して選びます。

### 設問2 キ｜探索用のキューには、状態全体を追加する

ゴールにまだ到達しておらず、かつ37行目で check_list にも未登録の盤面だと分かったら、次の探索候補として登録します。

38行目の explore_queue が保持するのは、盤面・空白位置・1手前の参照をまとめた **BoardState への参照**です。そのため、キには状態全体をそのまま渡す「**add(new_state)**」が入ります。

### 設問2 ク｜重複確認用のリストには、盤面だけを追加する

続く39行目の check_list が保持するのは、図6のとおり **board（盤面の二次元配列）**です。したがって、クには盤面配列だけを取り出して渡す「**add(new_state.board)**」が入ります。同じ add メソッドでも、入れ物によって渡すデータの型（new_state か new_state.board か）が異なる点が見どころです。

スライドパズルでは「駒を右に動かして、すぐ左に戻す」のように、何手か動かすと以前とまったく同じ盤面に戻ってしまうことがよくあります。キューに追加するタイミングで check_list にも盤面を登録しておけば、すでに探索した盤面だけでなく、**いまキューの中で順番待ちしている盤面との重複登録**も確実に防ぐことができます。

## この大問から持ち帰ること

- **幅優先探索とキュー**：先入れ先出し（FIFO）のキューを使うことで、手数の少ない盤面から順番に調べ、最短手数を見つけられる。
- **二次元配列と境界チェック**：行番号・列番号が何番から始まり、どちらへ進むと増えるかを確認する。端からはみ出さない条件は盤面サイズ（board_size）で判定する。
- **メソッドと引数の選び方**：副作用の有無（poll と peek の違い）や、渡すべきデータの時点・型（動かす前の state か動かした後の new_state か、状態全体か盤面配列 .board か）を照らし合わせる。

余裕があれば、「21行目の空欄イで、もし先頭を削除しない peek() を使ってしまったら、最初の架空例 [A, B] はどうなるか？」をたどってみてください。Aを調べてもキューの先頭にAが残り続けるため、次のループでもまたAを取り出してしまい、いつまで経ってもBへ進めないことがはっきりイメージできるはずです。
