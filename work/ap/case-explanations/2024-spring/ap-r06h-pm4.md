# CRMシステムの改修

## この問題は、何を考える問題だった？

アルミサッシの製造・販売を行うC社では、これまで社内LAN上のPCから利用していた自社開発の **CRM（Customer Relationship Management：顧客関係管理）システム** を改修し、営業担当者が外出先のスマートフォンやノートPCからも利用できるようにしようとしています。

この大問で一貫して問われているのは、**「データベース（DB）を変更せず、開発コストも抑えながら、画面性能（レスポンス・CPU負荷）と将来の拡張性を両立するには、画面描画とデータ加工をどの機器（端末・Webサーバ・AP・DB）に分担させるべきか」**というシステムアーキテクチャの設計判断です。

全体の流れは次の4ステップで進みます。
1. **初期構成案と静的ファイルの最適化（設問1）**：画面表示用の静的ファイルとデータ処理用のWeb APIを分離し、静的ファイルのサイズを小さくして受信を速める。
2. **プロトタイプ検証とボトルネックの特定（設問2）**：初期案（方式Ⓟ）でスマートフォン表示が遅くバッテリ消耗が激しい原因を、処理時間の計測結果（表1）とJSONデータ（図3）から突き止める。
3. **改善方式（方式②）の評価とレスポンス試算（設問3・設問4）**：データ加工をサーバ側へ移す方式②が優れている理由を言語化し、通信時間（空欄a）とCPU処理時間（空欄b）から3秒以内に収まるかを計算する。
4. **将来の拡張性を見据えたAP分割（設問5）**：外出先端末向けのWeb APIを専用APに配置することで、CRM以外の社内システムとも連携しやすくする。

## まず、システム構成と4つの方式（Ⓟ・①〜③）を整理しよう

設問に入る前に、図1のシステム構成における各サーバの役割と、表2で比較されている4つの方式（方式Ⓟ・方式①・方式②・方式③）の違いを整理しておきましょう。

- **Webサーバ**：画面の構造を定義する**HTML**、見た目（スタイル）を指定する**CSS**、画像、ブラウザ上で動くスクリプトなどの**静的ファイル**を配信します（PC用とスマートフォン用で個別に用意）。
- **AP（アプリケーションサーバ）**：**DB（データベースサーバ）**からデータを取得し、**JSON形式**で返す **Web API**（プログラム同士が決められた手順でデータをやり取りする窓口）を提供します。

プロトタイプ（方式Ⓟ）では「DBにある全件の日誌データをWeb APIでスマートフォンへ送り、スマートフォンのWebブラウザ内で並べ替え・抽出・文字数短縮・本人判定を行ってから描画する」仕組みをとっていましたが、性能問題が出たため、表2のとおり見直し案（方式①〜③）を比較しています。

| 方式 | データ描画の場所 | データ加工の場所 | 仕組みの特徴と評価（レスポンス／開発コスト／CPU負荷＝合計点） |
| --- | --- | --- | --- |
| **方式Ⓟ（初期案）** | Webブラウザ | Webブラウザ | 全件データを端末へ送りブラウザで加工・描画する（×／◎／×＝**3点**） |
| **方式①** | スマホアプリ | スマホアプリ | 専用スマホアプリを新規開発し、アプリ内で加工・描画する（○／△／△＝**4点**） |
| **方式②（採用案）** | **Webブラウザ** | **サーバ側（DB・AP）** | **表示に必要なデータだけを返すWeb APIを作り、ブラウザで描画する（○／○／○＝6点）** |
| **方式③** | スマホアプリ | サーバ側（DB・AP） | 方式②のWeb APIと専用スマホアプリの両方を開発する（◎／×／○＝**5点**） |

この役割分担の違いを押さえておくと、設問2〜設問4の理由と計算がすっきりとつながります。

## 設問1｜静的ファイルを小さくして受信を早める

設問1は、［Webアプリの実装方式の検討］の下線①「ユーザーインタフェースの表示速度を向上させるために，静的ファイルを最適化する」に該当するものを、解答群から**すべて**選ぶ問題です。

ここでの「**静的ファイル**」とは、リクエストのたびに営業日誌のデータから動的に組み立てられる応答データとは異なり、あらかじめWebサーバに置いて配信する画面用のファイル（HTML、CSS、スクリプト、画像など）を指します。画面の機能や必要な画質を損なわずに、ブラウザが受信するファイルサイズを小さくできる手段を選びましょう。

| 選択肢 | 判断と理由 |
| --- | --- |
| ア HTML，CSS，スクリプトなどのコードに，パイプライン処理を有効にする設定を行う。 | 不適切。パイプライン処理はCPUなどが命令を段階に分けて並行処理する高速化手法であり、静的ファイルのコードを小さくする設定ではありません |
| **イ HTML，CSS，スクリプトなどのコードに含まれる，余分な改行やコメントを削除する。** | **適切。表示や動作に影響しない改行・空白・コメントを削ることで配信ファイルサイズを削減できます（ミニファイ／Minifyと呼ばれます）** |
| ウ 画像を，BMPやTIFFなどの画像フォーマットにする。 | 不適切。BMPは基本的に非圧縮でサイズが大きく、TIFFは主に印刷や高精細保存向けの形式であり、Web配信の軽量化には向きません |
| **エ 画像を，PNGやSVGなどの画像フォーマットにする。** | **適切。PNGは画質を保って可逆圧縮でき、SVGは図形を座標や線（ベクタ形式）で軽量に表せるため、Web画面の最適化に適しています** |
| オ 全てのファイルをバイトコードに変換して圧縮する。 | 不適切。バイトコードはプログラム実行用の中間形式であり、HTMLや画像を含む全ファイルをバイトコード化してブラウザへ配ることはできません |

したがって、適切なものをすべて選ぶと答えは **イ，エ** です。

## 設問2(1)｜スマートフォンで日誌を並べ替え、加工している

設問2(1)は、［実現可能性の評価］においてプロトタイプ（方式Ⓟ）で発生した下線②「スマートフォンのCPU負荷が大きく，頻繁に使用するとバッテリの消耗が激しい」の要因として最も適切なものを解答群から選ぶ問題です。

**CPU**は、プログラムの命令を実行して計算やデータ処理を行う装置です。方式Ⓟで図2の「日誌一覧の表示画面」を表示するとき、どこでどれだけ時間が掛かっているかを表1で確認しましょう。

- **No.1（300ミリ秒）**：静的ファイル（HTML、CSS、画像、スクリプト）の受信
- **No.2（800ミリ秒）**：Web APIへのリクエストと、図3の応答データ（全件）の受信
- **No.3（1,200ミリ秒）**：Webブラウザ内で日誌データを日付の降順にソートし、表示する最大件数（4件目まで）を抽出
- **No.4（300ミリ秒）**：日誌本文が42文字を超える場合、先頭41文字＋“…”に短縮
- **No.5（200ミリ秒）**：ログインユーザー本人が作成した日誌かを判定し、“編集”ボタンを表示
- **No.6（500ミリ秒）**：Webブラウザへの画面描画

全体で 300＋800＋1,200＋300＋200＋500＝3,300ミリ秒（3.3秒）掛かっており、そのうち **No.3〜No.5の「スマートフォンのメモリ上で日誌のデータを加工する処理」だけで 1,200＋300＋200＝1,700ミリ秒** と半分以上を占めています。特にNo.3のソート・抽出だけで1,200ミリ秒を要しており、日誌件数が増えるほど端末のCPUに大きな負荷が掛かります。したがって、正解は **ウ** です。

| 選択肢 | 判断と理由 |
| --- | --- |
| ア JSON形式の応答データを送受信する処理 | No.2（800ミリ秒）の通信処理であり、端末のCPU負荷の主要因ではありません |
| イ WebブラウザにHTML，CSS，画像ファイルをレンダリングする処理 | No.6（500ミリ秒）の描画処理であり、データ量増加に伴うCPU負荷の主要因はデータ加工（No.3〜5）にあります |
| **ウ スマートフォンのメモリ上で日誌のデータを加工する処理** | **No.3〜5（合計1,700ミリ秒）のソート・抽出・文字列短縮・本人判定を端末内で行っていることがCPU負荷の主要因です** |
| エ 日誌一覧の各担当がログインユーザーか否かを判別する処理 | No.5（200ミリ秒）のみの処理であり、加工処理全体（ウ）の一部にすぎません |

## 設問2(2)｜角括弧の中は、日誌を一件ずつ並べた配列

設問2(2)は、図3（Web APIからの応答データ）のαとβにある角括弧 **［** と **］** で囲まれたデータがどのようなデータを表現しているかを、データ形式に着目し、「日誌」という単語を用いて15字以内で答える問題です。

**JSON（JavaScript Object Notation）**形式では、次の2つの括弧を使い分けてデータ構造を表します。
- **波括弧 { }（オブジェクト）**：「"項目名": 値」の組を集めて、1つのまとまり（図3では日誌1件分のデータなど）を表します。
- **角括弧 [ ]（配列）**：同じ種類のデータ要素をカンマで区切って複数件並べた「繰り返し（リスト）」を表します。

図3の構造を日誌2件の例で簡略化して示すと、次のようになっています。

```json
{
  "customer": "A設計",
  "count": 2,
  "diaries": [
    {"date": "2024-01-08", "salesperson": "A", "salesprocess": "問合せ", "diary": "仕様を確認した"},
    {"date": "2024-01-10", "salesperson": "B", "salesprocess": "見積り", "diary": "見積りを送った"}
  ]
}
```

**customer** が取引先名、**count** が日誌件数であり、αとβの角括弧 **[ ]** は **diaries** の値を囲んでいます。その中には、日付・担当者・営業プロセス・本文を1組にした「日誌1件分のデータ **{ }**」が件数分だけ繰り返し並んでいます。

したがって、「日誌」という単語を使って15字以内でまとめると次のようになります。

- **公式解答例**：「日誌の繰返しデータ」（9字）

## 設問3 理由①・②｜サーバで加工し、表示に使う分だけ送る

設問3は、表2において「方式②のレスポンスが、方式Ⓟに比べて優れていると評価した理由」を2つ挙げ、それぞれ30字以内で答える問題です。

方式Ⓟでは、表1の末尾にあるとおり「**①図3の応答データのスマートフォンへの転送処理（No.2）**」と「**②Webブラウザ内でその応答データを加工する処理（No.3〜5）**」の2箇所に多くの時間が掛かっていました。

方式②では、「リクエストのあった応答データのうち，Webブラウザに描画するデータだけを返すWeb API」を開発します。これにより、2つのボトルネックがそれぞれ次のように解消されます。

1. **理由①（データ加工場所の変更による高速化）**：
   方式Ⓟでは処理能力の低いスマートフォンのWebブラウザ内で行っていた応答データの加工処理（ソート・4件抽出・42文字短縮・本人判定）を、方式②では処理能力の高い**サーバ側（DBおよびAP）で行う**ため、加工時間が短縮されます。
   - **公式解答例（理由①）**：「応答データの加工処理をサーバ側で行うから」（20字）

2. **理由②（データ転送量の削減による通信時間短縮）**：
   方式Ⓟでは全16件・全文の日誌データをスマートフォンへ送っていましたが、方式②では画面に描画する最大4件・短縮済みのデータだけに絞って返すため、**応答データの転送量が削減され**、送受信時間が短縮されます。
   - **公式解答例（理由②）**：「応答データの転送量が削減されるから」（17字）

（なお、理由①と理由②は順不同です。片方だけでなく「サーバ側での加工」と「転送量の削減」の両面を書き分けましょう。）

## 設問4 a｜応答データが4分の1なら、転送時間は200ミリ秒

設問4は、［レスポンス時間の試算］における空欄a（方式②でのNo.2の所要時間）と空欄b（方式②でのNo.3〜No.5の処理時間の合計）を求める計算問題です。

まず空欄a（No.2：Web APIの要求及び応答データの送受信時間）を計算しましょう。
- 表1より、方式ⓅにおけるNo.2の所要時間は **800ミリ秒** です。
- 試算の前提条件として、「方式②のWeb APIからの応答データのサイズは，図3のデータのサイズの**4分の1**になり，サーバ側でのデータ転送には時間を要しないものと仮定する」とあります。

応答データのサイズが4分の1になれば、送受信に掛かる時間も4分の1になるため、計算式は `800÷4＝200` ミリ秒となります。したがって、空欄aの答えは **200** です。

- **公式解答例**：「200」

## 設問4 b｜同じ処理なら、CPU能力が高いほど短時間で終わる

続いて空欄b（方式②でのNo.3〜No.5の処理時間の合計）を計算しましょう。

**MIPS（Million Instructions Per Second）**は、CPUが1秒間に実行できる命令数を100万命令単位で表した性能指標です。本文の条件では「処理時間は各機器のCPU処理能力だけに依存すると仮定する」とされており、各機器のCPU処理能力は次のとおりです。
- **スマートフォン**：10,000 MIPS相当（基準）
- **DB**：40,000 MIPS相当（スマートフォンの **4倍** の処理能力 → 所要時間は **4分の1**）
- **AP**：20,000 MIPS相当（スマートフォンの **2倍** の処理能力 → 所要時間は **2分の1**）

方式②では、No.3を **DB** で行い、No.4とNo.5を **AP** で行います。それぞれの処理時間を換算して表にまとめましょう。

| No. | 方式②で加工する機器 | 元の時間（ミリ秒） | 方式②の試算（ミリ秒） |
| --- | --- | --- | --- |
| 3 | DB | 1,200 | 300 |
| 4 | AP | 300 | 150 |
| 5 | AP | 200 | 100 |

- **No.3（DBで実行）**：1,200ミリ秒 ÷ 4 ＝ **300ミリ秒**
- **No.4（APで実行）**：300ミリ秒 ÷ 2 ＝ **150ミリ秒**
- **No.5（APで実行）**：200ミリ秒 ÷ 2 ＝ **100ミリ秒**

したがって、No.3〜No.5の処理時間の合計は **300＋150＋100＝550** ミリ秒となり、空欄bの答えは **550** です。

- **公式解答例**：「550」

ちなみに、画面全体のレスポンス時間（No.1〜No.6の合計）を確かめると、**300＋200＋550＋500＝1550** ミリ秒（＝1.55秒）となり、方式Ⓟの3,300ミリ秒（3.3秒）から半減して目標値である「3秒以内」を十分に達成できることが分かります。

## 設問5｜Web APIを窓口に別の社内システムと連携できる

設問5は、［システム構成の検討］の下線③「将来的な拡張性を考慮した結果，図1のAPとは別に，スマートフォンやノートPCから呼び出されるWeb APIのためのAPを，新たに追加する構成にした」について、この「将来的な拡張性」とは何かを40字以内で答える問題です。

1. **冒頭の［Webアプリの改修方針］を確認する**：
   本文冒頭の改修方針の3つ目に、「**将来的に，CRMシステム以外の社内システムとも連携できるように拡張性をもたせる**」と明記されています。
2. **専用APを追加する構成と結び付ける**：
   外出先のスマートフォンやノートPCから呼び出される **Web API** を専用のAPへ切り出して配置しておけば、将来、外出先の画面から別システムの情報も参照・更新したくなったときに、そのWeb APIを介してCRMシステム以外の社内システムとも柔軟に連携できるようになります。

「Web APIを介して」という手段と、改修方針の「CRMシステム以外の社内システムとも連携する」という目的を組み合わせて40字以内でまとめます。

- **公式解答例**：「Web APIを介してCRMシステム以外の社内システムとも連携する拡張性」（36字）

## 次の問題でも使うこと

- Webシステムの画面表示を高速化する際は、①**静的ファイルの軽量化**（コードの改行・コメント削除＝ミニファイ、PNG/SVGなど適切な画像形式の選択）、②**通信データ量の削減**（表示に必要な件数・項目だけをWeb APIで返す）、③**データ加工処理のサーバ側（DB・AP）への移管**の3つの切り口で検討する。
- **JSON形式**のデータでは、波括弧 **{ }** が「名前と値の組の集まり（1件のオブジェクト）」、角括弧 **[ ]** が「複数要素を並べた配列（繰返しデータ）」を表す。
- 「処理時間がCPU処理能力（MIPS）だけに依存する」という条件の試算では、移行先機器のMIPS値が元の機器の **$k$ 倍** であれば、所要時間は **$1/k$** になる。
- システム設計の後半で「なぜこの構成にしたのか（拡張性・保守性など）」を問われたら、問題文冒頭の「改修方針・システム化方針」に書かれた要件へ立ち返って対応づける。
