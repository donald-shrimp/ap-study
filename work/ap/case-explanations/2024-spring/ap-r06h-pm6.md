# 人事評価システムの設計と実装

## この問題は、何を考える問題だった？

K社は、中小企業向けに人事評価システムをクラウド経由で提供する **SaaS（Software as a Service）** 事業者です。これまでは契約会社ごとに仮想サーバとデータベースを個別に用意していましたが、サポート期限を機に、**「機能は変えずにサーバリソースを最適化するため、1つのデータベースに統合する（マルチテナント化する）」**という再構築に取り組んでいます。

この大問で一貫して問われているのは、**「複数の契約会社のデータを1つのデータベースで扱うときに、会社間のデータ分離（セキュリティ）と、会社をまたぐ共通参照・横断分析（利便性・既存SQLの維持）をどう両立するか」**というデータベース設計の考え方です。

全体の流れは次の3ステップで進みます。
1. **単一データベース・単一スキーマ方式の検討（設問1）**：すべての表を1つのスキーマにまとめた場合のE-R図の関連（1対多の向き）と、祝日一覧・評価対象従業員一覧を取り出すSQL文（範囲指定・結合条件・並び順）を完成させる。
2. **単一データベース・個別スキーマ方式への見直し（設問2・設問3）**：SQLインジェクション発生時の情報漏えいリスクを抑えるために会社別スキーマへ分割し、共有用スキーマの表を会社別スキーマの**ビュー**から参照するSQLを作成する。
3. **個別スキーマ方式のレビューと配置修正（設問4）**：ログイン時に利用スキーマを特定するための列追加と、同業他社のデータも参照する「**退職分析**」機能を実現するための表配置の見直しを行う。

## まず、8つの機能とスキーマ方式の違いを整理しよう

設問に入る前に、表1に示された8つの機能で「どの範囲の会社のデータを参照するか」と、本文中で検討される2つのデータベース統合方式の違いを整理しておきましょう。

- **自社内のデータだけで完結する機能**：入社、評価者管理、目標設定、実績入力、評価、退職（登録のみ）
- **全契約会社で共通のデータを参照する機能**：**祝日管理**（「国民の祝日」は全社共通、「会社記念日」は会社ごと）
- **同業他社のデータも横断して参照する機能**：**退職分析**（**自社および自社と同じ業種の退職者**について、在籍期間と退職理由を分析する）

また、本文で段階的に検討されるスキーマ構成の違いは次のとおりです。

| 方式 | 仕組みの概要 | メリット・課題 |
| --- | --- | --- |
| **① 単一データベース・単一スキーマ方式（初期案）** | 1つのデータベース・1つのスキーマの中に全契約会社のデータを混在させ、「会社番号」列で区別する | サーバリソースは最適化できるが、**SQLインジェクション**の脆弱性があると全契約会社の情報が漏えいするおそれがある |
| **② 単一データベース・個別スキーマ方式（改善案）** | 全社共通のデータを置く**共有用スキーマ（PUB）**と、契約会社ごとの**個別会社用スキーマ（Cxxx）**に分ける | 接続時の参照範囲を自社スキーマ＋PUBに制限でき、漏えい範囲を局所化できる。ただし同業他社を分析する「**退職表**」はPUB側に置く工夫が必要 |

この全体像を押さえておくと、後半の設問2〜設問4で「なぜスキーマを分けるのか」「なぜ退職表の配置を見直すのか」が自然につながります。

## 設問1(1) a｜一人の管理者が複数の部署を管理する

設問1(1)は、［単一データベース・単一スキーマ方式の検討］の図1（E-R図）において、「従業員」と「部署」を結ぶ空欄aに入れる適切なエンティティ間の関連（矢印の向き）を答える問題です。

まず **E-R図（Entity-Relationship Diagram）** の基本を確認しましょう。
- **エンティティ（四角形）**：管理対象となるデータのまとまりであり、関係データベースの**表（テーブル）**に対応します。
- **属性**：エンティティがもつ項目であり、表の**列（カラム）**に対応します。実線の下線は行を一意に特定する**主キー**、破線の下線は他表を参照する**外部キー**を表します。
- **関連（矢印）**：図1の凡例では、1対多の関係があるとき**「1」側から「多」側へ向けて矢印**を引きます。

図1で左側の「従業員」と右側の「部署」の間を見ると、上下2本の線が引かれています。
1. **上側の線（所属：従業員 ← 部署）**：
   1つの部署には複数の従業員が所属し、各従業員は1つの部署に所属するため、「部署（1）→ 従業員（多）」の左向き矢印がすでに描かれています。
2. **下側の線（管理：空欄a）**：
   「部署」表には外部キーとして「管理者番号」があり、その部署の管理者を1人指定します。一方で、表1の「評価者管理」の概要を読むと、「**1人の従業員が複数の部署を管理する場合がある**」と明記されています。
   つまり、管理の関連では**「従業員が1、部署が多」**となります。

図1では左側に「従業員」、右側に「部署」が配置されているため、左（従業員）から右（部署）へ向かう右向き矢印 **→** が答えです。

- **公式解答例**：「→」

## 設問1(2) b・c｜指定年度の両端を含め、まとめた一覧を昇順にする

設問1(2)は、図2（国民の祝日と会社記念日の一覧を日付の昇順に出力するSQL文）の空欄b・c、および図3の空欄cに入れる適切な字句を答える問題です。

図2のSQL文が何をしているかを順番に確認しましょう。
- 上段のSELECT文では「国民の祝日」表から祝日を取り出し、下段のSELECT文では「会社記念日」表から指定した会社（**会社番号 = :会社番号**）の記念日を取り出しています。
- どちらも **AS** を使って出力列名を「日付」「日付名」にそろえ、**UNION ALL** で上下の検索結果を1つの一覧に結合しています（重複行を統合しない **UNION ALL** を使うことで、国民の祝日と会社記念日が同じ日に重なっていても両方の行が出力されます）。
- コロン（**:**）で始まる **:会社番号**、**:年度開始日**、**:年度終了日** は、プログラムから実行時に条件値を渡す**埋込み変数**です。

ここで空欄b・cに入る条件を考えます。
1. **空欄b（指定年度の範囲指定）**：
   「指定された会社と年度における」一覧を出すため、「祝日」および「会社記念日」の日付が **:年度開始日** から **:年度終了日** までの間（両端の日付を含む）に入っている行を抽出します。SQLで両端を含む範囲を指定する演算子は **BETWEEN 開始値 AND 終了値** なので、bの字句は **BETWEEN :年度開始日 AND :年度終了日** です。
2. **空欄c（昇順での並べ替え）**：
   図2では「日付の昇順に」、図3では「部署番号，従業員番号の昇順に」並べ替えて出力します。SQLで結果の行を並べ替える句は **ORDER BY** であり、並び順の指定（ASC／DESC）を省略すると既定で**昇順（ASC）**になります。したがって、cは **ORDER BY** です。

完成した図2のSQL文は次のようになります。

```sql
SELECT 祝日 AS 日付, 祝日名 AS 日付名
FROM 国民の祝日
WHERE 祝日 BETWEEN :年度開始日 AND :年度終了日
UNION ALL
SELECT 会社記念日 AS 日付, 会社記念日名 AS 日付名
FROM 会社記念日
WHERE 会社番号 = :会社番号
  AND 会社記念日 BETWEEN :年度開始日 AND :年度終了日
ORDER BY 日付
```

## 設問1(3) d｜会社番号と部署番号をそろえて従業員と部署を結ぶ

設問1(3)は、図3（指定された管理者が評価する対象の従業員の一覧を出力するSQL文）の空欄dに入れる適切な字句を答える問題です。

図3のSQL文では、「従業員」表に **EMP**、「部署」表に **DEP** という別名（相関名）を付け、**INNER JOIN（内部結合）** で2つの表を結び付けています。

単一データベース・単一スキーマ方式では、1つの「部署」表の中に複数会社の部署データが入っています。そのため、図1のE-R図にあるとおり、「部署」表の主キーは「**会社番号**」と「**部署番号**」の2列の組み合わせ（複合主キー）になっています。例えば、A社にも「部署番号10」があり、B社にも「部署番号10」が存在し得ます。

もし **ON EMP.会社番号 = DEP.会社番号** だけで結合すると、同じ会社内のすべての部署とすべての従業員が総当たりで結び付いてしまいます。逆に部署番号だけで結合すると、他社の同じ部署番号の行まで混ざってしまいます。したがって、各従業員を自分の所属部署の行と1対1で正しく結び付けるには、会社番号の一致に加えて**両表の部署番号も一致させる条件**が必要です。よって、dは **EMP.部署番号 = DEP.部署番号** です。

完成した図3のSQL文は次のようになります。

```sql
SELECT DEP.部署番号, DEP.部署名, EMP.従業員番号, EMP.従業員氏名
FROM 従業員 EMP INNER JOIN 部署 DEP
  ON EMP.会社番号 = DEP.会社番号
    AND EMP.部署番号 = DEP.部署番号
    AND EMP.会社番号 = :会社番号
    AND DEP.管理者番号 = :管理者番号
ORDER BY DEP.部署番号, EMP.従業員番号
```

## 設問2｜会社ごとに読める範囲を制限して漏えいを局所化する

設問2は、［単一データベース・単一スキーマ方式のレビュー］の下線①「システム利用者の会社ごとのスキーマに分ける方式」にする利点を20字以内で答える問題です。

まず **スキーマ** と **SQLインジェクション** の関係を押さえましょう。
- **スキーマ**：1つのデータベースの中で、表やビューをグループ分けして管理し、アクセス権限を個別に設定できる「名前付きの区画」です。
- **SQLインジェクション**：アプリケーションの入力処理の不備を突いて、攻撃者が不正なSQL文を注入・実行し、本来見られないはずのデータを読み出したり改ざんしたりする攻撃です。

レビューの指摘では、「単一データベース・単一スキーマ方式では、SQLインジェクションの脆弱性が見つかってしまった場合、**多くの情報が漏えいしてしまうおそれがある**」と述べられています。全契約会社のデータが同じスキーマの同じ表に入っていると、1箇所の脆弱性から全契約会社のデータが抜き取られてしまいます。

これに対し、契約会社ごとにスキーマ（C001、C002…）を分け、システム利用者が操作するときは「自社のスキーマと共有用スキーマ（PUB）だけを参照できる権限」で接続するようにしておけば、万が一SQLインジェクション攻撃を受けても、他社のスキーマにあるデータは参照できません。

この「漏えいする情報の範囲を1社分（会社単位）に封じ込められる」という利点を20字以内でまとめます。

- **公式解答例**：「漏れる情報を会社単位に制限できる。」（17字）

## 設問3 e・f｜会社側にビューを作り、共有側の祝日表を読む

設問3は、［単一データベース・個別スキーマ方式の検討］の図4（スキーマC001に国民の祝日ビューを作成するSQL文）の空欄e・fに入れる適切な字句を答える問題です。

**ビュー（VIEW）**は、SELECT文による検索結果に名前を付け、あたかも実体のある表（テーブル）のように参照できるようにした**仮想的な表**です。

表2を見ると、「国民の祝日」の実体の表は**共有用スキーマ（PUB）**に配置し、**個別会社用スキーマ（Cxxx）**には同じ名前の「国民の祝日」ビューを配置する設計になっています。こうする理由は、レビューのアドバイスにあるとおり、「現在のシステムのSQL文（図2のようにスキーマ名を付けずに **FROM 国民の祝日** と書いたSQL文）への修正を少なくするため」です。

SQLで別スキーマの表やビューを指定するときは、**スキーマ名.表名（またはビュー名）** と記述します。
- **空欄e（作成するビューの名前）**：スキーマ **C001** の中に「国民の祝日」ビューを作るため、**C001.国民の祝日** を指定します。
- **空欄f（参照元の表の名前）**：実体の表は共有用スキーマ **PUB** の中にあるため、**PUB.国民の祝日** を指定します。

図4のSQL文を完成させると次のようになります。

```sql
CREATE VIEW C001.国民の祝日 (祝日, 祝日名)
AS SELECT 祝日, 祝日名
FROM PUB.国民の祝日
```

- **公式解答例**：e「C001.国民の祝日」、f「PUB.国民の祝日」

## 設問4(1) g・h｜会社から利用先スキーマを引けるようにする

設問4(1)は、［単一データベース・個別スキーマ方式のレビュー］の指摘「システム利用者ごとに，利用するスキーマを指定するために，［g］表に［h］列を追加する必要がある」の空欄g・hに入れる適切な字句を答える問題です。

個別スキーマ方式では、契約会社ごとに **C001**、**C002** のような個別スキーマを作ります。ただし表2の注記にあるとおり、**Cxxx** の **xxx** は任意の英数字であり、会社番号そのものとは限りません。

そのため、システム利用者がログインしたときに「この利用者の所属会社はどのスキーマ（**Cxxx**）を使えばよいか」をデータベース上で引けるようにしておく必要があります。契約会社の基本情報を管理しているのは共有用スキーマ（PUB）にある **会社** 表なので、この **会社** 表（空欄g）に、対応する **スキーマ名** 列（空欄h）を追加すれば、会社番号から利用すべきスキーマを特定できます。

- **公式解答例**：g「会社」、h「スキーマ名」

## 設問4(2)｜自社だけの表では同業他社の退職者を分析できない

設問4(2)は、レビューで指摘された下線②「表2の表とビューの配置のままでは利用できない機能」を、表1の機能名から答える問題です。

表2の当初案では、個別会社用スキーマ（Cxxx）に「会社記念日，従業員，部署，目標，実績，評価，退職」の7つの表が配置されています。設問2で確認したとおり、各社のシステム利用者は「自社の個別スキーマ」と「共有用スキーマ（PUB）」しか参照できず、**他社の個別スキーマにある表は参照できません**。

ここで表1の8つの機能を振り返ると、「退職」機能は自社の退職者を登録するだけですが、「**退職分析**」機能は「人事部の管理者が**自社及び自社と同じ業種の退職者について**，在籍期間と退職理由を分析する」機能です。各社の「退職」表が個別会社用スキーマに閉じ込められていると、同じ業種の他社の退職データを参照・集計することができません。したがって、利用できない機能は **退職分析** です。

- **公式解答例**：「退職分析」

## 設問4(3)｜他社分も必要な退職表を共有用に配置する

設問4(3)は、設問4(2)の「退職分析」を利用できるようにするために、下線③「配置を一部見直す」内容を20字以内で答える問題です。

1. **どの表をどこへ移せばよいかを考える**：
   「退職分析」では、自社だけでなく同じ業種の他社の退職データも検索・集計する必要があります。他社の個別スキーマへのアクセス権を開放してしまうと設問2のセキュリティ上の利点が失われてしまうため、全社から参照できる**共有用スキーマ（PUB）**へ「**退職**」表を移すのが適切です。
2. **共有用スキーマに置いたときのつながりを確認する**：
   図1のE-R図を見ると、「退職」表には「会社番号」「従業員番号」「退職年月日」「在籍期間」「退職理由」だけがあり（個人氏名などは「従業員」表にあります）、共有用スキーマの「会社」表にある「業種」と結合すれば、同業他社の退職者の在籍期間と退職理由を分析できます（なお、個別会社用スキーマ側には「会社」や「国民の祝日」と同様に「退職」ビューを配置すれば、既存のSQLもそのまま動かせます）。

この見直し内容を20字以内で簡潔にまとめます。

- **公式解答例**：「退職表を共有用スキーマに配置する。」（17字）

## 次の問題でも使うこと

- **E-R図の1対多の矢印**を決める際は、本文や機能一覧にある「1人の〜が複数の〜を担当する場合がある」といった業務ルールから、どちらが「1」でどちらが「多」かを読み取る。
- 複数会社のデータを1つの表にまとめる設計では、主キーが「会社番号＋部署番号」などの**複合主キー**になるため、**INNER JOIN** の結合条件でも会社番号と部署番号の**両方**を一致させる必要がある。
- **SaaSのマルチテナント設計**では、会社ごとにスキーマを分けて接続権限を絞ることで、SQLインジェクション発生時の情報漏えい範囲を会社単位に局所化でき、全社共通の表は**共有用スキーマの表＋個別スキーマの同名ビュー**で参照させると既存SQLの修正を抑えられる。
- スキーマ分割後に「実現できない機能」を問われたら、機能一覧の中から**会社をまたいで他社データを参照・集計する機能**（業界平均や同業他社分析など）を探す。
