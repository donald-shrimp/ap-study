# ダッシュボードの設計

## この問題は、何を考える問題だった？

食品などを販売する複数の店舗を経営するY社では、商品の売れ行きや在庫状況を見ながら割引率の設定や店舗間の在庫移動を判断するため、販売・在庫状況をリアルタイムで画面表示する**ダッシュボード**を開発することになりました。

この大問で一貫して問われているのは、**「データベースの更新をきっかけに複数のグラフ画面を自動更新する仕組み（Observerパターン）をオブジェクト指向でどう設計し、絞り込み条件の引き渡しや重複描画による過負荷をどう解決するか」**というクラス設計・メソッド連携の考え方です。

全体の流れは次の3ステップで進みます。
1. **クラス図（継承・多重度）と監視対象の設計（設問1〜設問3）**：グラフの種類やテーブルの種類ごとに親クラスを**継承**して子クラスを作り、「時間帯ごと商品分類ごとの売上金額」を集計するために監視すべきテーブル（**Subject**）を特定する。
2. **データベース更新からグラフ再描画までの呼び出し連鎖（設問4）**：抽象メソッドとポリモーフィズム（多態性）によって、各グラフオブジェクトに応じた**画面表示更新メソッド**が呼び出される流れをたどる。
3. **フィルタリング機能の追加と過負荷の回避（設問5・設問6）**：グラフをクリックしたときの**絞込条件オブジェクト**を引数で引き渡す仕様変更と、1回の販売で複数回通知が届く問題に対する**更新フラグ**を使った再描画の集約を設計する。

## まず、データモデル（図1）とクラス構成（図3）を整理しよう

設問に入る前に、図1のデータベースのテーブル構成と、図3・表2のクラスの役割分担を整理しておきましょう。

まず、図1のデータモデルのうち、販売や在庫のたびに日々更新されるトランザクション系の3つのテーブルには、それぞれ対応する **Subjectクラス** が用意されています。

| テーブル名 | 主な項目（属性） | 対応するSubjectクラス | 役割のポイント |
| --- | --- | --- | --- |
| **販売実績** | 店舗コード、販売コード、**販売日時**、売上金額合計 | **販売実績Subject** | 1回の会計（レシート単位）の時刻と合計金額を記録する |
| **販売明細** | 店舗コード、販売コード、明細番号、**商品コード**、**販売単価**、**販売数量** | **販売明細Subject** | 1回の会計の中で「どの商品が何個・いくらで売れたか」の内訳を記録する |
| **在庫** | 店舗コード、商品コード、在庫数 | **在庫Subject** | 各店舗に各商品が今いくつ残っているかを記録する |
| **商品マスタ／商品分類マスタ／店舗マスタ** | 商品コード、**商品分類コード**、商品分類名、店舗名など | （なし） | 商品の分類名や店舗名を引くためのマスタデータ |

次に、データを監視して通知する側（**Subject**）と、通知を受け取ってグラフを描画する側（**View**）の連携構造（**Observerパターン**）を整理します。

| クラス名 | 役割と主なメソッド |
| --- | --- |
| **Controller** | システム全体を制御する。DB更新時に **dbUpdated(更新テーブル名配列)** が呼ばれ、該当するSubjectの **notifyObservers()** を呼び出す |
| **Subject**（親クラス）<br>↳ 販売実績Subject／在庫Subject／販売明細Subject | 通知先のViewオブジェクトを配列 **views** に保持する。**addObserver()** で通知先を登録し、**notifyObservers()** で登録済み全Viewの **notify()** を呼び出す |
| **View**（親クラス）<br>↳ 棒グラフView／円グラフView／折れ線グラフView | 1つのグラフを表示する。**notify()** が呼ばれると自身の **画面表示更新()**（抽象メソッド）を呼び出し、各子クラスの実装で集計・再描画を行う |
| **集計項目／集計処理／DAO** | グラフの軸や集計対象項目の定義を保持し、**DAO** を通じてデータベースからデータを取得・集計する |

この「**Controller → Subject → View**」の通知の流れを押さえておくと、すべての設問が明快に解けます。

## 設問1 a｜共通部分を継承し、種類ごとのクラスを作る

設問1は、［ダッシュボードのクラスの設計］の空欄a（3箇所共通）に入れる適切な字句を答える問題です。

本文には「グラフには複数の種類があるので，その種類ごとに，Viewクラスを［a］したクラスを作成する」「ダッシュボードで監視したい情報に関するテーブルのそれぞれについて，Subjectクラスを［a］したクラスを作成する」と書かれています。

オブジェクト指向プログラミングにおいて、複数のクラスに共通する属性（データ）やメソッド（処理）を親クラス（スーパークラス）にまとめ、その性質を受け継いで種類ごとの差分だけを定義した子クラス（サブクラス）を作る仕組みを **継承（インヘリタンス）** と呼びます。
- **Viewクラス**を継承して → **棒グラフView**、**円グラフView**、**折れ線グラフView** を作成
- **Subjectクラス**を継承して → **販売実績Subject**、**在庫Subject**、**販売明細Subject** を作成

したがって、空欄aには **継承** が入ります。

- **公式解答例**：「継承」

## 設問2 b・c｜View側は0個以上、白抜き三角形は親へ向ける

設問2は、図3（クラス図）の空欄b（多重度）と空欄c（クラス間の関係を表す記号）を答える問題です。

1. **空欄b（Subjectから見たViewの多重度）**：
   クラス図の**多重度**は、「一方のオブジェクト1個に対して、相手側のオブジェクトが何個結び付き得るか」を表します。
   Subjectクラスは、通知先のViewオブジェクトを格納する配列 **views** をもっており、グラフが新規表示されるたびに **addObserver** メソッドで通知先のViewが追加されます。
   - まだそのテーブルを使うグラフが1つも表示されていなければ、登録されているViewオブジェクトは **0個** です。
   - 同じテーブルを使うグラフが画面上に複数表示されれば、登録されるViewオブジェクトは **1個以上（複数個）** になります。
   したがって、「0個以上」を表す多重度 **0..*** が空欄bに入ります。

2. **空欄c（親クラスと子クラスを結ぶ関係記号）**：
   空欄cは、親クラスである **Subject** とその子クラス群（販売実績Subject・在庫Subject・販売明細Subject）、および親クラスである **View** とその子クラス群（棒グラフView・円グラフView・折れ線グラフView）を結ぶ線にあります。
   設問1で確認したとおり、これらは**継承**の関係です。図3の凡例を見ると、継承は**親クラスの側に白抜き三角形を向けた実線**で表すと定義されています。図3では親クラス（Subject、View）が上側、子クラス群が下側に配置されているため、子クラスから伸びる縦線の上端（親クラス側）に、上向きの **△**（白抜き三角形）を描きます。

- **公式解答例**：b「0..*」、c「△（白抜き三角形，下から縦線でつなぐ上向きの継承矢印）」

## 設問3｜売上を時間帯と商品分類で分けるには、実績と明細が要る

設問3は、［グラフの新規表示］において“時間帯ごと商品分類ごとの売上金額”の棒グラフを画面上に表示するとき、下線①「関係するSubjectオブジェクト」のクラス名を図3中から**すべて**選ぶ問題です。

図2の左上にある「時間帯別売上（商品分類別積上げ）」の棒グラフを描くために、図1のどのテーブルの項目が必要かをたどってみましょう。
1. **横軸「時間帯（8時台、9時台…）」を知るには**：
   いつ販売が行われたかを表す「**販売日時**」が必要です。図1を見ると、「販売日時」は **販売実績** テーブルにあります。
2. **縦棒の内訳「商品分類ごとの売上金額」を知るには**：
   「販売実績」テーブルには会計全体の「売上金額合計」しかなく、どの商品分類がいくら売れたかという内訳はありません。商品分類ごとの売上金額を求めるには、**販売明細** テーブルの「商品コード」「販売単価」「販売数量」を参照し、商品コードから「商品マスタ」→「商品分類マスタ」をたどって商品分類を特定する必要があります。

具体例で確認しましょう。例えば8時15分の会計で、120円の青果が2個と、300円の肉類が1個売れたとします。
- 「8時台」という時間帯は、**販売実績**テーブルの販売日時（8時15分）から分かります。
- 商品分類別の売上金額は、**販売明細**テーブルから青果が `120×2＝240` 円、肉類が `300×1＝300` 円と計算できます（販売実績の合計540円だけを見ても、240円と300円の内訳には分けられません）。

このように、時間帯別・商品分類別の売上金額を集計するには**販売実績**テーブルと**販売明細**テーブルの両方を参照するため、通知先として登録すべきSubjectオブジェクトのクラス名は **販売実績Subject，販売明細Subject** の2つです（なお、在庫数を監視する在庫Subjectはこのグラフの集計には関係しません）。

- **公式解答例**：「販売実績Subject，販売明細Subject」

## 設問4 d・e｜実際のグラフの種類が描画処理を決める

設問4は、［グラフの表示内容更新］の空欄d・eに入れる適切な字句を答える問題です。

店舗で商品が販売されてからグラフが再描画されるまでの呼び出しの流れを順番に追ってみましょう。
1. 販売管理システムがデータベースにレコードを追加すると、Controllerクラスの **dbUpdated** メソッドが呼ばれます。
2. Controllerは、更新されたテーブルに対応するSubjectオブジェクトの **notifyObservers** メソッドを呼び出します。
3. Subjectは、配列 **views** に登録されているすべてのViewオブジェクトの **notify** メソッドを呼び出します。
4. Viewクラスの **notify** メソッドが、自身の **画面表示更新** メソッドを呼び出します。

ここで空欄d・eの前後を見ると、「Viewクラスの画面表示更新メソッドは［d］メソッドなので，例えば，“時間帯ごと商品分類ごとの売上金額”の場合は［e］クラスに実装されたメソッドを呼び出す」とあります。
- **空欄d**：図3のViewクラスを見ると、**画面表示更新()** が**斜字体**で書かれています。図3の凡例に「斜字体は**抽象**クラス又は**抽象**メソッドを表す」とあるとおり、親クラスであるViewではメソッド名だけを宣言し、具体的なグラフの描画処理は子クラス側に任せています。したがって、空欄dは **抽象** です。
- **空欄e**：“時間帯ごと商品分類ごとの売上金額”を表示しているオブジェクトの実体（インスタンス）は、設問3の冒頭にあるとおり **棒グラフView** クラスのオブジェクトです。したがって、実際に呼び出される画面表示更新メソッドが実装されているクラス（空欄e）は **棒グラフView** です。

- **公式解答例**：d「抽象」、e「棒グラフView」

## 設問5｜絞込条件を二つのメソッドの引数で渡す

設問5は、［データのフィルタリング］において、Viewオブジェクトが画面の表示を更新する際に絞込条件のオブジェクトが引き渡されるようにするため、Subjectクラスの **notifyObservers** メソッドとViewクラスの **notify** メソッドのそれぞれについて行う下線②「仕様を変更する」内容を30字以内で答える問題です。

1. **絞込条件オブジェクトがどこに保持されているかを確認する**：
   利用者がグラフ上の特定の商品分類をクリックすると、Viewが **絞込条件クラスのオブジェクト**（テーブル名＝“商品マスタ”、項目名＝“商品分類コード”、絞込条件の値＝“商品分類コードの値”）を生成し、Controllerの **setFilter** メソッドを呼んで **Controllerの属性** に保持させます。
2. **DB更新時にControllerからViewまでどう届けるかを考える**：
   その後、データベースが更新されて **dbUpdated** が呼ばれたときも、Controllerが保持している「絞込条件クラスのオブジェクト」を各Viewまで届けて、絞り込みを維持したまま再集計させる必要があります。
   DB更新時の呼び出し経路は「**Controller → SubjectのnotifyObserversメソッド → Viewのnotifyメソッド → 画面表示更新メソッド**」です。図3の当初設計では **notifyObservers()** も **notify()** も引数なし（空括弧）になっているため、この2つのメソッドの**引数に絞込条件クラスのオブジェクトを追加**すれば、ControllerからSubjectを経由して各Viewへ絞込条件を引き渡すことができます。

この仕様変更の内容を30字以内でまとめます。

- **公式解答例**：「引数に絞込条件クラスのオブジェクトを追加する。」（23字）

## 設問6 f｜一つのViewに複数の通知が届くので更新をまとめる

設問6は、［過負荷の回避］のレビュー指摘「一つのViewオブジェクトは［f］ので，1回の販売実績の登録で，表示の更新が複数回発生してしまう」の空欄fに入れる適切な字句を30字以内で答える問題です。

1. **なぜ1回の販売で表示更新が複数回発生するのかを振り返る**：
   設問3で確認したとおり、“時間帯ごと商品分類ごとの売上金額”を表示する1つの棒グラフViewオブジェクトは、**販売実績Subject** と **販売明細Subject** の**2つのSubjectオブジェクト（複数のSubjectオブジェクト）に通知先として登録**されています。
2. **1回の販売登録で起きる動きを追う**：
   店舗で1回の会計（販売）が行われると、データベースの「販売実績」テーブルと「販売明細」テーブルの両方にレコードが追加されます。するとControllerの **dbUpdated** に両方のテーブル名が渡され、**販売実績Subject** と **販売明細Subject** の両方から同じ棒グラフViewの **notify** メソッドが立て続けに呼び出されます。
   その結果、1回の販売につき同じグラフの集計・再描画が2回実行されてしまい、連続して販売が行われると過負荷の原因になります。

そこで改善案では、**notify** が呼ばれた時点では「更新フラグ」をONにするだけにとどめ、別スレッドなどの定期処理が「更新フラグがONのViewだけを1回再描画してフラグをOFFに戻す」仕組みにしています。

空欄fの直後には「〜ので，1回の販売実績の登録で，表示の更新が複数回発生してしまう」と続くため、主語である「一つのViewオブジェクトは」につながる形で30字以内にまとめます。

- **公式解答例**：「複数のSubjectオブジェクトに登録される」（22字）

## 次の問題でも使うこと

- **UMLクラス図の記号**では、親クラス側に向ける**白抜き三角形（△）が継承（汎化・特化）**、全体側につける**白抜きひし形（◇）が集約**、**斜字体が抽象クラス／抽象メソッド**を表す。
- **Observerパターン**（SubjectとViewの分離）では、「1つのSubjectに複数のViewを登録できる（多重度 **0..***）」だけでなく、「**1つのViewが複数のSubjectを監視（登録）することもある**」という多対多の関係に注意する。
- 1つのViewが複数のSubjectに登録されていると、1回の業務イベント（販売登録など）で複数テーブルが更新された際に**同じViewへ複数回通知が届く**。即座に再描画せず**更新フラグ（ダーティフラグ）**を立てて定期更新で1回にまとめる手法は、UI設計の定番パターンである。
- メソッド呼び出しの連鎖（Controller → Subject → View）の途中で新たな情報（絞込条件オブジェクトなど）を伝える必要があるときは、経路上のメソッドの**引数にそのオブジェクトを追加する**。
