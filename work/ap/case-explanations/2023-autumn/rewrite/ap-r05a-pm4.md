# システム統合の方式設計

## この問題は、何を考える問題だった？

家具の製造・販売を行うC社とD社が合併するにあたり、両社で重複している業務システムを統合する方式設計の事例です。
同じ「家具を作って売る会社」であっても、注文を受けてから出荷するまでの業務の流れ（ビジネスモデル）が異なれば、システムに求められる機能やデータ連携の周期も変わります。

- **C社（存続会社）**：ショッピングセンター向けに安価な家具を量産する**見込み生産方式**です。売れ行きを見込んで日次で生産計画を立て、完成した製品を倉庫に在庫として保管し、注文が入ったら倉庫から出荷します。
- **D社**：百貨店やハウスメーカーの展示場向けにセミオーダーメイド家具を作る**個別生産方式**です。顧客ごとに見積りを作って受注してから週次で生産計画を立てて製造するため、完成品の在庫を持ちません（在庫システムが存在しません）。

合併直後にすべてのシステムを一から作り直すと、費用も期間もかかり、日々の業務に大きな影響が出ます。そこで、**既存のシステムをできるだけ活用しながら重複するシステムを片方に寄せる（片方を廃止し、もう片方を継続利用する）**という方針をとります。

この問題では、次の4つのステップでシステム統合の設計を進めます。

1. **どのシステムを残し、どれを廃止するか**（生産方式の違いと「ホスト系システムを廃止する」方針から判断する）
2. **廃止したシステムが担っていた固有の業務をどこへ移すか**（両社の機能一覧を比較して不足機能を特定する）
3. **システムを片方に寄せたことで新しく発生するシステム間連携は何か**（送る情報の種類と業務の周期をたどる）
4. **残すクラウドサービス（SaaS）に別会社のシステムをつなぐとき、なぜ入念な調査が必要になるのか**（SaaSの仕様変更の制約を考える）

## まず、両社の業務・システムの違いと統合方針を整理しよう

設問に入る前に、問題文の統合方針と、表1（C社）・表2（D社）に書かれている各システムの特徴を整理しておきましょう。

**システム統合の3つの基本方針**

1. **生産システムと在庫システム**：合併後も両社の生産方式（C社の見込み生産・D社の個別生産）は変えないため、**生産システムは両社とも継続利用**します。また、見込み生産で製品を倉庫に保管する**C社の在庫システムも継続利用**します（D社にはもともと在庫システムがありません）。
2. **販売・購買・配送・会計システム**：両社で重複しているため、**どちらか一方のシステムを廃止し、もう一方のシステムを継続利用**します。その際、保守費用がかさむ**ホスト系（汎用機）のシステムは廃止する**方針です。
3. **機能の移植**：廃止するシステムにしか存在しない固有の機能（継続利用する側のシステムにはない機能）がある場合、業務が止まらないように、継続利用するシステムへその機能を**移植**（処理の仕様を変えずに別システムへ移すこと）します。

表1（C社）と表2（D社）のシステム構成と主な機能・連携を並べると、全体像がはっきり見えます。

| システム名 | C社（表1：見込み生産・日次中心） | D社（表2：個別生産・週次中心） | 統合後の方針（図1） |
| --- | --- | --- | --- |
| **販売システム** | **ホスト系**／受注（EDI）・販売実績管理（月次）・請求（EDI）・売上計上 | **オープン系**／見積・受注（手入力）・請求（請求書発行）・売上計上 | C社（ホスト系）を廃止し、**D社側を継続利用**（a） |
| **生産システム** | **オープン系**／日次で計画・実績管理、会計・購買・在庫と日次連携 | **オープン系**／週次で計画・実績管理、会計・購買・配送と週次連携 | **両社とも継続利用**（D社側がb） |
| **在庫システム** | **オープン系**／入出庫・在庫数量管理、生産へ在庫状況・配送へ出荷指示（日次） | （個別生産で製品在庫を持たないため存在しない） | **C社側を継続利用** |

| **配送システム** | **オープン系**／配送伝票・配送先管理、販売へ出荷情報（日次）・会計へ配送経費（月次） | **オープン系**／配送伝票・配送先管理、販売へ出荷情報（週次）・会計へ配送経費（月次） | D社側を廃止し、**C社側を継続利用** |

## 残すシステムは、業務の違いと廃止の方針から決まる

**設問1(1) 空欄a・b・c｜統合後のシステム構成（図1）に入るシステム名**

図1は、統合後に残るシステムをC社側（左側）とD社側（右側）に分けて描いた構成図です。表1・表2のシステム一覧と統合方針を照らし合わせて、空欄a〜cを埋めましょう。

- **空欄a（D社側に残るシステム）**：
  表1を見ると、C社の販売システムは「オンプレミス（ホスト系）」、表2のD社の販売システムは「オンプレミス（オープン系）」です。ホスト系を廃止して一方に寄せる方針なので、C社の販売システムを廃止し、D社の販売システムを残します。図1でも、aからC社の生産システムやD社のシステムbへ矢印が出ており、注文を受け付ける起点になっていることから、aは **販売システム** です。
- **空欄b（D社側に残るシステム）**：
  両社の生産方式は合併後も維持するため、生産システムはC社・D社の両方に残ります。図1のD社側を見ると、a（販売システム）から実線の矢印を受け取り、D社の購買システムやC社の配送システム（点線エ）、C社のシステムc（点線オ）へ情報を送っています。表2で「販売システムから受注情報を受け取り、購買へ購買指示情報、配送へ出荷指示情報、会計へ原価情報を送る」役割を担っているのは **生産システム** です。
- **空欄c（C社側に残るシステム）**：
  表2を見ると、D社の会計システムは「オンプレミス（ホスト系）」、表1のC社の会計システムは「クラウドサービス（SaaS）」です。ホスト系であるD社の会計システムを廃止し、C社の会計システムに一本化します。図1でも、両社の販売・生産・購買・配送のすべてから矢印が集まる最終的な集約先になっているため、cは **会計システム** です。

したがって、空欄aは **販売システム**、空欄bは **生産システム**、空欄cは **会計システム** です。

## システムを廃止しても、その会社の仕事は続く

**設問2(1)・(2)｜固有機能の移植先システムと、移植が必要になる機能**

C社の販売システム（ホスト系）を廃止しても、旧C社の顧客（ショッピングセンターなど）から注文を受け、販売実績を集計し、代金を請求する業務そのものがなくなるわけではありません。
廃止するシステムにしかなく、継続利用するシステムには備わっていない「固有機能」を、残す側のシステムへ移植する必要があります。

**設問2(1)｜固有機能の移植先となる会社名とシステム名**

問題文には、固有機能の移植が「1システムだけに発生する」と書かれています。
重複する4つの業務（販売・購買・配送・会計）について、表1（C社）と表2（D社）の「主な機能」欄を見比べてみましょう。

- **購買システム**（C社を廃止 → D社へ統合）：両社とも「発注、買掛管理、購買先管理」でまったく同じです。
- **配送システム**（D社を廃止 → C社へ統合）：両社とも「配送伝票作成、配送先管理」でまったく同じです。
- **会計システム**（D社を廃止 → C社へ統合）：廃止するD社は「原価計算、一般財務会計処理、支払（振込）」ですが、残すC社は「原価計算、一般財務会計処理、支払（振込，手形）」であり、D社の機能をすべて包含しています。
- **販売システム**（C社を廃止 → D社へ統合）：廃止するC社の機能と、残すD社の機能には明確な違いがあります。

したがって、C社の販売システムを廃止したときに、その固有機能を移植する先は **D社** の **販売システム** です。

**設問2(2)｜移植する固有機能（表1・表2の用語での列挙）**

廃止するC社の販売システムの「主な機能」（表1）と、移植先であるD社の販売システムの「主な機能」（表2）を1つずつ比較します。

- **C社の販売システムの主な機能（表1）**：
  1. 受注（EDI）
  2. 販売実績管理（月次）
  3. 請求（EDI）
  4. 売上計上
- **D社の販売システムの主な機能（表2）**：
  1. 見積
  2. 受注（手入力）
  3. 請求（請求書発行）
  4. 売上計上

見比べると、「売上計上」はD社の販売システムにも既にあります。
しかし、C社がショッピングセンターなどの大口顧客と電子データ交換（EDI）で行っている「受注（EDI）」と「請求（EDI）」は、D社の「受注（手入力）」や紙の「請求（請求書発行）」とは処理の仕組みがまったく異なります。さらに、C社で行っている「販売実績管理（月次）」はD社の機能一覧には存在しません。

したがって、D社の販売システムへ移植しなければならないC社固有の機能は、表1の用語のまま挙げると **受注（EDI），販売実績管理（月次），請求（EDI）** です。

## 矢印が変わっても、受け取る情報と業務の周期をたどる

**設問1(2) 空欄d・e・f・g｜新たなシステム間連携（表3）の情報と連携頻度**

図1の実線の矢印は「統合前から存在していたシステム間連携」、点線の矢印（ア〜キ）は「片方のシステムを廃止してもう片方に寄せたことで、新しくつなぎ直す必要が生じたシステム間連携」です。
表3の「新たなシステム間連携」とは、見たこともない新しいデータを作るという意味ではありません。**「今まで自社のシステム同士でやり取りしていた情報の送信元または送信先が、相手会社のシステムに変わったもの」**です。

したがって、「どの会社の業務を処理するための連携か」に注目し、表1（C社の業務）と表2（D社の業務）の「システム間連携」欄をたどれば、送る情報と頻度（日次・週次・月次）が正確に決まります。点線ア〜キの7本をすべて整理してみましょう。

したがって、空欄dは **出荷情報**、空欄eは **週次**、空欄fは **売上情報**、空欄gは **月次** です。

## 残す会計サービスが、新しい相手から受け取れるか確かめる

**設問3｜検討チームが下線①（C社の会計システムのインターフェース仕様の調査）を実施する理由（40字以内）**

問題文の最後に、「新たなシステム間連携の実現性を確認するために、検討チームはまず、①C社の会計システムのインターフェース仕様の調査を実施することにした」とあります。なぜ他のシステムではなく、真っ先に「C社の会計システム」のインターフェース仕様を調べる必要があるのでしょうか。

表1・表2の「システム構成」欄をもう一度確認すると、決定的な違いが見つかります。

- C社の生産・在庫・配送、およびD社の販売・生産・購買システム：すべて**オンプレミス（オープン系）**
- C社の会計システム：唯一、**クラウドサービス（SaaS）**

自社で保有・管理しているオンプレミス（オープン系）のシステム同士であれば、連携するデータの形式や項目が合わなくても、送り手側・受け手側のどちらのプログラムでも自社の判断で改修（仕様変更）できます。
ところが、**SaaS（Software as a Service）**はクラウド事業者が多数の企業向けに標準化して提供しているサービスです。「今回合併するD社のシステムから送られてくるデータ形式に合わせて、会計システム側の受け取り仕様を特別に作り変えてほしい」と要望しても、**特定の1社（個別の会社）向けの仕様変更は困難**です。

つまり、図1の点線オ・カ・キのように、これまでつながっていなかったD社の販売・生産・購買システムからC社の会計システム（SaaS）へ新しくデータを連携させるには、**C社の会計システム（SaaS）側が最初から用意している標準のインターフェース仕様をまず調査し、送り手であるD社の各システム側（オンプレミス）をその仕様に合わせて改修できるか**を確かめなければならないのです。

**答案の組み立て方（40字以内）**

答案には、次の2つの要素を入れて因果関係（「〜なので、…が困難だから」）で結びます。

1. **システムの形態**：C社の会計システムはSaaSであること
2. **生じる制約**：個別の会社（自社）向けの仕様変更（カスタマイズ・改修）が困難であること

これらを40字以内で簡潔にまとめると、次の解答例になります。

- 公式解答例：「C社の会計システムはSaaSなので，個別の会社向けの仕様変更が困難だから」（36字）

したがって、解答は **C社の会計システムはSaaSなので，個別の会社向けの仕様変更が困難だから** です。

## 次の問題でも使うこと

- **システム統合（M&A）では「業務の違い（残すもの）」と「システム構成（廃止するもの）」を分けて見る**
  見込み生産と個別生産のようにビジネスモデルが異なる部分は無理に統合せず（生産・在庫は維持）、どの会社でも共通するバックオフィスや販売・購買・配送は片方に寄せます。どちらに残すかは「ホスト系（レガシー）の廃止」などのシステム方針から論理的に決まります。
- **システムを廃止しても「業務と情報の流れ」は消えない**
  片方のシステムを廃止したら、①そのシステムにだけあった固有機能（EDIや月次実績管理など）を残すシステムへ**移植**し、②そのシステムに出入りしていた**データ連携の矢印（何を・どの周期で送るか）**を残すシステムへつなぎ直します。周期（日次・週次・月次）は、データを生み出す業務側のサイクルに従います。
- **SaaSとオンプレミスをつなぐときは「SaaS側の標準仕様」が基準になる**
  SaaSはマルチテナント等で標準提供されるため、個社向けの仕様変更ができません。インターフェース設計では必ず「SaaS側の仕様を先に調べ、オンプレミス側をSaaSに合わせる」という順序を押さえておきましょう。
