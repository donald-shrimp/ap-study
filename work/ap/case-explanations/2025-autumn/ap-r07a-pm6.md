# 問6 受講管理システムの改修

## この問題は、何を考える問題だった？

英会話サービスを提供するD社が、これまでの「ビジネス英会話講座」に加えて、新たに「日常英会話講座」を開設します。日常英会話ではレベルやジャンルの区分がビジネス英会話と異なり、さらに「受講者の年齢層」も管理します。また、受講者が希望の日時と講師を選んで予約できるようにするため、講師ごとの勤務日や勤務可能時間帯もデータベースで管理する必要があります。

こうした業務要件の追加・変更を、**E-R図（エンティティとリレーションシップ）**や**SQL（表定義・検索）**へ正確に落とし込む問題です。解くときの軸になるのは次の3点です。

- **1件の記録（行）を何の組合せで一意に区別するか（主キー）**
- **共通の属性と、講座の種類ごとに異なる属性をどう分けるか（スーパータイプ／サブタイプ）**
- **親子の表や関連する表どうしを、どの列の組で結び付けるか（外部キー・JOIN）**

## まず、「講座」と「その講座の開催」を分けよう

関係データベースでは、管理したい対象（エンティティ）を「表（テーブル）」として定義し、1件ごとの記録を「行（レコード）」、項目を「列（カラム／属性）」で表します。

この問題で最初に押さえておきたいのが、**「講座」そのもの**と、**「その講座の開催スケジュール」**の違いです。例えば、講座コード「K01」という同じ講座を、別々の日に複数回開催することがあります。

| 講座コード | 開催番号 | 開催年月日 |
| --- | --- | --- |
| K01 | 1 | 2025-11-01 |
| K01 | 2 | 2025-11-08 |

このとき、「K01の講座」という情報だけでは、第1回（11月1日）と第2回（11月8日）のどちらの開催なのかを区別できません。そのため、図1の「開催スケジュール」エンティティでは、**講座コード**と**開催番号**の2つを組み合わせた**複合主キー**（実線下線）で1つの開催を識別しています。

- **主キー**：表の中の1行を一意に特定するための列（複数の列を組み合わせる場合は**複合主キー**）

## 設問1｜予約の単位と、1対多の向きを確かめる

### 設問1 a｜受講者と講座だけでは予約を区別できない

図1の「受講予約・結果」は、「どの受講者が、どの講座の、何回目の開催を予約・受講したか」を記録するエンティティです。

もし主キーが「受講者コード」と「講座コード」だけだった場合、同じ受講者が同じ講座（例：K01）の第1回と第2回の両方を予約すると、主キーの値がまったく同じ行が2つできてしまい、区別できなくなります。どの開催に対する予約かを特定するには「開催スケジュール」の主キーである講座コードと**開催番号**の両方が必要なので、空欄aには **開催番号** が入ります。

ここで解答の表記にも注意しましょう。空欄aの「開催番号」は、「受講者コード・講座コード・開催番号」という**複合主キーの一部**になります。したがって、図1の凡例に従い、**開催番号の下に主キーを表す実線下線**を引いて答えます（採点講評でも、この実線下線の引き忘れが多くの受験者の失点箇所として指摘されています。なお、図1の注記より、主キーかつ外部キーである属性には破線下線ではなく実線下線だけを引きます）。

### 設問1 b｜一つの開催に、何件の予約が結び付くか

空欄bは、「開催スケジュール」と「受講予約・結果」の間の対応関係（1対多の矢印の向き）を答える設問です。

- 表1より、ビジネス英会話はグループレッスンで**最大6人**まで受講できます。つまり、**1つの「開催スケジュール」に対して、複数の「受講予約・結果」**が結び付きます。
- 逆に、1件の「受講予約・結果」は、特定の1つの「開催スケジュール」に対する予約です。

したがって、「開催スケジュール」側が **1**、「受講予約・結果」側が **多** の関係になります。図1では「受講予約・結果」が左側に配置されているため、1から多へ向かう矢印は左向きの **←** となります。データの流れではなく、「1件に対して複数件が対応する側へ矢印を引く」というE-R図のルールで判断しましょう。

## 設問2｜属性名が同じでも、許される値は同じか

### 設問2(1) c・d｜レベルとジャンルを種類ごとに分ける

ある属性（列）に格納することが許される値の範囲や集合を**定義域（ドメイン）**といいます。「ビジネス英会話」と「日常英会話」では、同じ「レベル」「ジャンル」という名前の項目であっても、表1を見ると取り得る値（定義域）が異なっています。

| 属性 | ビジネス英会話 | 日常英会話 |
| --- | --- | --- |
| **レベル** | 初級・中級・上級の **3段階** | A1・A2・B1・B2・C1・C2の **6段階** |
| **ジャンル** | 海外出張・会議・交渉など **15種類** | 社交・旅行・趣味など **10種類**（今後変更の可能性あり） |
| **年齢層** | （分類なし） | 幼児・小学生、中学生・高校生、大学生・大人の **3種類** |

すべての講座に共通する属性（講座コード、講座名、受講料など）を親の**スーパータイプ**（「講座」）に置き、講座の種類ごとに異なる属性を子の**サブタイプ**（「ビジネス英会話講座」「日常英会話講座」）に分けて持たせるのが図2の設計です。

改修前の「講座」にあった属性のうち、講座の種類によって取り得る値が異なる **レベル** と **ジャンル** をそれぞれのサブタイプへ移すため、空欄c・dには **レベル** と **ジャンル** が入ります（順不同）。

### 設問2(2)｜「分けると便利」を、理由の答案にする

なぜ「レベル」と「ジャンル」は名前が同じなのに、共通の「講座」エンティティに残さず、サブタイプ側へ移すのでしょうか。設問2(1)で確認した表1の違いを、データベース設計の言葉でまとめます。

1. 「レベル」に取り得る値は、ビジネス英会話（3段階）と日常英会話（6段階）で異なる。
2. 「ジャンル」に取り得る値も、ビジネス英会話（15種類）と日常英会話（10種類、変更の可能性あり）で異なる。
3. つまり、これら2つの属性は**講座区分（ビジネスか日常か）によって定義域が異なる**。

20字以内の公式解答例は、**「定義域が講座区分によって異なるから」（17字）**です。サブタイプごとに列を分けることで、それぞれの講座区分に合った値の範囲（CHECK制約など）を個別に設定・変更できるようになります。

### 設問2(3) e｜日常英会話だけにある属性を置く

表1を見ると、日常英会話講座には「幼児・小学生」「中学生・高校生」「大学生・大人」という**年齢層**の区分がありますが、ビジネス英会話講座には年齢層の区分がありません。

日常英会話講座だけに存在する固有の属性なので、「日常英会話講座」サブタイプの空欄eには **年齢層** を追加します。「両方のサブタイプにあるが定義域が異なる属性（c・d：レベル、ジャンル）」と、「片方のサブタイプだけに存在する属性（e：年齢層）」を整理すると、図2のサブタイプ分割の意図がよく分かります。

## 設問3｜既存の表の構造を変えるSQL

図3は、サブタイプへの分割に合わせて、既存の「講座」表に「講座区分」列を追加し、サブタイプ側へ移す「レベル」列と「ジャンル」列を削除するSQL文です。

すでに存在する表の構造（列や制約の定義）を変更するときは **ALTER TABLE** 文を使うため、空欄fには **ALTER** が入ります。

```sql
ALTER TABLE 講座 ADD COLUMN 講座区分 VARCHAR(10)
ALTER TABLE 講座 DROP COLUMN レベル CASCADE
ALTER TABLE 講座 DROP COLUMN ジャンル CASCADE
```

- **CREATE TABLE**：新しい表を作成するときに使う命令
- **ALTER TABLE**：既存の表に列や制約を追加（ADD）・変更・削除（DROP）するときに使う命令
- **DROP TABLE**：表そのものを丸ごと削除するときに使う命令

なお、ここでの **DROP COLUMN ... CASCADE** は、「削除する列に依存している制約やビューなどがあれば、それらも一緒に削除する」という指定です（次の設問4で登場する、親の行を削除したときに子の行も連動して削除する **ON DELETE CASCADE** とは対象が異なります）。また、本文にあるとおり、列を削除する前には既存の「レベル」「ジャンル」のデータを保存しておき、新しく作ったサブタイプの表へデータを移行します。

## 設問4｜勤務日の特定と、削除に連動する範囲

### 設問4 g｜勤務年月日と講師コードを対にする

図1を見ると、「勤務日」エンティティの主キーは **（勤務年月日，講師コード）** の複合主キーです。同じ日に複数の講師が勤務し、1人の講師も複数の日に勤務するため、「いつ」「どの講師が」の2つをそろえて初めて1件の勤務日が特定できます。

**外部キー（FOREIGN KEY）** は、別の表の主キー（または一意キー）を参照して表どうしの関連を保つための制約です。図4の「勤務可能時間」表では、**FOREIGN KEY(勤務年月日, 講師コード) REFERENCES 勤務日(［ g ］)** と定義されているため、参照元の列の並びに対応させて、空欄gには **勤務年月日, 講師コード** を指定します。

なお、「勤務可能時間」表自身の主キーには「開始時刻」も含まれていますが、これは「同じ講師の同じ勤務日の中で、9:00〜12:00と14:00〜17:00のように複数の時間帯を登録できるようにするため」の列です。親である「勤務日」表のどの行を参照するかを指定する空欄gには、開始時刻は含めません。

### 設問4 h｜親の勤務日を消すと、どの行が消えるか

本文には「勤務日表の行を削除すると、それを参照する勤務可能時間表の行も自動的に削除される」という条件があります。親テーブル（参照先）の行が削除されたときに、それを参照している子テーブル（参照元）の行も連動して自動削除する外部キーの指定は **ON DELETE CASCADE** なので、空欄hには **CASCADE** が入ります。

例えば、講師T01の「2025-11-01」の勤務日データを1行削除すると、「勤務可能時間」表にある講師T01の「2025-11-01」の時間帯データ（午前・午後など）がすべて連動して削除されます（他の講師の2025-11-01のデータや、講師T01の別の日のデータは消えません）。

なお、本文には「その日に担当する講座がない場合に限り、勤務日を削除できる」という業務上のルールもありますが、そのチェック自体はプログラム側などで行い、実際に「勤務日」の行を削除した後のデータ連動をデータベースの **ON DELETE CASCADE** が担っています。

## 設問5｜同じ開催どうしを結合する

図5のSQLは、指定した講師（**:講師コード**）が指定した日（**:開催年月日**）に担当する講座コードの一覧を取得するものです。ここでは「開催スケジュール」表に **t0**、「講座担当割当」表に **t1** という別名（エイリアス）を付けて、**INNER JOIN**（内部結合）で結び付けています。

冒頭で確認したとおり、1つの「開催」を特定する主キーは **講座コード** と **開催番号** の2つの組です。したがって、「開催スケジュール（t0）」と「講座担当割当（t1）」で**同じ開催どうし**を正しく結合するには、この2つの列が両方とも一致している必要があります。空欄iに入る条件は次のとおりです。

```sql
ON t0.講座コード = t1.講座コード
   AND t0.開催番号 = t1.開催番号
```

もし誤って **ON t0.講座コード = t1.講座コード** だけで結合してしまうと、何が起きるでしょうか。冒頭の具体例で確かめてみましょう。

- **開催スケジュール（t0）**：講座K01の第1回（11月1日）と、第2回（11月8日）がある
- **講座担当割当（t1）**：講師T01は、K01の**第2回（11月8日）だけ**を担当している（第1回は別の講師が担当）

このとき、講座コードだけで結合してしまうと、講師T01の「K01・第2回」の担当データが、同じ講座コードを持つ「K01・第1回（11月1日）」のスケジュール行にもくっついてしまいます。その結果、**WHERE** 句で「11月1日」と「講師T01」に絞り込んでも、本来は担当していないはずのK01が誤って抽出されてしまいます（**SELECT DISTINCT** を書いても、誤って残ったK01は消えません）。

**複合主キーを持つ表どうしを結合するときは、主キーを構成するすべての列（講座コードと開催番号）を AND でつないで一致させる**ことが不可欠です。

## 次の問題でも使うこと

- **複合主キーの見抜き方**：「同じ受講者が同じ講座の別の日程を予約したらどうなるか」のように具体例を2行並べてみて、どの列が足りないと区別できなくなるかを考える。
- **スーパータイプ／サブタイプの分割基準**：一方の種類にしか存在しない固有属性（年齢層）だけでなく、属性名は同じでも種類ごとに定義域（取り得る値の集合）が異なる属性（レベル・ジャンル）もサブタイプへ分ける。
- **複合キーの参照と結合**：複合主キー（講座コード＋開催番号、勤務年月日＋講師コード）を外部キーで参照したり **JOIN** で結合したりするときは、構成するすべての列を漏れなく対応させる。
