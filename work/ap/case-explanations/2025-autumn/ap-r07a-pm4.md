# 問4 エッジコンピューティングによる動画配信

## この問題は、何を考える問題だった？

E社は、小学生のサッカーの練習試合を保護者のPCやスマートフォンへライブ配信するシステムを企画しています。カメラは観覧席に固定したままグラウンド全体を4Kで撮影し、その映像からボールの位置を自動で見つけて、ボール周辺だけをフルHD（FHD）で切り出して配信します。ただし、観覧席にはコンセント（電源）も有線LANもないため、**モバイルバッテリー**と**モバイル通信回線**だけでシステムを動かさなければなりません。

この問題では、**「限られた通信帯域とバッテリー容量の中で、どのように映像を処理して試合終了まで配信し続けるか」**を考えます。ハードウェアの基礎知識（設問1・設問2）から、エッジ側で処理を行う理由（設問3）、消費電力量の計算と省電力化の工夫（設問4）までが、すべて1つのシステム設計としてつながっています。

## まず、処理の順番と、使う資源を対応させよう

**エッジコンピューティング**とは、カメラやセンサなどの「データが発生する現場（エッジ）に近い機器」でデータを処理する考え方です。本問では観覧席に置くボードコンピュータがその役割を担います。撮影した高精細な元映像をそのまま全てクラウドへ送るのではなく、現場のボードコンピュータで必要な部分を切り出し、データ量を圧縮してからクラウドへ送信します。

図2と表2に示されたボードコンピュータ内の処理の流れは、次のとおりです。

| 処理の順番 | 主に使う装置 | 平均使用率 |
| --- | --- | --- |
| ① 4K動画を撮影する | カメラモジュール | 100% |
| ② 各フレームからボールの位置を検出する | GPU | 90% |
| ③ ボール周辺のFHD動画を切り出す | CPU | 80% |
| ④ 動画を圧縮する | 専用チップ | 90% |
| ⑤ クラウドへ送信する | モバイル通信装置 | 50% |

- **CPU**：プログラムの制御や一般的な処理を実行する中心的な装置
- **GPU**：画像処理や画像認識（ボール検出など）の並列計算を得意とする装置

なお、表2の条件では、②でボールの位置を検出できた場合は③で「ボール周辺のFHD動画」を切り出しますが、検出できなかった場合は代わりに「4K動画全体をFHDサイズへ縮小した動画」を作ります。そして、クラウド側が受け取った動画を保護者の端末へと配信します。

また、本文に出てくる**プロトタイプ**は試作品、**PoC（Proof of Concept：概念実証）**は「考えた仕組みや構成が実際の条件で成立するかを試作して確かめること」を指します。E社はこのPoCを通じて、映像の配信だけでなく「バッテリーが60分間の試合終了まで持つか」を検証しています。

## 設問1｜CPUの方式と、映像の接続口を選ぶ

### 設問1 a｜単純な命令セットはRISC

CPUが直接理解して実行できる命令の集まり（種類や書式の決まり）を**命令セット**といいます。

- **RISC（Reduced Instruction Set Computer）**：1つ1つの命令を単純にして回路をシンプルにし、省電力化や処理の効率化を図りやすい方式（ボードコンピュータやスマートフォン向けのCPUで広く採用されています）
- **CISC（Complex Instruction Set Computer）**：1つの命令で複雑な処理を行えるように豊富な命令を備えた方式

本文では「複雑な命令セットを用いるCISCではなく、単純な命令セットを用いる［ a ］」と対比されているため、空欄aは **エ（RISC）** です。

### 設問1 b｜ディスプレイにつなぐのはHDMI

**インタフェース**とは、機器どうしをつないでデータや信号をやり取りするための接続規格（接続口）のことです。ボードコンピュータからディスプレイへ映像信号を出力するインタフェースは **HDMI** なので、空欄bは **ウ** です。

他の選択肢も、つなぐ相手と用途で整理しておきましょう。

- **ア（CISC）・エ（RISC）**：CPUの命令セットの方式であり、接続インタフェースではない
- **イ（DCジャック）**：直流（DC）の電源ケーブルを差し込むための接続口
- **オ（RJ45）**：有線LANケーブル（イーサネット）をつなぐためのコネクタ

## 設問2(1) c｜1枚の映像から、1秒当たりの通信量へ進む

デジタル映像は、細かい色の点である**画素（ピクセル）**の集まりで構成されています。4K動画の「3,840×2,160」は、1枚の画像に横3,840個×縦2,160個の画素があることを表します。計算に使う3つの単位を確認しましょう。

- **bpp（bits per pixel）**：1画素の色を表すのに使うビット数（ここでは **24ビット**）
- **fps（frames per second）**：1秒間の動画に含まれる静止画（フレーム）の枚数（ここでは **60枚**）
- **bps（bits per second）**：1秒当たりに転送するビット数

無圧縮の4K動画の1秒当たりのデータ量は、「1枚の画素数 × 1画素当たりのビット数（bpp） × 1秒当たりの枚数（fps）」で求められます。

```
3,840 × 2,160 = 8,294,400 画素／枚
8,294,400 × 24 = 199,065,600 ビット／枚
199,065,600 × 60 = 11,943,936,000 ビット／秒
11,943,936,000 ÷ 1,000,000,000 = 11.943936 Gbps
```

設問の指示より、1Gbps＝10の9乗bps（1,000,000,000bps）としてGbps単位に換算し、小数第1位を四捨五入するため、空欄cの答えは **12** です。なお、bppもbpsも「ビット（bit）」の単位なので、バイト（Byte）へ換算する「÷8」の計算は不要です。

ちなみに、画面をFHD（1,920×1,080）に切り出して画素数を4分の1に減らしたとしても、無圧縮（24bpp・60fps）のままでは約2.986Gbps（＝約2,986Mbps）ものデータ量になります。本文のモバイル通信の上り実効速度は「数十Mbps」なので、切り出しただけでは到底送信できず、動画の圧縮が不可欠だと分かります。

## 設問2(2)｜圧縮の方式と、圧縮する装置を区別する

### 設問2(2) d｜動画を圧縮する方式を選ぶ

動画データを小さなデータ量へ圧縮する方式（規格）を選ぶ設問です。解答群の中で動画圧縮の規格を表すのは **H.265** なので、空欄dは **ア** です。

- **ア（H.265）**：H.264の後継にあたる代表的な動画圧縮規格（HEVCとも呼ばれます）
- **イ（MP3）**：音声データの圧縮形式
- **ウ（PNG）・エ（WebP）**：主に静止画（画像）で使われるデータ形式
- **オ（エンコーダ）・カ（デコーダ）**：圧縮や伸長を行う「装置・プログラム」の名称であり、圧縮方式（規格）の名前ではない

空欄dは「代表的な動画圧縮方式である［ d ］」、空欄eは「圧縮符号化する［ e ］」と書かれているため、規格名と装置名を混同しないように読み分けます。

### 設問2(2) e｜圧縮符号化するのはエンコーダ

データを規則に従って圧縮符号化する装置や回路を **エンコーダ** と呼ぶため、空欄eは **オ** です。逆に、圧縮されたデータを受け取って元の再生できる映像へ復号（伸長）する側を**デコーダ**と呼びます。ボードコンピュータはこれからクラウドへ送る動画を圧縮する側なので、エンコーダを使います。

## 設問2(3)｜専用チップへ任せると、何を別の仕事へ使えるか

ボードコンピュータ上では、動画の圧縮だけでなく、4K映像からの「ボール位置の検出」や「FHD動画の切り出し」も同時に行う必要があります。

もし動画の圧縮処理をCPUやGPUのソフトウェア処理で行うと、そちらに多くの計算能力を取られてしまいます。動画圧縮をハードウェアの専用チップ（エンコーダ）に任せれば、CPUやGPUを動画圧縮に使わずに済むため、**GPUの処理能力をボール位置の検出などに振り向けられる**ようになります。したがって、正解は **ア** です。

他の選択肢が適切でない理由も確認しておきましょう。

- **イ**：様々な圧縮方式へ柔軟に対応しやすいのはソフトウェア処理の特徴であり、特定方式向けに作られた専用チップの利点ではありません。
- **ウ**：専用チップ（ハードウェア）で圧縮したからといって、ソフトウェアで同じ方式に圧縮したときよりデータサイズが小さくなるとは限りません。
- **エ**：音声と映像を1つにまとめる処理は専用チップ固有の利点ではなく、そもそも本システムでは音声を配信しません。

## 設問3｜クラウドへ送る前に加工する理由

下線①では、ボードコンピュータ上で「ボール位置の検出 → 周辺映像の切り出し → 圧縮」を行ってからクラウドへ送信しています。なぜボール位置の検出までクラウド側に任せず、現場（エッジ）で行うのでしょうか。

もしクラウド側でボールの位置を検出するなら、切り出す前の「グラウンド全体の4K動画」をクラウドへ送り続けなければなりません。しかし、設問2(1)で確認したとおり、高解像度の元映像はデータ量が非常に大きく、現場で利用できる**モバイル通信の上り速度（数十Mbps）では帯域が足りず送信しきれない**からです。

- **帯域（帯域幅）**：通信回線が一定時間あたりに送ることができるデータ量の大きさ（通信容量・速度の上限）

つまり、この設計を選んだ背景には「モバイル通信の帯域が限られている」という通信面の制約があります。20字以内でまとめる公式解答例は、**「モバイル通信の帯域が不足する制約」（16字）**です。「エッジコンピューティングだから」と方式名を答えるのではなく、なぜ現場でデータ量を減らしてから送る必要があるのかという「回線側の制約」を答えるのがポイントです。

## 設問4(1)｜60分間の基本動作と、各装置の使用分を足す

**電力量（mWh：ミリワット時）**は、一定の時間に消費する電気エネルギーの総量を表します。問題文に与えられている各装置の消費電力量は「使用率100%で1時間動かしたときの値」であり、実際の消費電力量は使用率に比例します。

試合開始から終了までは **60分間＝1時間** です。ここで見落としやすいのが、**「何も処理をしていない起動状態でも、基本動作として1時間に1,500mWhを消費する」**という条件です。これは電源を入れた瞬間だけにかかる値ではなく、起動している1時間のあいだ常にベースとして消費される電力量なので、各装置の消費分と合わせて合計します。

| 内訳 | 計算 | 1時間分の電力量（mWh） |
| --- | --- | --- |
| 起動状態の基本動作 | 1,500 | 1,500 |
| CPU | 2,000×0.80 | 1,600 |
| GPU | 3,000×0.90 | 2,700 |
| 専用チップ | 400×0.90 | 360 |
| モバイル通信装置 | 500×0.50 | 250 |
| カメラモジュール | 100×1.00 | 100 |

```
1,500 + 1,600 + 2,700 + 360 + 250 + 100 = 6,510 mWh
```

合計すると、60分間の消費電力量は **6,510mWh** となります。用意したモバイルバッテリーの容量（5,000mWh）を1,510mWh上回ってしまうため、このままでは試合終了までバッテリーが持たないことが計算から裏付けられます。

計算する際は、基本動作の1,500mWhを足し忘れないこと、また元の数値がすでに「1時間（60分）当たり」のmWhで与えられているため、さらに60を掛けないことに注意しましょう。

## 設問4(2)｜検出に必要な情報を残し、1画素の情報量を減らす

設問4(1)の内訳を見ると、GPUの消費電力量（2,700mWh、使用率90%）が全体の4割以上を占めています。そこで、GPUで行う「ボール位置の検出」に渡す動画のデータ量を減らして、GPUの負荷（使用率）を下げたいと考えます。

動画のデータ量を減らすには、大きく分けて①解像度（画素数）を下げる、②フレームレート（fps）を下げる、③1画素当たりのビット数（bpp：色数・階調）を下げる、の3つの方法があります。それぞれの影響を本文の条件に照らして比べてみましょう。

- **① 解像度（画素数）を下げると**：グラウンド全体を写した広い画面の中で、小さく写っているボールを識別しにくくなるおそれがある。
- **② フレームレート（fps）を下げると**：1秒間のコマ数が減るため、速く動くサッカーボールの位置を滑らかに追いかけにくくなる。
- **③ 1画素のビット数（bpp）を下げると**：色の細かな違いは減るが、見つけたいサッカーボールは**白色と黒色**なので、フルカラー（24bpp）の豊富な色情報がなくても十分に検出できる。

したがって、解像度とfpsは保ったまま、ボール位置を検出する前の段階で**動画のbpp（1画素当たりのビット数）を下げる処理**を追加するのが適切です。15字以内の公式解答例は**「動画のbppを下げる。」（11字）**となります。

例えば、24bpp（フルカラー）から8bpp（グレースケールなど）へ変換すれば、画素数やfpsを変えずに1枚あたりのデータ量を3分の1に減らせます。bppを下げる変換処理そのもので少し電力を消費したとしても、最も電力を食っていたGPUの負荷が大きく下がることで全体の消費電力量が5,000mWh以下に収まり、試合終了までバッテリーが持つようになります。

## 次の問題でも使うこと

- **動画データ量の基本式**：「1枚の画素数（横×縦） × 1画素のビット数（bpp） × 1秒の枚数（fps）」で1秒当たりのビット数（bps）が求まる。ビット（bit）とバイト（Byte＝8bit）のどちらで問われているかを最初に確認する。
- **エッジコンピューティングの目的**：現場で処理を行う理由は、応答速度（リアルタイム性）だけでなく、「加工前の大容量データをそのまま送ると通信回線の帯域が不足する」という通信面の制約を解消するためでもある。
- **消費電力量の積算**：待機・起動時のベース消費電力と、各装置の「最大消費電力 × 使用率」を同じ時間単位（1時間など）にそろえて合計する。
- **データ削減のトレードオフ**：解像度（空間の細かさ）・fps（時間の細かさ）・bpp（色の細かさ）のうち、目的の処理（白黒のボール検出など）で削っても支障がない要素を選ぶ。
