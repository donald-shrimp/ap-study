# 問8 モバイルオーダーシステムの画面設計

## この問題は、何を考える問題だった？

カフェを運営するC社では、ドリンクのサイズやトッピングを細かくカスタマイズできることが人気ですが、混雑時には店頭での注文に時間がかかっていました。そこで、顧客自身のスマートフォンから商品の注文・決済を行える**モバイルオーダーシステム**を開発します。

この問題は、単に画面の見た目を決めるだけの問題ではありません。**「業務や利用者の要望を、画面項目定義書（部品の種類・選択肢・初期値・入力チェック・その他の仕様）へ漏れなく落とし込むこと」**、そしてテストで見つかった**「表示速度やセキュリティの課題を解決すること」**がテーマになっています。

## まず、画面項目の役割を分けよう

**画面コンポーネント（UI部品）**とは、ボタン、入力欄、選択リストなど、画面を構成する部品のことです。同じ「候補から選ぶ」という操作でも、**「1つだけ選ぶのか、複数選べるのか」「候補が最初から画面に見えているのか、タップしたときに開くのか」**によって適切な部品が変わります。

また、本文の画面項目定義書（表1・表2）では、1つの画面項目について次の5つの観点を分けて定義しています。

| 定義する欄 | 内容と本問での具体例 |
| --- | --- |
| **部品（コンポーネント）** | どのUI部品を使うか（例：ドロップダウンリスト、ラジオボタンなど） |
| **選択肢** | どんな候補を表示するか（例：対象店舗で扱う商品、受取り可能な時刻など） |
| **初期値** | 画面を開いたときに最初から入っている値（例：最寄り店舗、前回入力した電話番号など） |
| **入力チェック** | 注文確定時などに検証する条件（例：必須項目が選ばれているか、受取り時刻が範囲内か） |
| **その他の仕様** | 表示の並び順、スクロール方向、操作できる条件（活性／非活性）など |

例えば、「商品一覧を横2列のテーブルで表示する」と決めただけでは、どの商品を先頭に並べるかまでは決まりません。本文の要望と表1・表2の各欄を突き合わせて、**「どの欄に、どの条件が足りないか」**を探すのが設問2の解き方になります。

## 設問1(1)｜何を、何個、どのように選ぶかで部品を決める

図1の画面イメージと表1の仕様から、空欄a〜dに入る画面コンポーネントを解答群から選びます。

### 設問1(1) a｜三本線から、画面の移動先を開く

図1の画面右上にある「三本線のアイコン」をタップすると、商品紹介サイト・ログイン・顧客情報変更などへのリンクメニューが開きます。この三本線のアイコンで表されるメニュー部品を **ハンバーガーメニュー** と呼ぶため、空欄aは **カ** です。

他の紛らわしい選択肢との違いも押さえておきましょう。

- **ア（カルーセル）**：複数の画像やバナーを横スライドなどで順番に切り替えて表示する部品（図1の「季節のおすすめ商品」の表示などに使われます）
- **オ（パンくずリスト）**：Webサイト内でいま自分がどの階層（トップ ＞ カテゴリ ＞ 商品詳細など）にいるかを示すリンクの並び

### 設問1(1) b｜開いた候補の中から、一つを選ぶ

「店舗」や「受取り時刻」の欄は、普段は1行で表示されており、タップして選択すると候補のリストが下に開き、その中から1つを選びます。この部品は **ドロップダウンリスト（プルダウンメニュー）** なので、空欄bは **エ** です。

- **イ（コンボボックス）**：候補リストから選ぶだけでなく、テキストを直接自由入力することもできる部品
- **ク（リストボックス）**：最初から複数行の枠内に候補が並んで表示されており、スクロールして選ぶ部品

### 設問1(1) c・d｜一つだけの選択と、複数の選択を区別する

画面上に最初から見えている候補を選ぶ部品には、**ラジオボタン**と**チェックボックス**があります。

- **空欄c（利用形態・サイズ）**：「店内利用」か「テイクアウト」か、あるいはサイズが「S・M・L・自由指定」のどれかのように、**複数の候補から必ず1つだけを選ぶ（相互に排他的な選択）**には **ラジオボタン（キ）** を使います。
- **空欄d（トッピング）**：「コーヒーパウダー」と「チョコパウダー」の両方を選ぶことも、1つだけ選ぶことも、どちらも選ばないこともできます。このように**各候補を独立して0個以上いくつでも選べる（複数選択）**には **チェックボックス（ウ）** を使います。

したがって、空欄cは **キ（ラジオボタン）**、空欄dは **ウ（チェックボックス）** です。

## 設問1(2)｜正規表現の記号を、文字としての意味と区別する

**正規表現**は、文字列のパターン（使える文字の種類や繰り返しの回数など）を記号で表す記法です。電話番号の入力チェックでは、以下の条件を満たす必要があります。

- 数字（0〜9）とハイフン（「-」）を使える（例：03-1234-5678）
- 国際電話の国番号を表すため、先頭にプラス（「+」）が0回または1回付く場合も許す（例：+1-123-4567890）

ここで注意したいのが、正規表現の中では「+」は「直前のパターンの1回以上の繰り返し」、「[ ]」の中の「-」は「文字の範囲（0-9 など）」という特別な意味（メタ文字）を持つ点です。これらを単なる「文字としてのプラス（+）やハイフン（-）」として扱いたいときは、直前にエスケープ文字（本問では **¥**）を付けて **¥+** や **¥-** と書きます。

選択肢 **エ** の正規表現を分解して読んでみましょう。

```
¥+{0,1}[0-9¥-]+
```

| 正規表現の部分 | 本問の記法での意味 |
| --- | --- |
| **¥+** | 文字としてのプラス記号「+」 |
| **{0,1}** | 直前の要素が **0回または1回** 現れる（先頭の「+」はあってもなくてもよい） |
| **[0-9¥-]** | 数字（0〜9）または文字としてのハイフン「-」のどれか1文字 |
| **末尾の +** | 直前の要素（数字またはハイフン）が **1回以上** 繰り返される |

これにより、国内形式の「03-1234-5678」（先頭の「+」が0回）も、国際電話形式の「+1-123-4567890」（先頭の「+」が1回）も両方受け入れることができます。

他の選択肢が誤りである理由も確認しておきましょう。

- **ア**：先頭が「+」（エスケープなし）になっており、また **[0-9]** にハイフンが含まれていないため、ハイフン入りの電話番号を入力できません。
- **イ**：先頭のプラス記号に対応する記述がないため、「+1-123-4567890」のような国番号付きの番号を入力できません。
- **ウ**：**[0-9]+** となっており、数字以外のハイフンを入力できません。

したがって、正解は **エ** です（なお、この正規表現は「使える文字の種類と先頭の「+」の有無」をチェックするものであり、桁数やハイフンの位置まで厳密に制限するものではありませんが、4つの選択肢の中で本文の仕様を満たすパターンとしてエを選びます）。

## 設問1(3)｜表示したまま、操作できない状態にする

ドリンクのサイズ欄で「S」「M」「L」のいずれかのラジオボタンを選んでいる間は、「サイズ自由指定」の数値入力欄は画面に表示したまま、利用者が入力・変更できない状態にしておきます。そして、「自由指定」のラジオボタンを選んだときだけ入力できるように切り替えます。

このように、画面部品を表示したまま操作できない状態にすることを **非活性化**（または無効化／disabled）と呼びます。10字以内の公式解答例は **「非活性化」（4字）** です。部品そのものを画面から消してしまう「非表示」とは区別して押さえておきましょう。

## 設問2(1)｜受取り時刻の、抜けている上限を探す

本文の要望には、商品の受取り可能時刻について **「当日の開店時刻から閉店時刻の30分前まで」** という条件が書かれています。ところが、表1の「受取り時刻」の定義を見ると、「いつから（下限）」の条件だけが書かれていて、**「いつまで（上限）」の条件が抜けています**。

| 表1の欄 | 現在書かれている条件（下限のみ） | 抜けている条件（上限） |
| --- | --- | --- |
| **選択肢**（候補リストを作るとき） | 開店時刻以降、かつ画面表示時点の現在時刻＋15分以降 | **閉店時刻の30分前まで** |
| **入力チェック**（注文ボタンを押したとき） | 開店時刻以降、かつ注文ボタン押下時刻以降 | **閉店時刻の30分前まで** |

したがって、20字以内の公式解答例は **「閉店時刻の30分前までとする。」（15字）** です。

例えば閉店時刻が21:00の店舗なら、受取り時刻の上限は20:30になります。選択肢のリストを作る段階でも20:30までの候補しか出さないようにし、注文確定ボタンを押したときの入力チェックでも上限を超えていないかを確かめます（なお、画面を開いてから注文ボタンを押すまでに少し時間が経つことがあるため、下限の条件は選択肢生成時が「現在時刻＋15分以降」、注文ボタン押下時が「押下時刻以降」と使い分けられています）。

## 設問2(2)｜おすすめ商品を、どの位置に並べるか

本文には「店舗ごとのおすすめ商品や店舗独自商品を顧客にアピールしたい」という要望があります。一方、表2の「商品」テーブルの定義を見ると、「横2列で表示し、縦方向にスクロールする」ことは決まっていますが、**商品をどの順番で並べるか**が定義されていません。

スマートフォンの画面に一度に表示できる商品の数には限りがあります。もしおすすめ商品や店舗独自商品が一覧の下の方に並んでいると、最後までスクロールしない顧客の目にとまりません。そこで、どの商品を優先して上部に表示するかという **商品の並び順** を商品開発部に確認して定義する必要があります。10字以内の公式解答例は **「商品の並び順」（6字）** です。

## 設問3(1)｜見せるページだけでなく、読み込む量も分ける

テストを行うと、商品数が多い店舗で「注文画面の初期表示に時間がかかる」という問題が見つかりました。原因は、画面を開くときに**すべての商品の画像や情報を一度に読み込んでいること**です。

これを解決するには、商品一覧を複数のページに分割し、ページ番号や「次へ」ボタンで切り替えながら1ページ分の商品だけを取得・表示する **ページネーション**（ページ分割）を取り入れます。15字以内の公式解答例は **「ページネーション」（8字）** です。

例えば120商品を扱う店舗でも、1ページあたり20商品ずつのページネーションにすれば、画面を最初に開くときは先頭の20商品分のデータだけを読み込めばよいため、初期表示の時間を大幅に短縮できます（全120件のデータを最初にすべて読み込んでおいて、画面上の見た目だけ20件ずつ隠すやり方では初期通信量が減らないため、データ取得もページ単位で分けるのがポイントです）。

## 設問3(2)｜入力がSQLの命令へ混ざる問題を防ぐ

「おこのみ要望」の欄は、顧客がキーボードから自由に文字列を入力できるテキストボックスです。このような自由入力欄の値をそのまま文字連結してデータベースへの命令（SQL文）を組み立てると、悪意のある記号や命令文を入力されたときに、本来のSQL文の構造が書き換えられて不正な操作を実行される **SQLインジェクション** の脆弱性が生まれます。

この設問では、SQLインジェクションの対策として **適切でないもの（対策にならないもの）** を選びます。各選択肢の働きを確認しましょう。

| 選択肢 | 働きとSQLインジェクションに対する効果 |
| --- | --- |
| **ア：SQLで利用する記号の入力を制限する** | シングルクォート（「'」）やセミコロン（「;」）など、SQL文の構造を変える記号の入力を制限することで、攻撃の成立を防ぐ対策の1つになる |
| **イ：プレースホルダを使う** | SQL文の骨組みを先に確定させ、後から入力値を単なる「データ（値）」として割り当てる仕組み。入力値がSQLの命令として解釈されなくなるため、**最も根本的で確実な対策**になる |
| **ウ：WAF経由にする** | **WAF（Web Application Firewall）** はWeb通信の中身を検査し、SQLインジェクションなどの攻撃パターンを含む通信を検知・遮断する防御策になる |
| **エ：マルウェア対策ソフトを入れる** | ウイルスなどの不正プログラム（マルウェア）の感染を検知・駆除する対策であり、Webアプリの入力値がSQL文に混ざる脆弱性を防ぐ効果は**ない** |

したがって、対策にならない **エ** が正解です。

## 次の問題でも使うこと

- **UI部品の使い分け**：「1つだけ選ぶ（ラジオボタン／ドロップダウンリスト）」か「複数選べる（チェックボックス）」か、また「候補が常に見えている」か「開いたときに見える」かで部品を選ぶ。
- **正規表現のエスケープ**：「+」（1回以上の繰り返し）や「-」（範囲指定）のように正規表現で特別な意味を持つ記号を、文字そのものとして判定したいときはエスケープ文字を付ける。
- **非活性化と非表示の区別**：条件が満たされるまで操作できなくする「非活性化（disabled）」と、画面から見えなくする「非表示（hidden）」を区別する。
- **SQLインジェクション対策の基本**：自由入力値をSQL文へ直接連結せず、**プレースホルダ（バインド機構）**を使って命令とデータを分離する。
