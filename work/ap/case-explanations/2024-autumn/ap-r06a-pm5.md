# セキュアWebゲートウェイサービスの導入――中継先が変わると、許可する相手も変わる

## この問題は、何を考える問題だった？

E社ではこれまで、従業員のPCから社外のWebサイトへアクセスする際、社内のプロキシサーバを経由させることで危険なWebサイトへの接続を制限してきました。しかし、クラウドサービスの利用拡大に伴って通信量が増えたため、プロキシサーバの役割をクラウド上のセキュアWebゲートウェイサービスである**サービスZ**へ移行することにします。

```text
【移行前（図1）】
  社内PC → プロキシサーバ（ip3） → ルータ（NAPTでip1へ変換） → 社外のWebサイト（Y社SaaS：ip7 など）

【移行後（図2）】
  社内PC（ブラウザ → ソフトC） → ルータ → サービスZ（ip8） → 社外のWebサイト（Y社SaaS：ip7 など）
```

ネットワークの設定変更を考えるときは、**「PCが最初に通信を送る相手（中継役）」と「最終的な接続先のサービスから見える送信元IPアドレス」を切り分けてたどること**がポイントです。途中で中継する装置やアドレス変換を飛ばして「PC自身のIPアドレス」などと考えてしまうと、図の見方を誤ってしまいます。パケットが通る順番に沿って一つずつ確認していきましょう。

## まず、ネットワークの構成と通信経路を整理しよう

図1・図2に登場するネットワークの構成要素と用語を表で整理しておきましょう。

| 分類 | 用語・機器 | この事例での役割 |
| --- | --- | --- |
| **セグメント** | 内部・サーバ・**DMZ** | ネットワークを用途ごとに区切った範囲。従業員PCがある「内部セグメント」、業務サーバがある「サーバセグメント」、外部公開用・中継用サーバを置く「**DMZ（非武装地帯）**セグメント」の3つがある |
| **中継・制御機器** | **プロキシサーバ** | 社内PCの代わりに社外のWebサイトへアクセスする代理（中継）サーバ（導入前のDMZに設置、IPアドレスは **ip3**） |
| **中継・制御機器** | **FW（ファイアウォール）** | 送信元・宛先のIPアドレスやポート番号を見て、通信を通すか遮断するかを制御する機器 |
| **中継・制御機器** | **ルータ / L3SW** | **ルータ**は社内とインターネットの間で通信を転送し、外部へ出るときのアドレス変換も担う（WAN側IPは **ip1**）。**L3SW**は社内セグメント間の通信を転送するスイッチ |
| **プロトコル・クラウド** | **HTTP / HTTPS / SaaS** | **HTTP**（TCP/80）はWebの要求・応答のプロトコル、**HTTPS**（TCP/443）はそれを**TLS**で暗号化した通信。**SaaS**はクラウド経由で利用するソフトウェアで、Y社サービス（**ip7**）やZ社のサービスZ（**ip8**）はいずれもSaaS |

なお、社内のサーバセグメントにある**業務サーバ**を利用するときは、導入前も導入後もプロキシを通さずにPCから直接HTTPでアクセスします。「社外向けのWebアクセス」と「社内業務サーバへのアクセス」で経路が分かれている点をおさえておきましょう。

## 設問1(1) a｜IPアドレスだけでなくポート番号も変換するNAPT

**IPアドレス**はネットワーク上の機器を識別する番号です。社内ネットワークの機器には社内専用の**プライベートIPアドレス**を割り当て、インターネットへ出ていくときにルータで世界中で一意な**グローバルIPアドレス**へ変換します。

このとき、IPアドレスだけを1対1で変換する仕組みを「NAT」と呼びますが、本文の空欄aの直前には「プライベートIPアドレスと**ポート番号**の組を、グローバルIPアドレスと**ポート番号**の組に変換する」と書かれています。**ポート番号**とは、同じ機器の中で「どのアプリケーション・どの通信か」を区別するための番号です。IPアドレスだけでなくポート番号も一緒に変換すれば、1つのグローバルIPアドレス（ip1）を使って複数の社内通信を同時にインターネットへ出し、戻ってきた応答パケットもポート番号を手掛かりに元の通信へ正しく振り分けることができます。

この機能は **NAPT（Network Address Port Translation）** と呼ばれます。アルファベット4字の指定に従い、空欄aには**NAPT**が入ります。

## 設問1(2)｜Y社SaaSから見える送信元をたどる

設問1(2)は、図1（導入前）において、Y社SaaSがアクセスを許可する「接続元のグローバルIPアドレス」として登録すべきものを図1から選ぶ問題です。

図1に書かれている3つのIPアドレスの役割を、通信の通り道に沿って整理しましょう。

| 図1のラベル | どの機器・どの位置のIPアドレスか |
| --- | --- |
| **ip3** | E社内のDMZにある**プロキシサーバ**のプライベートIPアドレス |
| **ip1** | E社の**ルータのインターネット側（WAN側）**に割り当てられたグローバルIPアドレス |
| **ip7** | 接続先である**Y社SaaS**自身のグローバルIPアドレス |

社内PCからのアクセスを中継したプロキシサーバ（ip3）の通信は、インターネットへ出る際にE社のルータを通過し、設問1(1)のNAPT機能によって送信元IPアドレスが **ip3 から ip1 へと変換**されます。

したがって、インターネットの先にあるY社SaaSがパケットを受け取ったとき、そのパケットの「送信元IPアドレス」として見えるのは**ip1**です。Y社SaaS側で行う送信元IP制限には、「Y社から見てどのIPアドレスからアクセスがやってくるか」を登録するため、答えは**ip1**となります（社内のプライベートIPアドレスであるip3や、宛先自身のアドレスであるip7と混同しないよう注意しましょう）。

## 設問2(1) b｜Web上のアクセス先を表すURL

設問2(1)は、サービスZが危険なWebサイトへのアクセスを遮断する際に参照する「アクセス先の情報」をアルファベット3字で答える問題です。

たとえば「https://example.test/catalog/item」のように、通信プロトコル（https）やホスト名（example.test）、サーバ内の場所を表すパスなどを組み合わせて、Web上のアクセス先を指定する文字列を **URL（Uniform Resource Locator）** と呼びます。

本文には「アクセス先の空欄bやIPアドレスに基づいてアクセスを遮断する」とあるため、アルファベット3字で空欄bに入るのは**URL**です。なお、図1・図2には「DNSサーバ」も描かれていますが、**DNS**はホスト名をIPアドレスに変換する仕組みの名前であり、アクセス先そのものを表す文字列ではないため区別しましょう。

## 設問2(2)｜保護された領域で動かして確かめるサンドボックス

設問2(2)は、下線②「Webサイトからダウンロードされるプログラムを、サービスZ内の保護された領域で動作させることによって、不正なプログラムであるか否かを検査する機能」の名称を解答群から選ぶ問題です。

通常の業務環境（PCや社内ネットワーク）から隔離された安全な領域を用意し、その中で怪しいプログラムを実際に動かしてみて、ファイルの改ざんや不審な通信などの危険な挙動をしないか観察・検査する仕組みを**サンドボックス**と呼びます。したがって、答えは**ウ**（サンドボックス）です。

他の選択肢との違いも確認しておきましょう。

| 選択肢 | 機能名 | 下線②の説明との違い |
| --- | --- | --- |
| ア | HTTPSデコード | 暗号化されたHTTPS通信を復号して中身を検査できるようにする機能（本文の(2)に対応）であり、プログラムの隔離実行ではない |
| イ | アンチウイルス | マルウェア（不正プログラム）を検知・駆除する対策全般を指す言葉であり、「保護された領域で実際に動作させる」という方式を特定する名称ではない |
| **ウ** | **サンドボックス** | **保護・隔離された領域でプログラムを動作させて安全性を検査する仕組みであり、下線②に合致する** |
| エ | セキュアブラウジング | 安全にWebを閲覧するための機能全般を指す広い言葉であり、下線②の検査方式の名称ではない |
| オ | トラフィック検査 | ネットワークを流れる通信データを検査することであり、プログラムを保護領域で動かすこととは異なる |

## 設問3(1) c｜PCからの社外Web接続をサービスZへ集約する

サービスZの導入後（図2）は、社内のプロキシサーバを廃止し、各PCにインストールした「ソフトC」を**ローカルプロキシ**（そのPCの内部で動く中継役）として動作させます。Webブラウザの中継先をソフトCに設定すると、社外Webサイトへの通信は次の経路を通るようになります。

```text
Webブラウザ → PC内のソフトC → サービスZ（ip8） → 社外のWebサイト（Y社SaaSなど）
```

本文では、「ソフトCは、アクセス先が社外のWebサイトの場合、通信をサービスZ（宛先IPアドレス：空欄c）へHTTPSで転送する」と説明され、さらに表2（変更後のFWルール）でも内部セグメントから空欄cへの通信を許可しています。図2を見ると、Z社SaaS（サービスZ）のIPアドレスは**ip8**なので、空欄cには**ip8**が入ります。

もしFWでY社SaaS（ip7）だけを許可してしまうとサービスZへ接続できず、反対にインターネット上のあらゆる宛先への直接接続を許可してしまうと「必ずサービスZを経由させて検査する」という目的が果たせなくなってしまいます。まずすべてのPCの社外向けWeb通信をサービスZ（ip8）へ集約するのが、この設計の要です。

なお、導入後はY社SaaSへのアクセスもサービスZを経由するようになるため、本文にあるとおりY社SaaS側の「接続元グローバルIPアドレスの許可設定」も、E社のルータ（ip1）からサービスZ側のIPアドレスへと変更する必要があります。

## 設問3(2) d｜社内の業務サーバへの直接通信は残す

設問3(2)は、PCのWebブラウザの設定で「プロキシサーバ（ソフトC）を経由しない宛先」として指定する対象（空欄d）を答える問題です。

冒頭で確認したとおり、E社のPCは社内のサーバセグメントにある**業務サーバ**へHTTPで直接アクセスしています。もしこの通信までソフトCからクラウド上のサービスZ（ip8）へ転送してしまうと、社内ネットワークの中にある業務サーバへアクセスできなくなってしまいます。

したがって、従来どおりPCから直接アクセスさせるために「プロキシを経由しない例外」として設定する空欄dは**業務サーバ**です。

## 設問4 e｜導入前の4行はプロキシを挟む二段の通信

設問4は、E社のFWに設定する通信許可ルールの抜粋（表1：変更前、表2：変更後）の空欄e・fを埋める問題です。

まず表1（変更前）の4行を見ると、通信の送信元と宛先が次の2段階に分かれています。

- 1〜2行目：送信元「内部セグメント」→ 宛先「**空欄e**」（TCP/443 および TCP/80）
- 3〜4行目：送信元「**空欄e**」→ 宛先「インターネット」（TCP/443 および TCP/80）

導入前（図1）において、内部セグメントのPCからWeb通信（HTTPS/HTTP）を一旦受け取り、そこからインターネット上のWebサイトへ中継していたのはDMZにある**プロキシサーバ**です。したがって、空欄eには**プロキシサーバ**（またはそのIPアドレスである**ip3**）が入ります。

## 設問4 f｜HTTPSでサービスZへ接続するのでTCP/443

続いて表2（変更後）を確認しましょう。導入後はプロキシサーバ（ip3）が廃止され、内部セグメントのPC（ソフトC）からサービスZ（c＝ip8）へ直接**HTTPS**で通信を送ります。

表1を見ても分かるとおり、HTTPが使うポート番号はTCPの80番、**HTTPS**が使うポート番号はTCPの**443**番です。したがって、空欄fには**443**が入ります。変更後の表2のルールは、次の1行に集約されます。

| 導入後の送信元 | 宛先 | 許可するWeb接続 |
| --- | --- | --- |
| 内部セグメント | ip8 | TCP/443 |

なお、本文の注記にあるとおり、E社のFWは**ステートフルパケットインスペクション**機能（行きの通信を許可したとき、その通信状態を記憶して戻りの応答パケットを自動的に通す機能）を持っています。そのため、表1・表2には「通信を開始する向き（往路）」のルールだけを書けばよく、応答パケット用のルールを追加する必要はありません。

## 次の問題でも使うこと

- ネットワーク構成変更の問題では、「誰が通信を始めるか」「どの中継装置（プロキシ・ルータ・クラウドゲートウェイ）を通るか」「どこでアドレス変換（NAPT）が行われるか」を矢印で追いかける。
- 接続先での「送信元IPアドレス制限」を考えるときは、社内PCのプライベートIPアドレスではなく、インターネットへ出る出口で変換された後のグローバルIPアドレス（またはクラウド型プロキシのIPアドレス）を見る。
- 社内プロキシからクラウド型プロキシ（ローカルプロキシ経由）へ移行するときは、「社外向けWeb通信はクラウドへ集約する（TCP/443）」一方で、「社内業務サーバへの通信はプロキシ除外に設定して直接通信を残す」という切り分けを確認する。
- FWのルール表を読むときは、HTTP（TCP/80）とHTTPS（TCP/443）の対応、およびステートフルパケットインスペクション（往路を許可すれば復路の応答も通る）の前提を確認する。
