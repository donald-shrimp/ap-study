# スマートイヤホン――期限に間に合う範囲でクロックを下げる

## この問題は、何を考える問題だった？

G社は、音楽再生（音源再生）、通話、ノイズキャンセル、音声アシストの4つの機能を備えた左右独立型のワイヤレスイヤホンを開発しています。バッテリーを長持ちさせるためには制御部の消費電力をできるだけ抑えたいところですが、処理能力を落としすぎて音声処理が期限（周期）に間に合わなくなると、音飛びやノイズが発生してしまいます。

この大問では、次の3つの視点からリアルタイム制御の設計を読み解きます。

- **使用状況に応じたクロック周波数の選択**：どの機能が同時に動くかを整理して仕事量の割合を計算し、期限内に処理できる最小のクロック倍率を選ぶ（設問1・設問2）
- **周期タスクの優先度設計**：短い周期で動く音声処理が、長い処理に妨げられないように優先度を決める（設問3）
- **タスクの状態遷移とクロック停止の可否**：「実行可能状態」と「待ち状態」を区別し、クロック再開時間（5ミリ秒）とタスク周期の関係から停止できる条件を考える（設問4）

## 設問1(1) a・b｜通話と同時に使えない二つを拾う

設問1(1)は、通話が始まったときに停止させる2つの機能（空欄a・b）を答える問題です。

問題文の冒頭（表1の説明）を確認すると、「通話中は、**音源再生機能**と**音声アシスト機能**を使用できない」と明記されています。一方、ノイズキャンセル機能については「通話中もオン・オフを切り替えられる」とあります。

したがって、通話開始時に停止させる機能である空欄a・bには、**音源再生機能**と**音声アシスト機能**が入ります（aとbは順不同です）。「マイクやスピーカーを使うからこれも止まるはずだ」と推測するのではなく、問題文に書かれた同時使用の条件から確実に抜き出しましょう。

## 設問1(2)｜止まった制御部ではなく、動いている通信部が再開のきっかけを作る

設問1(2)は、待機時（クロックへの指示が0で、制御部へのクロック供給が止まっている状態）において、クロック部がクロック供給を再開するきっかけ（イベント）を選ぶ問題です。

クロックの供給が止まると、制御部はその時点の状態を保ったまま停止します。再びクロックが供給されれば続きから処理を再開できますが、**止まっている制御部自身が自分で命令を実行してクロックを再開させることはできません**。つまり、制御部とは別に動いているブロックからの通知が必要になります。

そこで表2の各ブロックの説明を見ると、**通信部**について「**内部に独自のクロックを持ち、電源オン後は常に動作する**」と書かれており、さらに「スマホからデータを受信すると、その旨をクロック部にも通知する」とあります。この通知をきっかけとして、クロック部は5ミリ秒後に制御部へのクロック供給を再開します。したがって、正解は**イ**（「スマホからのデータを受信」）です。

各選択肢の判断理由も比較しておきましょう。

| 選択肢 | 判断と理由 |
| --- | --- |
| ア 一定時間経過 | 一定時間の経過だけで自動的にクロックを再開するタイマのような仕組みは、本問の仕様（表2）にはありません |
| **イ スマホからのデータを受信** | **制御部が停止していても、独自のクロックで常時動作している通信部がデータを受信し、クロック部へ再開のきっかけを通知できます** |
| ウ 制御部からの指示を受信 | クロック供給が止まっている制御部は新たな指示を出すことができないため、再開のきっかけにはなりません |
| エ 電力部が電力を供給 | クロック停止中もイヤホンの電源自体はオンのまま電力が供給されています。電力供給は再開のきっかけを表すイベントではありません |
| オ 特定のキーワードを検出 | キーワード検出（特定語検出タスク）は制御部が行う処理なので、停止中の制御部では検出できません |

## 設問2｜同時に動くタスクの仕事量からc・d・eを求める

設問2は、表3の使用状況（「音源再生1」「音源再生2」「通話時」）ごとに、処理が間に合う最小のクロック指示値（空欄c・d・e）を求める問題です。

まず用語を整理しましょう。**タスク**とは、リアルタイムOSが実行を管理する処理の単位です。**起動周期**は「何ミリ秒ごとにその仕事が発生するか」という間隔であり、**実行時間**は「1回分の仕事に何ミリ秒掛かるか」を表します。表4に示された実行時間は「基準周波数（指示値1）のとき」の値です。なお、クロック周波数を変えると**実行時間**は変わりますが、音声データが届く間隔である**起動周期**は変わりません。

表4の周期タスクについて、基準周波数（指示値1）で動かしたときに「周期のうちどれだけの時間の割合（CPU稼働率）を使うか」を計算してみましょう。

| タスクと動作 | 周期（ミリ秒） | 基準での実行時間（ミリ秒） | 基準で必要な時間の割合 |
| --- | --- | --- | --- |
| マイク | 2 | 1.0 | 1.0÷2＝0.5 |
| スピーカー・音源再生 | 5 | 3.4 | 3.4÷5＝0.68 |
| スピーカー・通話 | 5 | 0.5 | 0.5÷5＝0.1 |
| 特定語検出 | 40 | 20 | 20÷40＝0.5 |

たとえば「マイク」タスクは2ミリ秒ごとに1.0ミリ秒働くため、基準周波数では全体の 1.0÷2＝0.5（50%）の時間を使います。同時に動くタスクの割合を足し合わせた合計値を、クロック周波数の倍率 r で割ったものが「倍率 r のときの時間の割合」です。この割合が **1（100%）を超えると、次々に発生する仕事を周期内に処理しきれなくなります**。省電力のために、割合が1以下に収まる**最小の倍率**を「0.5、1、1.5、2」の中から選びます（メインタスク・通信タスクの実行時間やタスク切替え時間は、設問の注記どおり無視します）。

3つの使用状況を順番に計算しましょう。

1. **音源再生1（空欄c）：音源再生オン・音声アシストオン**
   音声アシストのキーワード検出やノイズキャンセルのために「マイク」と「特定語検出」が動き、音楽出力のために「スピーカー・音源再生」が動きます。基準周波数での割合の合計は次のとおりです。

   `1.0÷2 + 3.4÷5 + 20÷40 = 1.68`

   倍率1.5では `1.68÷1.5 = 1.12` となり、1を超えてしまうため処理しきれません。倍率2にすれば `1.68÷2 = 0.84` となって1以下に収まるため、最小の倍率は **c＝2** です。

2. **音源再生2（空欄d）：音源再生オン・ノイズキャンセルオン・音声アシストオフ**
   ノイズキャンセル用の音声入力に「マイク」、音楽出力に「スピーカー・音源再生」を使います（音声アシストがオフなので「特定語検出」は動きません）。基準周波数での割合の合計は次のとおりです。

   `1.0÷2 + 3.4÷5 = 1.18`

   倍率1では1.18となり1を超えますが、倍率1.5にすれば 1.18÷1.5 ≈ 0.787 となって1以下に収まります。したがって、最小の倍率は **d＝1.5** です。

3. **通話時（空欄e）：通話オン（音源再生・音声アシストはオフ）**
   通話音声やノイズキャンセルの入力に「マイク」を使い、相手の声を出すために「スピーカー・通話」を使います。基準周波数での割合の合計は次のとおりです。

   `1.0÷2 + 0.5÷5 = 0.6`

   倍率0.5では `0.6÷0.5 = 1.2` となり1を超えてしまいますが、倍率1なら0.6で1以下に収まります。したがって、最小の倍率は **e＝1** です。

以上より、組合せとして適切なのは **オ（c＝2，d＝1.5，e＝1）** です。

| 選択肢 | 判断の決め手 |
| --- | --- |
| ア | c＝0.5では音源再生1の仕事量（基準の1.68倍）を処理しきれません |
| イ | c＝1、d＝1、e＝0.5のいずれも処理能力が不足します |
| ウ | c＝1.5では音源再生1の割合が1.12（＞1）となり不足します |
| エ | c＝2は足りますが、d＝1とe＝0.5で処理能力が不足します |
| **オ** | **すべての使用状況で期限内に処理できる最小の倍率（c＝2，d＝1.5，e＝1）に一致します** |
| カ | すべて2倍にすれば処理は間に合いますが、dとeを必要以上に高い周波数で動かすことになり、「消費電力を最小限に抑える」という目的に合いません |

## 設問3(1) f・g・h｜周期が短いタスクほど先に処理する

設問3(1)は、表4の周期タスク（マイク、スピーカー、特定語検出）に割り当てる優先度の順番（空欄f・g・h）を答える問題です。

リアルタイムOSでは、ただ計算結果が正しいだけでなく、**決められた期限（起動周期）までに処理を完了させること**が求められます。もし、1回の処理に時間が掛かる「特定語検出（周期40ミリ秒・基準実行時間20ミリ秒）」の優先度を高くしてしまうと、特定語検出が動いている間ずっと「マイク（周期2ミリ秒）」や「スピーカー（周期5ミリ秒）」の処理が待たされ、2ミリ秒や5ミリ秒という短い期限をあっという間に過ぎてしまいます。

そのため、周期的に動くタスクでは**「起動周期が短いタスクほど優先度を高くする」**のが基本原則です。周期の短い順に並べると、通信タスク・メインタスクに続く優先度は次のようになります。

- **空欄f（優先度・中）**：**マイク**（起動周期 2ミリ秒）
- **空欄g（優先度・低）**：**スピーカー**（起動周期 5ミリ秒）
- **空欄h（優先度・最低）**：**特定語検出**（起動周期 40ミリ秒）

このように設定しておけば、特定語検出やスピーカーの処理を実行している最中でも、2ミリ秒ごとにマイクの起動タイミングが来た瞬間にマイクの処理が割り込んで（プリエンプションして）先に実行され、マイクの処理が終わった後の残り時間でスピーカーや特定語検出の続きを進めることができます。

## 設問3(2)｜左イヤホンだけが特定語検出を生成する

設問3(2)は、表4のタスクのうち「右イヤホンでは生成されず、左イヤホンだけで生成されるタスク」を答える問題です。

冒頭で確認したとおり、表1・表2において音声アシストのキーワードを検出する役割は**左イヤホン**にだけ割り当てられています。メインタスクは「そのイヤホンで必要なタスクだけを生成する」仕様になっているため、右イヤホンでは生成されず左イヤホンだけで生成されるのは**特定語検出**タスクです。

## 設問4(1) i｜アイドルが実行できるとき、ほかは待ち状態

設問4(1)は、最も優先度が低い「アイドルタスク」が実行状態にあるとき、他のすべてのタスクがどの状態にあるか（空欄i）を答える問題です。

リアルタイムOSにおけるタスクの3つの状態を正確に区別しましょう。

- **実行状態**：現在、制御部（CPU）が割り当てられて実際に処理を進めている状態
- **実行可能状態**：実行する準備がすべて整っており、制御部の順番が回ってくるのを待っている状態
- **待ち状態**：データの到着や次の起動周期の到来など、処理を始めるための条件（イベント）を待っている状態

アイドルタスクは、すべてのタスクの中で**最も優先度が低い**タスクです。もし他のタスクの中に1つでも「**実行可能状態**」のタスクがあれば、OSはアイドルタスクではなくそちらのタスクに制御部を割り当てます。

言い換えると、アイドルタスクが実行状態になれるのは、**他のすべてのタスクがまだ次の起動タイミングやデータ到着を待っていて動けないとき、つまり「待ち状態」にあるときだけ**です。したがって、空欄iには**待ち状態**が入ります（日常会話の「順番を待っている」という意味に引きずられて「実行可能状態」と書かないよう注意しましょう）。

## 設問4(2)｜少し空いた時間でも、再開に5ミリ秒必要なら止められない

設問4(2)は、下線①について「待機時以外の使用状況（音楽再生中や通話中など）では、アイドルタスクが実行状態になったとしてもクロックの供給を停止（指示値0に）できない理由」を、タスクの起動周期の観点から40字以内で答える問題です。

音楽再生中や通話中であっても、マイクやスピーカーの1回分の処理が早く終われば、次の起動周期が来るまでの「ほんの1〜2ミリ秒の隙間」にアイドルタスクが実行状態になることがあります。しかし、そこでクロックの供給を止めてしまうとどうなるかを3ステップで整理しましょう。

1. **クロック再開に掛かる時間（表2）**：停止状態からイベントを受けてクロック供給が再開するまでに**5ミリ秒**掛かり、その間はどのタスクも実行できない。
2. **動いているタスクの起動周期（表4）**：待機時以外の使用状況では、起動周期**2ミリ秒**の「マイク」タスクや起動周期**5ミリ秒**の「スピーカー」タスクが動いているため、再開に5ミリ秒掛かると次の周期に間に合わない。
3. **起動周期の観点から40字以内でまとめる**：公式解答例は**「クロックの再開に掛かる5ミリ秒以下の周期で動くタスクがあるから」**（31字）です（「音が出なくなるから」といった結果だけでなく、再開時間の5ミリ秒とタスクの起動周期を結び付けて書くのがポイントです）。

## 次の問題でも使うこと

- クロック周波数を基準の r 倍にすると、タスクの**実行時間は 1/r 倍**になるが、外部から仕事がやってくる**起動周期は変わらない**。
- 周期タスクのCPU稼働率（実行時間 ÷ 起動周期）の合計を計算し、倍率 r で割った値が 1（100%）以下に収まる最小の倍率を選ぶことで、期限を守りつつ消費電力を抑えられる。
- リアルタイムOSの周期タスクでは、**起動周期が短いタスクほど優先度を高くする**ことで、実行時間の長いタスクによって短周期のタスクが期限遅れになるのを防ぐ。
- 「実行可能状態（いつでも動けるがCPUの順番待ち）」と「待ち状態（次の周期やイベントが来るまで動けない）」を区別する。最低優先度のアイドルタスクが動くのは、他の全タスクが**待ち状態**のときである。
