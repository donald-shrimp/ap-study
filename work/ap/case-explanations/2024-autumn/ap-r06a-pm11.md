# チャットボット導入における開発計画の監査

## この問題は、何を考える問題だった？

中堅家電メーカーのW社では、顧客からの製品に関する問合せへ自動回答するチャットボット（現行CB）を改善し、機械学習方式を用いた新しいチャットボット（新CB）を導入するプロジェクトを進めています。企画プロセス（概念実証であるPoCを含む）が完了した段階で、システム監査チームが「新CBの開発計画の適切性」を監査することになりました。

この大問で問われているのは、AIのアルゴリズムの細かな仕組みではなく、**「新CBが本番業務で期待どおりの効果を発揮できるように、学習データの準備・性能要件・評価基準・テスト体制が開発計画に漏れなく盛り込まれているかをどう確かめるか」**というシステム監査の視点です。

**監査**とは、監査対象が目的や基準に照らして適切に計画・運用されているかを、客観的な証拠（開発計画書などの文書や記録）を集めて確かめる活動です。監査人自身が新CBを開発・テストするのではなく、「想定されるリスクに対して、必要な作業・担当部門・判断基準が計画されているか」を点検します。

## 新CBは「答えの蓄積」と「言葉の解釈」を組み合わせる

各設問に入る前に、本文と図1に示された「現行CBの課題」と「新CBの仕組み」を整理しておきましょう。

| 構成要素・用語 | 本問での役割とポイント |
| --- | --- |
| **知識ベース** | よくある質問とその回答（**FAQ**）を登録・蓄積する場所です。新製品のFAQも発売に合わせて登録されます |
| **類義語DB** | 類似する言葉を整理し、言葉どうしの関連度合いを格納するデータベースです。初期納入時は一般的な語句のみ対応しています |
| **回答機能（自然言語処理）** | 顧客の入力テキストを**自然言語処理**（人が使う言葉をコンピュータで解析する処理）し、類義語DBと突き合わせることで、曖昧な言葉遣いの問合せでも適切なFAQへ結び付けます |
| **類義語DBの整備方法①：手作業入力機能** | 手作業入力データを基に、W社製品固有の語句や関連度合いを直接類義語DBへ反映する方法です |
| **類義語DBの整備方法②：機械学習** | 現行CBの回答履歴から抽出した文章を品詞別に分解し、AIモデル（ディープラーニング不使用）で機械学習して類義語DBを整備する方法です |
| **回答満足率と目標レベル** | 顧客から「役立った」と評価された割合が**回答満足率**（評価指標）であり、有効性を判断する合格ラインが**目標レベル**です |

たとえば利用者が「機械が冷えない」と質問したとき、FAQ側が「冷却機能が動かない」という表現で登録されていたとします。現行CBでは言葉の対応関係が分からず回答を表示できませんでしたが、新CBでは**自然言語処理**と**類義語DB**を組み合わせることで回答満足率の向上を目指しています。

また、企画段階で実施した **PoC（Proof of Concept：概念実証）** で品質向上の見込みが確認できた後も、本番導入に向けて「要件定義 → 追加の機械学習を含む設計 → 実装 → テスト → 受入テスト → 本番移行」を計画的に進める必要があります。

## 設問1(1) a｜学習に使うデータと、効果を測るデータを分ける

設問1(1)の空欄aは、表1（監査手続案）の項番1「テストでは効果があったにもかかわらず，本番では効果が認められないリスク」に対する監査手続（5字以内）を埋める問題です。

機械学習を使って類義語DBを整備し、その効果をテストするときは、言葉の関連度合いを学ばせるための**学習用データ**と、学習した結果が別の質問にも通用するかを評価するための**テスト用データ**を分けて準備する必要があります。

もし学習に使ったのと同じデータでテスト（評価）を行ってしまうと、「すでに学習で見た文章にうまく答えられただけ」なのに、あたかも未知の問合せにも高く対応できるかのように過大評価してしまうおそれがあります（練習で解いた問題とまったく同じ問題だけを本番の試験に出すと、初めて見る問題への対応力を正しく測れないのと同じです）。

また、本文の（3）③にも「現行CBのCB回答履歴から6か月分を**学習**用データ及びテスト用データとして，ランダムに抽出した」と対応する語句が書かれています。したがって、空欄aには **学習** が入ります。

- **公式解答例**：「学習」（2字）

## 設問1(1) b｜発売前の製品の言葉は手作業入力で補う

続いて空欄bは、表1の項番2「新製品の問合せに対して適切に回答できないリスク」に対する監査手続（5字以内）を埋める問題です。

まず、なぜ新製品の問合せに答えられなくなるのか、本文の条件をたどりましょう。
1. **知識ベース（FAQ）側**：（1）④と（3）①にあるとおり、新製品のFAQ自体は発売に合わせて知識ベースに登録されます。
2. **類義語DB側**：顧客の曖昧な質問をそのFAQへ結び付けるには、新製品に関する語句を類義語DBにも反映しなければなりません。しかし、**これから発売される新製品については、現行CBの過去の回答履歴に十分な問合せデータが存在しない**ため、過去履歴を使った「機械学習」だけでは類義語DBを整備できません。

そこで、図1と（3）②に示されたもう一つの整備方法である「**手作業入力**機能」を使って、新製品に関する語句を類義語DBへ反映する計画になっているかを確かめます。空欄の直後に「機能によって」と続いているため、空欄bには5字で **手作業入力** が入ります。

- **公式解答例**：「手作業入力」（5字）

## 設問1(2) c｜評価指標だけでなく、移行を認める目標レベルを決める

設問1(2)は、表1の項番3「受入テストで当初予定していた導入効果が出なかったにもかかわらず，再学習などの対応を行わずに本番運用へ移行してしまうリスク」に対する監査手続（空欄c）を、本文中の字句を用いて5字以内で答える問題です。

新CBの導入効果を測る「評価指標」として、本文では**回答満足率**（顧客から「役立った」という評価を得た割合）が使われています。しかし、「回答満足率を測る」と決めただけでは、何％に達すれば本番運用へ移行してよいのかを判断できません。**「どの水準に達すれば導入効果が十分だと認めるか」という合格基準**をあらかじめ定めておく必要があります。

たとえば「回答満足率80％以上なら目標達成」と決めた場合、「回答満足率」が評価指標であり、「80％以上」がその指標に設定した達成基準です。もし受入テストでの測定結果が75％だったなら、割合は測定できていても基準には届いていないため、再学習などの対応が必要だと判断できます。

本文の（3）③を確認すると、「回答満足率を指標にして，効果の**目標レベル**を定め，新CBの有効性を判断している」と明記されています。表1項番3が求めているのは「具体的な効果の［c］が定められていること」なので、空欄cには **目標レベル** が入ります（「回答満足率」と答えると、基準の高さではなく指標名を答えたことになってしまうため注意しましょう）。

- **公式解答例**：「目標レベル」（5字）

## 設問1(3) d｜記録を残し、関係者がレビューする

設問1(3)は、表1の項番4「テストで発見された不具合について，原因の特定が遅れたり，同じ不具合が本番で再発したりするリスク」に対する監査手続（空欄d）を5字以内で答える問題です。

テストで不具合（期待したとおりに動作しないこと）が見つかったとき、テスト結果や不具合への対応状況を文書化して保管しておけば、後から経緯をたどることができます。

しかし、ただ記録を作って保管するだけでは、未解決の不具合が残っているのに見落とされたり、不十分な修正のまま完了扱いにされたりするおそれがあります。そこで、記録されたテスト結果と不具合対応の状況をプロジェクト関係者が点検・確認する **レビュー** の計画が必要になります。

項番4の1つ目の箇条書きは「定められた手順どおりにテストを実施する計画」、2つ目の箇条書き（空欄d）は「テスト結果と不具合対応の記録を関係者がレビューする計画」をそれぞれ確認しています。

- **公式解答例**：「レビュー」（4字）

## 設問2(1) e｜学習が予定に間に合うかは性能要件で確かめる

設問2(1)は、［監査部長の指示］（1）「設計における追加の機械学習では，類義語DBの整備がスケジュールどおり完了しないおそれがある。機械学習を実行するサーバに対する非機能要件の一つである［e］が，PoCを実施した際の実績データから導いた要件になっているか確かめること」の空欄eを解答群から選ぶ問題です。

システム開発の要件は、大きく次の2つに分けられます。
- **機能要件**：「システムが何をするか（どんな機能を持つか）」を定める要件
- **非機能要件**：「システムがどのような品質や条件で動作するか（処理速度、安全性、変更のしやすさなど）」を定める要件

本文の（3）②には、「PoCでは，機械学習によって類義語DBを整備する際のサーバ処理に想定以上の時間を要していた」という事実が書かれています。設計段階でさらに多くのデータを使って追加の機械学習を行う際、スケジュールどおりに処理を完了させるには、**必要なデータ量を予定時間内に処理できるだけの処理時間・処理能力（サーバの性能）**が要件として定められている必要があります。したがって、空欄eには **イ（性能要件）** が入ります。

各選択肢の違いも比較しておきましょう。

| 選択肢 | 主に定める内容 | 監査部長の指示（1）との対応 |
| --- | --- | --- |
| ア 外部インタフェース要件 | 他システムとの接続方式やデータの受渡し形式 | サーバの機械学習処理がスケジュールどおりに完了するかどうかを直接定めるものではありません |
| **イ 性能要件** | **応答時間・バッチ処理時間や処理能力（スループット）・資源使用量** | **PoCで学習処理に時間が掛かった実績を踏まえ、予定期間内に追加学習を終えられる処理能力を定める要件に合致します** |
| ウ セキュリティ要件 | 不正アクセス対策や情報漏えい防止などの情報保護 | 今回の指示は不正利用や情報漏えいを問題にしているわけではありません |
| エ 保守性要件 | 稼働後のプログラム修正や設定変更のしやすさ | 設計段階での機械学習処理に掛かる所要時間とは観点が異なります |

## 設問2(2) f｜ランダムに選んでも、元の期間にない製品は補えない

設問2(2)は、監査部長の指示（2）〜（4）における空欄f・g・hに入れる適切な字句を、それぞれ10字以内で答える問題です。

まず指示（2）の空欄f（「新製品だけでなく，現行の［f］に関する問合せへの回答について，学習用データが不十分で，適切に回答できないおそれがある」）を考えましょう。

1. **現行CBの課題を振り返る**：
   ［予備調査の結果］（1）①に、「W社では，**季節性のある製品**を多く取りそろえているので，顧客から寄せられる問合せ数は，季節性のある製品では季節によって偏りがある」と明記されています。
2. **抽出方法の弱点と結び付ける**：
   （3）③にあるとおり、PoCでは「直近6か月分のCB回答履歴」から学習用データとテスト用データをランダムに抽出していました。**ランダム抽出（無作為抽出）**は対象期間の中から偏りなく選ぶ方法ですが、**そもそも抽出元の期間に含まれていない季節の問合せを生み出すことはできません**。たとえば4月から9月の履歴だけが抽出元だった場合、その6か月に記録のない冬物製品の問合せは、何回ランダム抽出しても選ぶことができません。

したがって、発売前の新製品だけでなく、現行の **季節性のある製品** についても学習用データが不足するおそれがあります。

- **公式解答例**：「季節性のある製品」（8字）

## 設問2(2) g｜効果の見込みを、本番移行に先立って評価する

次に指示（3）の空欄g（「表1項番3について，新CBの有効性を確保するために，［g］に先立って，プロジェクト運営委員会が，当初予定の導入効果が得られる見込みを評価する計画になっているか確かめること」）を考えましょう。

表1の項番3が扱っていたのは、「受入テストで当初予定していた導入効果が出なかったにもかかわらず、再学習などの対応を行わずに本番運用へ移行してしまうリスク」でした。

もし導入効果が不十分なまま本番運用へ切り替えてしまうと、顧客からの問合せに適切に回答できず混乱を招いてしまいます。そのため、プロジェクト運営委員会は開発計画書案を承認するだけでなく、テストが進んだ段階で、遅くとも **本番移行**（開発・テストしたシステムを本番環境へ切り替えること）に先立って導入効果の見込みを評価し、移行の可否を判断する計画になっている必要があります。

設問1(2)cで定めた「目標レベル」という判断基準を使い、空欄gの「本番移行」の前に達成見込みを評価し、未達なら再学習などの対応をとるという一連の流れになります。

- **公式解答例**：「本番移行」（4字）

## 設問2(2) h｜顧客サービス部が受入テストに参加する

最後に指示（4）の空欄h（「現行CB導入時における問題点を踏まえて，今後の開発プロセスにおいて顧客サービス部による［h］が適切に実施される計画になっているか確かめること」）を考えましょう。

［予備調査の結果］（1）⑤で現行CB導入時の失敗経緯を確認すると、「現行CBを導入した際には，**受入テスト**を顧客サービス部員が参加せずに開発担当者だけが実施したことから，新製品に関する問合せに対して適切に回答できないなど，本番移行後に混乱を招く問題点があった」と書かれています。

**受入テスト（承認テスト）**とは、システムを利用する業務部門（システムオーナーである顧客サービス部）が主体となり、「実際の業務で問題なく使えるか」を確かめるテストです。開発担当者だけで機能の動作確認を行っても、顧客が実際に使う曖昧な表現や、新製品で求められる回答品質までは十分に検証しきれません。

したがって、今回は顧客サービス部による **受入テスト** が適切に実施される計画になっているかを監査手続に追加して確かめます。

- **公式解答例**：「受入テスト」（5字）

## 次の問題でも使うこと

- システム監査の問題では、「想定されるリスク（何が起きると困るか）」と「それを防ぐために開発計画や運用ルールに盛り込むべき統制（誰が・いつ・何を基準に・どう確認するか）」を1対1で対応づける。
- 機械学習を利用したシステムでは、①**学習用データとテスト用データの分離**（過大評価の防止）、②**学習データの網羅性**（未発売の新製品は**手作業入力**、**季節性のある製品**は対象期間・網羅性の考慮）、③**学習処理の性能要件**（予定時間内に処理が終わるか）の3つの観点を点検する。
- 導入効果の評価では、単なる評価指標名（回答満足率など）だけでなく、合否を判断する具体的な基準値（**目標レベル**）を定め、**本番移行**に先立って利用部門参加の**受入テスト**と運営委員会の評価を行う計画になっているかを確認する。
