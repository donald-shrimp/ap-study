# トレーディングカードの個人間売買サイト――業務の約束を表の関係とSQLへ移す

## この問題は、何を考える問題だった？

S社は、個人間でトレーディングカードを売買できるWebサイトを構築しようとしています。このサイトでは、出品・購入・支払・発送・評価という一連の手続きを管理し、取引が完了した後に手数料を差し引いて出品者へ代金を支払います。データベース設計では、これらの情報を1つの巨大な表に詰め込むのではなく、「何を管理対象（表）とするか」「表と表がどの列でどう結び付くか」を整理して設計します。

この大問では、次の3つのステップを順番に考えていきます。

1. **業務のルールをE-R図の「対応関係（1対1・1対多）」や「属性（列）」として表現すること（設問1）**
2. **階層構造をもつカテゴリやキーワード条件をSQLで検索すること（設問2）**
3. **検索を高速化するために、どの列にB-treeインデックスを設定すべきか判断すること（設問3）**

カテゴリの親子関係や利用者同士のフォロー関係のように、「同じ種類の対象どうしが異なる役割で結び付く関係」をどう表すかに注目しながら読み進めていきましょう。

## まず、図1（E-R図）の読み方とルールを整理しよう

図1のE-R図（Entity-Relationship Diagram）の表記ルールと用語を表で整理しておきましょう。

| 項目 | 図1での表記・意味 | 読み取るときの注意点 |
| --- | --- | --- |
| **エンティティと属性** | 四角形が**エンティティ（表）**、その中の項目が**属性（列）** | たとえば「カテゴリ」は表名、「カテゴリID」「カテゴリ名」「上位カテゴリID」は列名にあたる |
| **主キーと外部キー** | **主キー**は実線の下線、**外部キー**は破線の下線 | 主キーかつ外部キーである列（フォロー表の2列など）には、主キーの実線下線だけが付く |
| **1対1の関連** | **矢印のない実線** | 1件の取引に1件の発送が対応するような場合を表す |
| **1対多の関連** | **片側に矢印がある実線**（矢印の先が「多」） | 「業務が進む順番」ではなく、**対応する件数（1対多）**を表す |
| **多対多の関連** | **両側に矢印がある実線** | 関係データベースの表にするとそのままでは扱えないため、間に交差エンティティ（フォロー表など）を挟んで2つの「1対多」に分解する |

## 設問1 a・b｜自己参照の1対多と、取引に対する1対1

まず空欄a（カテゴリ表の関連）を見ましょう。表1によると、カテゴリは「ブランド」やその中の「シリーズ」のように階層化されています。1つの上位カテゴリ（親）の下に複数の下位カテゴリ（子）が属し、各下位カテゴリの行には親を指す「上位カテゴリID」を持たせます。たとえば上位カテゴリ「ブランドA」の下に「シリーズB」と「シリーズC」があるなら、2つの下位カテゴリ行から同じ「ブランドA」のカテゴリIDを参照することになります（なお、親を持たない最上位カテゴリでは、上位カテゴリIDがNULLになります）。

このように、ある表の行から同じ表の別の行を参照する関係を**自己参照（再帰的関連）**と呼びます。対応関係は**上位カテゴリ1対下位カテゴリ多**になるため、原図へ描くaの形を言葉で表すと「**カテゴリの右側から折り返し，同じカテゴリへ戻る左向き矢印（上位カテゴリ1：下位カテゴリ多）。**」となります（原図の折り返し線では、下側の戻り先に矢印を付けます）。

次に空欄b（取引表と発送表の関連）を見ましょう。表1には「1取引の商品を分割して発送することはできず、複数の取引の商品をまとめて発送することもできない」と定められています。つまり、取引1件に対して発送1件が対応するため、bの描き方は「**取引と発送を結ぶ矢印のない実線（1対1）。**」となります。

## 設問1 c｜配送状況を問い合わせる追跡番号

設問1の空欄cは、「発送」エンティティ（発送表）に必要な属性（列）を補う問題です。

表1の「発送」の説明を見ると、「S社は発送商品の**追跡番号**を管理し、配送業者のWebサイトと連携して配送状況を確認できるようにする」と書かれています。したがって、発送表の空欄cに入るのは**追跡番号**です。

すでに発送表には主キーとして「発送ID」がありますが、発送IDはあくまでS社のシステム内部で発送データを識別するための番号です。配送業者のWebサイトへ配送状況を問い合わせるためには、それとは別に配送業者が発行する**追跡番号**を記録しておく必要があります。

## 設問1 d｜多対多をフォロー表で二つの1対多に分ける

表1の「利用者」と「フォロー」の要件を見ると、1人の利用者は複数の利用者をフォローでき、逆に1人の利用者が複数の利用者からフォローされることもあります。つまり、利用者どうしは本来「多対多」の関係にあります。

関係データベースでは、この多対多の関係をそのまま1本の線で持つのではなく、「誰が（フォロー元利用者ID）」「誰を（フォロー先利用者ID）」フォローしたかというペアを1行ずつ記録する**フォロー表**（このような関連を記録する表を**交差エンティティ**または関連エンティティと呼びます）を間に挟むことで、**2つの「1対多」の関係**に分解します。

たとえば、フォロー表に次の3行が入っている場面を考えてみましょう。

| フォロー元利用者ID | フォロー先利用者ID |
| --- | --- |
| 1 | 2 |
| 1 | 3 |
| 4 | 2 |

この表を見ると、「フォロー元が利用者1の行」が2行あり、「フォロー先が利用者2の行」も2行あります。つまり、「フォローする側（フォロー元）」として見ても、「フォローされる側（フォロー先）」として見ても、**利用者1人に対してフォロー表の複数行が対応する（利用者1：フォロー多）**ことが分かります。

図1の「利用者」と「フォロー」を結ぶ2本の線のうち、上側の線はすでに「フォロー元」としての1対多（利用者からフォローへ向かう矢印）を表しています。したがって、下側の空欄dには「フォロー先」としての1対多を描けばよく、描き方は「**利用者からフォローへ向かう右矢印（利用者1：フォロー多）。**」となります（矢印の先はフォロー表側です）。

たとえば上の例で、利用者2が新しく商品を出品したときに通知を受け取るのは、利用者2をフォロー先にしている「利用者1」と「利用者4」です。フォロー元とフォロー先の2つの役割を分けて管理することで、誰から誰へのフォローかを正確に表現できます。

## 設問2 e・f｜指定カテゴリから、子・孫へ繰り返し広げる

設問2は、図2の出品商品検索SQLの空欄e〜hを埋める問題です。

まずカテゴリの絞り込み条件を確認しましょう。本文によると、カテゴリを指定して検索するときは「指定されたカテゴリ自身」だけでなく、「その下位にあるすべてのカテゴリ（子カテゴリ、孫カテゴリ……）」に属する出品商品も検索対象に含めます。単純に1回だけ親子を結合するだけでは「すぐ下の子カテゴリ」までしか取得できないため、得られた結果を次の検索の入力として繰り返し下位へたどっていく**再帰的な問合せ（再帰共通テーブル式）**を使います。

まず空欄eには **WITH RECURSIVE** を入れ、一時的な検索結果に「指定カテゴリ」という名前を付けて定義します。カッコの中の構造は、前半の「出発点を選ぶSELECT文」と、後半の「そこから子・孫を繰り返し探すSELECT文」の2つに分かれています。

1. **前半のSELECT文（探索の出発点）**：
   WHERE句の「A.カテゴリID = :カテゴリID」によって、利用者が指定したカテゴリ1行を取り出します（先頭にコロンが付いた「:カテゴリID」は**埋込み変数（ホスト変数）**と呼ばれ、プログラムの実行時に検索条件の値が渡される場所です）。
2. **後半のSELECT文（親から子へ広げる繰り返し）**：
   すでに「指定カテゴリ」に入った親行Cに対して、WHERE句の「B.上位カテゴリID = C.カテゴリID」を満たすカテゴリB（つまりCを親に持つ子カテゴリ）を探します。新しく子が見つかると、次の繰り返しではその子を新たなCとしてさらに下位の子（孫）を探していきます。
3. **前半と後半をつなぐ空欄f**：
   出発点の結果と、繰り返しで見つかった結果を結合して積み重ねていくため、空欄fには集合演算子の **UNION ALL** が入ります。

たとえば指定したカテゴリIDが「1」で、その子が「2」と「3」、さらに「2」の子が「4」だった場合、最初に「1」が選ばれ、次のステップで「2・3」が加わり、その次のステップで「4」が加わって、「指定カテゴリ」には「1・2・3・4」が揃います。

ここで後半の条件「B.上位カテゴリID = C.カテゴリID」は、もし比較する列を取り違えて「B.カテゴリID = C.上位カテゴリID」と書いてしまうと、「すでに得たCの親（上位）を探す」という逆向き（上向き）の探索になってしまう点に注意しましょう。

## 設問2 g｜出品が属するカテゴリと検索対象を結合する

再帰問合せによって、検索対象となるカテゴリの一覧が「指定カテゴリ」に集まりました。メインのSELECT文では、この「指定カテゴリ」と「出品」表を **INNER JOIN（内部結合）** で結び付け、対象カテゴリに属する出品行だけを取り出します。

結合条件を書くON句（空欄g）では、「出品された商品が属しているカテゴリID」と「指定カテゴリに含まれるカテゴリID」が一致する行を組み合わせます。したがって、空欄gには **出品.カテゴリID = 指定カテゴリ.カテゴリID** が入ります。

「出品ID」と「カテゴリID」はどちらも名前にIDが付いていますが、識別している対象が異なります。ここでは「どのカテゴリの商品か」を照合するため、両方の表の**カテゴリID**どうしを等号で結びます。

## 設問2 h｜部分一致の前後へ%を連結する

続いて、WHERE句の末尾にあるキーワード検索（空欄h）を見ましょう。本文には「商品名または商品説明にキーワードを含む（部分一致）」という条件があります。

SQLで文字列のパターン一致を調べるには **LIKE** 演算子を使います。LIKEのパターン文字列において、パーセント記号（%）は「0文字以上の任意の文字列」を表すワイルドカードです。キーワードの前後両方に%を付ければ、前後にどんな文字があってもキーワードが含まれてさえいれば一致（部分一致）します。

SQLで文字列どうしを連結する演算子は **||** です。ワイルドカードの%は文字リテラルなので単一引用符（'）で囲って **'%'** と書き、埋込み変数の **:キーワード** と連結します。したがって、空欄hには **LIKE '%' || :キーワード || '%'** が入ります。

たとえばキーワードに「限定」が渡された場合、連結後のパターンは「%限定%」となり、「限定カード」にも「カード限定版」にも一致します。このとき、埋込み変数まで単一引用符で囲んで「':キーワード'」と書いてしまうと、変数の値ではなく「:キーワード」という文字列そのものを探してしまうため、引用符で囲むのは前後の「'%'」だけにするのがポイントです。

また、「商品名」か「商品説明」の**どちらか一方**にでも含まれていればよいため2つのLIKE条件を **OR** でつなぎますが、そのOR条件全体を丸括弧（カッコ）で囲むことで、「出品価格・商品状態・出品状況のAND条件」がどちらの場合にも必ず適用されるようにしています。なお、価格条件に使われている **BETWEEN** は下限値と上限値の両端を含みます。

空欄e〜hを埋めた完成形のSQL全体は次のようになります。

```sql
WITH RECURSIVE 指定カテゴリ(カテゴリID, カテゴリ名, 上位カテゴリID) AS (
  SELECT A.カテゴリID, A.カテゴリ名, A.上位カテゴリID
    FROM カテゴリ A WHERE A.カテゴリID = :カテゴリID
  UNION ALL
  SELECT B.カテゴリID, B.カテゴリ名, B.上位カテゴリID
    FROM カテゴリ B, 指定カテゴリ C WHERE B.上位カテゴリID = C.カテゴリID
)
SELECT * FROM 出品
  INNER JOIN 指定カテゴリ
  ON 出品.カテゴリID = 指定カテゴリ.カテゴリID
  WHERE 出品.出品価格 BETWEEN :下限価格 AND :上限価格
    AND 出品.商品状態 = :商品状態
    AND 出品.出品状況 = :出品状況
    AND (出品.商品名 LIKE '%' || :キーワード || '%'
         OR 出品.商品説明 LIKE '%' || :キーワード || '%')
```

## 設問3(1)｜B-treeは値の順序を利用する索引

設問3は、検索処理を高速化するための**インデックス（索引）**の設計に関する問題です。

データベースの**インデックス**は、本の巻末にある索引と同じように、表の全行を先頭から1行ずつ調べなくても（フルスキャンしなくても）目的の行を素早く見つけるための仕組みです。中でも標準的に使われる **B-treeインデックス** は、列の値を大小の順序付きの木構造（ツリー構造）で管理し、枝の分岐をたどって目的の値や範囲を探します。木の高さが偏らないようにバランスが保たれるため、データ件数 n に対して探索の段数はおおむね log n に比例する緩やかな増え方（計算量 **O(log n)**）に抑えられます。

ただし、インデックスを使えばどんな検索でも常に速くなるとは限りません。ここで重要になるのが**カーディナリティ**（その列に含まれる異なる値の種類数）と**値の分布**です。たとえば値の種類が「1・2・3」の3種類しかなく（低カーディナリティ）、どの値も均等に入っている場合、1つの値を指定しても表全体の約3分の1もの行が該当してしまいます。このように大量の行を取り出す場合は、インデックスをたどるよりも表をまとめて読み込んだ方が速いこともあります。

設問3(1)でB-treeインデックスの特徴として適切なものを3つ選ぶと、答えは **ア，ウ，オ** です。各選択肢の判断理由を整理しましょう。

| 選択肢 | 判断 | 理由 |
| --- | --- | --- |
| **ア** | **適切** | **AND条件で等値条件などを組み合わせて候補を絞り込む検索に有効です。一方、NOT条件（〜以外）は該当する行の範囲が広くなりやすく、通常のB-treeインデックスによる絞り込みには適しません** |
| イ | 不適切 | 元の列の値に対して作成した通常のインデックスは、WHERE句でその列に演算や関数・型変換を施した結果の順序とは対応しないため、そのままでは使えません |
| **ウ** | **適切** | **値の分布に偏りが小さければ、どの値を検索条件に指定しても該当する行数が極端に変動しにくく、検索性能が安定しやすくなります** |
| エ | 不適切 | カーディナリティが低い（値の種類が少ない）列では、特定の値を指定しても多くの行が残ってしまうため、インデックスによる絞り込み効果は小さくなります |
| **オ** | **適切** | **木構造の根から葉まで分岐をたどって特定の行を探すため、基本的な探索の計算量は木の高さに対応する O(log n) で表されます** |
| カ | 不適切 | 行の挿入時も木構造をたどって挿入位置を探すため、基本的な計算量は O(log n) です。全行数に比例する O(n) とする説明は誤りです |
| キ | 不適切 | B-treeインデックスは値を順序付けて管理しているため、等号（=）だけでなく大小比較や範囲検索（出品価格のBETWEENなど）にも利用できます |

## 設問3(2) 出品表・カテゴリ表｜検索で使い、十分に絞れる列を選ぶ

設問3(2)は、図2のSQLを高速化するために、「出品」表と「カテゴリ」表のどの列にB-treeインデックスを設定すべきかを答える問題です。

本文に示されたS社のインデックス設定方針と前提条件を確認しましょう。

1. **絞り込み効果の基準**：特定の値を指定したとき、**表全体の5%以下（20分の1以下）**に絞り込める列にだけB-treeインデックスを設定する。
2. **主キーの扱い**：主キーの列にはDBMSによって自動的にインデックスが作成されるため、今回の追加設定の対象からは除く。
3. **全文検索の扱い**：商品名と商品説明の部分一致検索には別途**全文検索エンジン**を利用するため、今回のB-treeインデックスの対象からは除く（先頭に%が付く部分一致「%キーワード%」は、文字の先頭から順序をたどる通常のB-treeインデックスでは効率よく絞り込めないためです）。

たとえば値が100種類あり均等に分かれていれば、1つの値を指定したときに残る割合は約1%（5%以下）ですが、値が3種類で一様分布なら1つの値を指定しても約33.3%（3分の1）が残り、5%以下という基準を満たしません。

この基準と表2・表3の分布条件を踏まえて、「出品」表と「カテゴリ」表の各列を順番に判定してみましょう。

| 表・列 | インデックス設定の判断と理由 |
| --- | --- |
| **出品・カテゴリID** | **設定する**：指定カテゴリとの結合条件（ON句）で使います。表2より中カーディナリティかつ一様分布であり、十分に絞り込めるため対象になります |
| **出品・出品価格** | **設定する**：WHERE句の範囲検索（BETWEEN）で使います。異なる値が多く、表2の分布条件から十分に絞り込めるため対象になります |
| 出品・出品ID | 設定しない：主キーであり、自動的にインデックスが作成されるため追加不要です |
| 出品・出品者ID | 設定しない：カーディナリティは高いものの、図2の出品商品検索SQLの結合や検索条件では使われていないため不要です |
| 出品・商品名、商品説明 | 設定しない：本文の方針により全文検索エンジンを使う列であり、B-treeインデックスの追加対象外です |
| 出品・商品状態、出品状況 | 設定しない：WHERE句で使いますが、表2より「1〜3の整数値で一様分布」なので1つを指定しても約33.3%（3分の1）が残り、5%以下の方針を満たしません |
| **カテゴリ・上位カテゴリID** | **設定する**：再帰問合せで親から子を探す条件（B.上位カテゴリID = C.カテゴリID）で使います。表3より中カーディナリティかつ一様分布で絞り込みに有効なため対象になります |
| カテゴリ・カテゴリID | 設定しない：再帰の出発点や結合で使いますが、主キーであり自動インデックスがすでにあるため追加不要です |
| カテゴリ・カテゴリ名 | 設定しない：SELECT句で取得はしますが、検索の絞り込み条件や結合条件には使われていないため不要です |

したがって、解答は出品表が **カテゴリID，出品価格**、カテゴリ表が **上位カテゴリID** となります。

補足として、表2にある出品価格の「0.00003」という数値の意味も確認しておきましょう。これは連続分布モデルにおける「確率密度の最大値」です。確率密度から割合を見積もるときは「価格の区間幅」を掛け合わせます。たとえば価格の狭い区間幅「0.01」を考えると、その区間に入る割合は最大でも `0.00003 × 0.01 = 0.0000003 = 0.00003%` となり、基準である5%を十分に下回ることが分かります。

また、本文の最後にあるとおり、表2・表3の分布はサービス開始前の想定であり、サービス開始後には実際のデータ分布や検索状況に合わせてインデックスを定期的に見直すことが大切です。インデックスは検索を速くする一方で、データの追加・更新時にはインデックス自体の更新コストも発生します。「とりあえず全列に付ければよい」のではなく、**「実際のSQLの条件や結合で使われるか」「主キーや全文検索と重複しないか」「指定したときに5%以下など十分に絞り込めるか」を組み合わせて判断すること**が、データベース設計の重要な考え方です。

## 次の問題でも使うこと

- E-R図の穴埋めでは、まず凡例（矢印の向きが「多」を表すのか、矢印なしが「1対1」かなど）を確認し、業務ルール（「分割・まとめ発送は不可」「上位カテゴリ1つに下位カテゴリ複数」など）と対応付ける。
- 多対多の関連（利用者どうしのフォローなど）は、2つの外部キーを持つ交差エンティティ（フォロー表）を間に置くことで、2つの「1対多」の関連に分解できる。
- **WITH RECURSIVE** を使った階層検索では、「出発点を選ぶSELECT」と「親のIDと子の上位IDを結合して1段下へ降りるSELECT」を **UNION ALL** でつなぐ。親子を比較する列の向き（親を探すのか、子を探すのか）を逆にしないよう注意する。
- インデックスを設定する列を選ぶときは、①検索・結合条件で使われているか、②主キー（自動インデックス）ではないか、③カーディナリティや分布から見て十分に絞り込めるか（選択率が低いか）の3点をチェックする。
