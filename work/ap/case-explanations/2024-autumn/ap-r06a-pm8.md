# オブジェクト指向設計――通信方法とデータ形式を組み替えられる部品にする

## この問題は、何を考える問題だった？

M社のデータ連携ハブは、人事システムなどからデータを受け取り、接続先の各システムが受け取れる形式に変換して送信するシステムです。これまで手続き型で開発されていましたが、接続先の仕様変更や追加が多く、似たようなコードを複数箇所へコピーして使っていたため、1か所の仕様変更が多くの修正へと広がりやすくなっていました。

この問題を解決する軸は、次の3つの役割を別々のクラスとして切り分け、必要な部品を自由に組み合わせられるように設計することです。

```text
1. 扱うデータの項目（連携データ → 組織データ など）
2. 文字列・バイト列への変換形式（フォーマット → CSV / XML）
3. 送受信の通信手順（プロトコル → FTPS / HTTPS）
```

オブジェクト指向の基本概念（カプセル化・継承・多相性）やクラス図の表記ルールを押さえたうえで、図2のクラス図でそれぞれの部品がどう組み合わされているかをたどっていきましょう。

## まず、図1・図2の用語とクラス図のルールを整理しよう

図1・図2に登場する通信・データ形式の用語と、クラス図の読み方を表で整理しておきましょう。

| 分類 | 用語・表記 | この問題での意味と役割 |
| --- | --- | --- |
| **通信プロトコル（図1）** | **FTPS / HTTPS** | データを送受信する手順・規則。**FTPS**はFTPによるファイル転送をTLSで暗号化した通信、**HTTPS**はHTTP通信をTLSで暗号化した通信 |
| **データフォーマット（図1）** | **CSV / XML** | データの表現形式。**CSV**は項目をカンマなどで区切る形式、**XML**はタグで階層構造を表す形式 |
| **クラスとインスタンス** | クラス・属性・メソッド | データ（**属性**）と処理（**メソッド**）の設計図が**クラス**、そこから生成した実体が**インスタンス**。メソッドへ渡す入力を**引数**、返す出力を**戻り値**という |
| **クラス間の関係（図2）** | **継承（白抜き三角矢印）**と**関連（実線）** | 三角矢印の先が**親クラス**で、親の性質を子クラスが引き継ぐ（**継承**）。矢印のない実線は部品としての結び付き（**関連**）を表す |
| **抽象とインターフェース** | 斜体表記 / `interface` | 斜体のクラス・メソッドは**抽象クラス・抽象メソッド**、`interface` は**インターフェース**で、どちらも「共通の呼び出し窓口（型）を定め、具体的な処理は子クラスで実装する」ために使う |

なお、図1では人事システム（ERP：人事・販売・会計などの基幹業務を統合管理するシステム）から「FTPS・CSV」でデータを取得し、販売システムへは「FTPS・CSV」、製造システムと会計システムへは「HTTPS・XML」で送信しています。

## 設問1 a・b・c｜三つの仕組みを図の役割と対応させる

設問1は、オブジェクト指向の3つの基本概念（空欄a・b・c）を答える問題です。本文の説明と図2の設計を対応させて確認しましょう。

- **空欄a：カプセル化**
  互いに関連するデータ（属性）と、そのデータを扱う処理（メソッド）を1つのクラスにまとめ、外部に公開する窓口と内部に隠す実装を切り分ける設計です。外部のクラスが内部のデータの持ち方に直接依存しないようにすれば、クラス内部の実装を変更したときの影響が外へ広がるのを防ぐことができます。
- **空欄b：継承**
  親クラスで定義した属性やメソッドを引き継いで、新しい子クラスを作る仕組みです。図2では「連携データ」を親として「組織データ」が作られ、「フォーマット」を親として「CSV」や「XML」が作られています。共通する部分を親クラスに置いて再利用し、違いがある部分だけを子クラスに記述できます。
- **空欄c：多相性**（ポリモーフィズム）
  同じ名前のメソッドを呼び出しても、実際に割り当てられているインスタンスの種類に応じて異なる処理が実行される性質です。たとえば、フォーマット型の部品に対して同じ「シリアライズ」というメソッドを呼び出しても、中身が「CSV」のインスタンスならCSV形式へ変換する処理が動き、「XML」のインスタンスならXML形式へ変換する処理が動きます。

呼び出す側のクラスで「もしCSVならこの処理、もしXMLならあの処理」と毎回条件分岐を書き分ける必要がなくなるのが、**多相性**の大きな強みです。

## 設問2(1) d｜コネクタで決めた取得の窓口を、組織コネクタに用意する

設問2(1)は、図2の「組織コネクタ」クラスにある空欄dのメソッド名を答える問題です。

図2の上部にあるインターフェース「コネクタ」を見ると、外部から呼び出せる窓口として **データ取得()** と **データ送信(data:連携データ):真偽値** の2つが定義されています。

「コネクタ」を実装する子クラスの「組織コネクタ」を見ると、下の行にはすでに「+ データ送信(data:連携データ):真偽値」が書かれています。したがって、その上の空欄dにはもう一方の窓口である **データ取得()** が入ります（末尾の丸括弧 () は引数がないことを表すため、図の表記どおり **データ取得()** と答えます）。

## 設問2(2) e・f｜#の保護属性と、同じメソッドを差し替える意味

設問2(2)は、図2のクラス図に関する説明文の空欄e・fを解答群から選ぶ問題です。

まず空欄eを確認しましょう。図2の凡例にあるとおり、属性やメソッドの前に付く記号はアクセスできる範囲（可視性）を表しています。

- **+**（公開 / public）：どのクラスからでもアクセスできる
- **−**（私的 / private）：そのクラスの内部からしかアクセスできない
- **#**（保護 / protected）：そのクラス自身と、**そのクラスを継承した子クラス**からアクセスできる

「連携データ」クラスの属性「論理削除」（データを物理的に消去する代わりに、削除済みという印を付けて管理するための属性）には **#（保護）** が付いています。「組織データ」は「連携データ」を継承した子クラスなので、組織データのメソッドから論理削除属性へアクセスすることが**できる**と判断できます。したがって、空欄eの答えは**オ**（できる）です。

次に空欄fを確認しましょう。「XML」クラスでは、親クラスである「フォーマット」の抽象メソッド「シリアライズ(data:連携データ):バイト列」と**同じ名称・同じ引数・同じ戻り値**のメソッドを定義して、XML形式へ変換する具体的な処理を実装しています。このように、親クラスで宣言されたメソッドを子クラスで同じ呼び出し形のまま再定義（上書き）することを **オーバーライド** と呼びます。したがって、空欄fの答えは**ア**（オーバーライド）です。

解答群の各選択肢の違いも整理しておきましょう。

| 選択肢 | 語句 | この設問での判断と理由 |
| --- | --- | --- |
| **ア** | **オーバーライド** | **空欄fに合致します。親クラスと同じ名称・引数・戻り値を持つメソッドを子クラスで再定義する仕組みです** |
| イ | オーバーロード | 同じクラス内などで、同じ名前でも「引数の数や型が異なるメソッド」を複数定義して使い分ける仕組みであり、空欄fの説明とは異なります |
| ウ | コンストラクタ | インスタンスを生成するときに初期化処理などを行う特別なメソッドであり、親のメソッドを再定義する仕組みの名称ではありません |
| エ | できない | 空欄eには合いません。論理削除属性の可視性は #（保護）なので、子クラスである組織データからアクセスできます |
| **オ** | **できる** | **空欄eに合致します。親クラスの #（保護）属性には子クラスからアクセスできます** |
| カ | デストラクタ | インスタンスが破棄されるときに呼ばれる後片付け用のメソッドであり、空欄fの説明とは異なります |

## 設問2(3) g・h｜製造システムへはXML形式をHTTPSで送る

設問2(3)は、組織データを「製造システム」へ送信するときに、組織コネクタのコンストラクタ「組織コネクタ(form:フォーマット, pro:プロトコル)」へ渡すインスタンスのクラス名（空欄g・h）を答える問題です。

まず図1で「製造システム」へ送信する際の条件を確認すると、通信プロトコルが **HTTPS**、データフォーマットが **XML** となっています。

一方、図2の組織コネクタの引数を見ると、第1引数の「form:フォーマット」が空欄g、第2引数の「pro:プロトコル」が空欄hに対応しています。

- 空欄g（form：フォーマットの子クラス）：**XML**
- 空欄h（pro：プロトコルの子クラス）：**HTTPS**

ここで、送信処理が動く流れも追っておきましょう。**シリアライズ**とは、プログラム内部のオブジェクト（連携データ）を送信・保存できる文字列やバイト列の形式へ変換することです（逆に、受信したCSVやXMLのバイト列を解析して内部の連携データに戻すことを**デシリアライズ**と呼びます）。

製造システムへの送信時には、組織コネクタが通信担当（pro＝HTTPSのインスタンス）の「送信(data, form)」メソッドを呼び出し、その中で形式担当（form＝XMLのインスタンス）の「シリアライズ(data)」メソッドを呼び出します。**formとして渡した実体がXMLのインスタンスだからこそ、多相性によってXMLクラスのシリアライズ処理が実行される**のです。

同じ組織コネクタのクラスを使っても、販売システムへ送るときは引数を「CSV」と「FTPS」のインスタンスに替えるだけで対応できます。通信方法とデータ形式を別々の部品として注入（合成）できるようにしたことで、組合せが変わってもコネクタや変換処理を作り直さずに済む設計になっています。

## 設問3(1)｜新しいデータ項目に対する二つの子クラスを加える

設問3(1)は、新たに「研修受講記録」のデータを送受信したいとき、どのクラスを親として2つの子クラスを追加すればよいかを答える問題です。

研修受講記録は、これまでの組織データ（組織コード、組織名など）とは持つデータの項目が異なります。そのため、次の2つのクラスを新しく用意する必要があります。

1. 研修受講記録のデータ項目を保持するクラス（既存の「組織データ」に相当）→ 親クラスは **連携データ**
2. 研修受講記録のデータを取得・送信するクラス（既存の「組織コネクタ」に相当）→ 親クラスは **コネクタ**

一方、データをCSVやXMLに変換する「CSV」「XML」クラスや、FTPSやHTTPSで通信する「FTPS」「HTTPS」クラスは、既存の部品をそのまま組み合わせて再利用できます。したがって、追加する2つのクラスの親クラスは **連携データ，コネクタ** です。

## 設問3(2)｜CSVとXMLに共通する文字コード変換を親へ置く

設問3(2)は、CSV形式とXML形式の両方で共通して必要になった「文字コード変換処理」のメソッドを、修正量が最も少なくなるようにどのクラスへ追加すべきかを答える問題です。

**文字コード**とは、文字をコンピュータ内部でどのような数値（バイト列）として表すかを定めた規則（UTF-8やShift_JISなど）です。接続先のシステムが求める文字コードに合わせるため、CSVとXMLのどちらの形式でも同じ文字コード変換処理を使いたい場面です。

もし「CSV」クラスと「XML」クラスの両方に同じ変換メソッドを別々にコピーして書いてしまうと、変換処理に修正が入ったときに2か所とも直さなければならず、冒頭で課題になっていた「コピーによる保守性の低下」を繰り返してしまいます。

そこで図2を見ると、「CSV」と「XML」には共通の親クラスとして **フォーマット** があります。この **フォーマット** クラスに文字コード変換のメソッドを追加すれば、継承によって子クラスであるCSVとXMLの両方から共通の処理として利用できます。したがって、答えは **フォーマット** です（通信手順を扱う「プロトコル」は、データの表現形式や文字コードを扱う場所ではないため区別しましょう）。

なお、親へメソッドを追加しただけで、既存の処理が自動的に文字コード変換を実行するわけではありません。実際に変換が必要なシリアライズやデシリアライズの経路から、その共通メソッドを呼び出すようにします。**「共通処理を置く場所（親クラス）」と「それをどこから呼び出すか」を整理して設計すること**で、最小限の修正で機能を追加できるというオブジェクト指向のメリットが活きてきます。

## 次の問題でも使うこと

- **カプセル化**（データと処理をまとめ、公開窓口と内部実装を分ける）、**継承**（親クラスの共通性質を子クラスが引き継ぐ）、**多相性**（同じ窓口の呼び出しでも、実際のインスタンスの種類に応じた処理が動く）の3つの役割をクラス図の上で説明できるようにする。
- クラス図の可視性記号は、**+** が公開（public）、**−** が私的（private）、**#** が保護（protected：自クラスと子クラスからアクセス可能）を表す。
- 親クラスと同じ名前・引数・戻り値のメソッドを子クラスで再定義することを**オーバーライド**と呼び、引数の型や数が異なる同名メソッドを定義する**オーバーロード**と区別する。
- 複数の子クラス（CSVとXMLなど）でまったく同じ処理が必要になったときは、各子クラスにコピーするのではなく、**共通の親クラス（フォーマット）にメソッドを置いて継承させる**ことで重複をなくし保守性を高められる。
